Overview
Every iOS app has exactly one instance of 
 (or, very rarely, a subclass of 
). When an app launches, the system calls the 
 function. Among its other tasks, this function creates a singleton 
 object that you access using 
.
Your app’s application object handles the initial routing of incoming user events. It dispatches action messages forwarded to it by control objects (instances of the 
 class) to appropriate target objects. The application object maintains a list of open windows (
 objects), which it can use to retrieve any of the app’s 
 objects.
The 
 class defines a delegate that conforms to the 
 protocol and must implement some of the protocol’s methods. The application object informs the delegate of significant runtime events—for example, app launch, low-memory warnings, and app termination—giving it an opportunity to respond appropriately.
Apps can cooperatively handle a resource, such as an email or an image file, through the 
 method. For example, an app that calls this method with an email URL causes the Mail app to launch and display the message.

Subclassing notes
Most apps don’t need to subclass

If your app must handle incoming events before the system does—a very rare situation—you can implement a custom event or action dispatching mechanism. To do this, subclass

Intercepting events is only rarely required and you should avoid it if possible.
