# 07 · 上下文与记忆引擎

> **摘要**：手机上跑 Agent，**上下文是最贵的资源**——它同时消耗钱（按 token 付费）、内存、延迟和电量。Rune 的上下文引擎因此不是"把东西塞进去"，而是一套**预算制装配管线**：先算钱，再分配额度，再按优先级填充，超了就压缩，压缩后还要保证"关键事实不丢"。
> 记忆则分三层：**工作记忆（本次 Turn）→ 项目知识（跨会话）→ 原始事件（永不遗忘的证据）**。

---

## 1. 上下文预算制装配

### 1.1 预算分配（单次模型调用）

```
可用窗口 W（由所选模型决定，如 200k / 128k / 32k）
├─ 固定开销：系统提示层 1+2   ≤ 25% W   （字节级稳定，命中 Prompt Cache）
├─ 会话历史（含压缩摘要）      ≤ 30% W
├─ 本轮工具结果               ≤ 25% W
├─ 记忆检索命中               ≤ 10% W
└─ 输出预留                   ≥ 10% W   （绝不允许被挤占）
```

**实现要点**：装配器先按"目标成本"倒推，而不是"能塞多少塞多少"。用户设了"单 Turn ≤ $0.05"，装配器就会把上下文压到对应 token 数，而不是把 200k 窗口用满。

### 1.2 装配管线

```
输入：Turn 目标 + 当前计划 + 候选素材池
  │
  ├─ 步骤 1  素材收集（并行）
  │     · 项目指令文件（缓存）
  │     · 工作区结构摘要（缓存）
  │     · 记忆检索（关键词 + 向量，见 §6）
  │     · 当前 Turn 已产生的事件（工具结果 / 错误 / 计划状态）
  │     · 用户显式引用（@文件、粘贴、图片、分享内容）
  │
  ├─ 步骤 2  打分（相关性 / 新鲜度 / 来源信任 / 成本）
  │     score = w1·语义相似 + w2·最近使用 + w3·是否用户显式引用
  │             − w4·token 成本 − w5·污点惩罚
  │
  ├─ 步骤 3  配额填充（按区块，块内按分数贪心填充）
  │
  ├─ 步骤 4  压缩（超配额时，见 §5）
  │
  ├─ 步骤 5  稳定性对齐（层 1+2 字节不变 → 缓存命中）
  │
  └─ 步骤 6  自检
        · 是否包含"当前目标"？（必须有）
        · 是否包含"未完成的 todo"？（必须有）
        · 是否包含"最近一次失败"？（若有，必须有）
        · 是否包含不可信内容的边界标记？（必须有）
        · 输出预留是否够？（不足则继续压缩）
```

**第 6 步是硬性断言**：任一条不满足则装配失败并降级（用更小的上下文重试），而不是把不完整的上下文发出去。经验表明"漏掉当前目标"和"漏掉最近的失败"是两个最常见的导致 Agent 跑偏的原因。

## 2. 项目指令文件（RUNE.md）

### 2.1 兼容策略（迁移友好）

Rune 按以下顺序查找并**合并**项目指令（后者可覆盖前者）：

```
1. <workspace>/AGENTS.md            ← Codex 生态
2. <workspace>/CLAUDE.md            ← Claude Code 生态
3. <workspace>/RUNE.md              ← Rune 原生（最高优先级）
4. <workspace>/.rune/instructions/*.md
5. 全局：~/Rune/global.md           ← 用户跨项目偏好
```

**合并规则**：章节级合并（按二级标题），同名章节以高优先级为准；冲突时在装配日志中记录，UI 可查看"最终生效的指令"。

> **为什么兼容**：用户的仓库里已经有 `AGENTS.md` / `CLAUDE.md` 了。让它们**开箱生效**，是"从桌面迁移过来零成本"的关键细节。

### 2.2 自动生成（首次进入项目时）

首次打开一个工作区，Rune 用**端侧模型 + 廉价模型**生成一份 `RUNE.md` 草稿：

```markdown
# 项目：shop-api

## 这是什么
支付订单服务，Python 3.12 + FastAPI + PostgreSQL，部署在 ECS。

## 怎么跑
- 安装：`pip install -r requirements.txt`（沙箱内已预装主要依赖）
- 测试：`pytest -q`（全量约 2 分钟）
- 只跑单文件：`pytest tests/test_orders.py -q`

## 代码约定
- 金额一律用 `Decimal`，禁用 float（见 src/money.py）
- 所有外部调用必须有超时
- 新增接口必须同时更新 docs/openapi.yaml

## 不要动
- migrations/ 下的历史迁移文件
- .env 与任何凭据文件

## 已知坑
- tests/legacy/ 里有一批依赖网络的测试，本地会失败（正常）
```

草稿生成后**要求用户确认或修改**（30 秒内可完成），然后纳入缓存层。

## 3. 工作区索引

### 3.1 三层索引（渐进构建，不阻塞使用）

| 层 | 内容 | 构建成本 | 用途 |
|---|---|---|---|
| **L0 结构摘要** | 目录树（top-200）+ 文件类型分布 + 构建/测试命令探测 + 入口文件识别 | < 1s（首次进入） | 每次装配必带（很小） |
| **L1 符号索引** | tree-sitter 解析出的类/函数/方法定义位置（文件 + 行号 + 签名） | 增量，1k 文件约 5-15s | `find_symbol`、`outline_file`、精确跳转 |
| **L2 语义索引** | 代码/文档块的向量（端侧 embedding），分块 ~512 token | 后台 Job，1k 文件约 2-5 分钟 | `semantic_search`、记忆检索 |

**构建策略（移动端特化）**：
- L1/L2 都在 **BGProcessingTask**（充电 + 空闲）里增量构建，绝不在用户等着的时候跑。
- 只索引**被 git 跟踪的文件**（+ 未被忽略的新文件），跳过 `node_modules`、`build`、二进制、> 512KB 的文件。
- 索引与 **git commit hash** 绑定：换分支/拉取后增量更新变更文件，不全量重建。
- 内存索引可选（会话结束释放），磁盘索引持久化（`artifacts/index/`，可重建、不备份）。

### 3.2 端侧 embedding

| 方案 | 维度 | 体积 | 质量 | 用途 |
|---|---|---|---|---|
| **`NLEmbedding.sentenceEmbedding(for:)`**（系统自带） | 512 | **0（系统）** | 中 | **默认**，零成本零体积零下载 |
| `NLContextualEmbedding`（iOS 17+） | — | 需下载资产 | 较好 | 可选升级。⚠️ **模拟器不可用**，且需处理资产下载 |
| Core ML MiniLM-L6 | 384 | ~90MB | 较好 | 用户可选升级 |
| BGE-small-en-v1.5 | 384 | ~130MB | 好（英文） | 英文项目可选 |
| MLX MiniLM | — | ~600MB | 好 | 大内存设备可选。⚠️ 已知 pooling bug，需自行修正 |

**默认用系统 embedding**：零体积、零下载、够用 —— 符合"手机上能跑起来比跑得好更重要"的工程哲学。

⚠️ **两个必须处理的问题**：
1. **中文质量未经核实** `[不确定]` → 上线前必须用真实中文语料做一次 recall 评测，否则中文项目的语义检索可能几乎不可用。
2. **中文分词/检索是硬需求**（见 §4.2 的 FTS5 中文陷阱），因此**语义检索必须建立在正确的词法检索之上**，不能只靠向量。

### 3.3 索引的存储与重建

| 项 | 设计 |
|---|---|
| 位置 | `artifacts/index/`（**不备份、可重建**）+ 增量状态记在 `project_knowledge_meta` |
| 版本绑定 | 与 commit hash 绑定；换分支或 pull 后**只增量更新变更文件** |
| 重建成本 | 全量重建 1k 文件约 2-5 分钟（后台 `BGProcessingTask` 完成） |
| 失效处理 | 索引与当前 commit 不一致时，**语义检索降级为纯词法检索并提示**（而不是给出过时结果） |
| 中文特例 | 若工作区含 CJK 路径/内容，**强制启用 CJK 分词器**（见 §4.2），否则检索会"零结果" |

---

### 4.1 ⚠️ FTS5 中文陷阱（不处理就等于检索没做）

**事实**：SQLite FTS5 的 `unicode61` 分词器**会静默丢弃 CJK 字符**。也就是说，一个中文项目里的中文 transcript、中文 README、中文注释，在全文检索里会返回**零结果**——而且**不报错**。

**这是最容易在中文项目上"静默失效"的一处**。处理方案（三选一，按项目语言自动切换）：

| 方案 | 做法 | 适用 |
|---|---|---|
| **CJK 分词器** | 引入 CJK 专用 FTS5 tokenizer（如 `simple` 系列） | 中文/日文为主的语料 |
| **trigram** | 用 FTS5 的 `trigram` 分词器 | 混合语言、要支持子串匹配 |
| **代码标识符分词** | 自研 tokenizer：驼峰/下划线/点号切分 + ASCII 保留 + CJK 按双字切分 | **代码检索的主路径** |

**实施要求**：
- 建库时**按工作区内容探测语言**，选择对应 tokenizer（并记录在 `project_knowledge_meta`，切换语言需重建索引）。
- 上线前必须用**中文语料**做一次 recall 验证（[附录 B §12](附录B-技术选型核实表.md) 第 5 项）。
- 全文检索对象包括：事件日志摘要、项目知识条目、工作区文件内容、技能库。

### 4.2 混合检索管线

```
query
  ├─ ① 结构化过滤：路径前缀 / 文件类型 / 时间范围 / git 分支
  ├─ ② 词法检索：FTS5（BM25）+ 标识符切分（驼峰/下划线拆词）
  ├─ ③ 语义检索：查询向量 × 分块向量（cosine，Top-50）
  └─ ④ 融合重排：RRF（Reciprocal Rank Fusion）
        最终分 = 1/(k+rank_bm25) + 1/(k+rank_vec)，k=60
        + 小幅加权：最近打开 (+) / 不可信来源 (−) / 用户显式引用 (+++)
  └─ ⑤ 结果处理
        · 每个命中截取"最佳片段 ± 上下文"
        · 附来源标签（文件路径 + 行号 + 信任级）
        · 去重（同一文件多处命中合并）
        · 按 token 预算截断
```

**为什么必须混合**：纯向量检索在代码库上表现不稳定（变量名、缩写、精确字符串），纯 BM25 又抓不住"这个函数负责什么"这类语义查询。RRF 融合是最省事且效果稳的方案。

### 4.3 检索结果的呈现（给模型看的样子）

```
<retrieved source="src/money.py:12-24" trust="project" score="0.87" why="语义+关键词命中：round,currency">
  ...
</retrieved>
```

`why` 字段让模型知道"为什么给你这段"，显著减少无效引用。

## 5. 压缩（Compaction）

### 5.1 三级压缩策略

| 级别 | 触发 | 手段 | 代价 |
|---|---|---|---|
| **L1 结构化裁剪** | 单区块超配额 | 工具结果只保留：结论 + 关键行 + 制品句柄；丢弃中间过程 | 0（本地） |
| **L2 端侧摘要** | 历史超配额 | 用**端侧模型**把旧轮次压成要点（不调云端，零成本） | 端侧推理，~1s |
| **L3 主模型全量压缩** | 会话太长（> 60% 窗口）或需要高保真 | 用当前主模型做一次"结构化压缩"（见 5.2） | 一次模型调用（成本可见） |

**关键洞察：能端侧压就端侧压。** 桌面 Agent 的压缩通常直接用主模型（贵），手机上每次压缩都要花钱，用户会不满。端侧小模型做"把 12 轮对话压成 8 条要点"这类任务完全够用。

### 5.2 结构化压缩的产物格式（L3）

不是"一段摘要散文"，而是**保留可执行性的结构化摘要**：

```json
{
  "goal": "修复退款测试失败",
  "confirmed_facts": [
    {"fact": "金额计算在 src/money.py:12 使用 round(amount)", "evidence": "read_file src/money.py:12"},
    {"fact": "测试失败原因是 Decimal 与 float 比较", "evidence": "run_tests pytest -q → 12 failed 中的首个失败栈"}
  ],
  "decisions": [
    {"decision": "改用 round(amount, currency.exponent)", "why": "避免币种精度丢失"},
    {"decision": "已拒绝方案：直接改测试断言", "why": "用户明确要求修业务代码"}
  ],
  "artifacts": [
    {"path": "artifacts/ci-log-0912.txt", "summary": "CI 失败日志 3.2MB，关键错误在第 412 行"}
  ],
  "open_items": [
    {"item": "跑全量测试", "status": "pending"},
    {"item": "更新 CHANGELOG", "status": "pending"}
  ],
  "rejected_paths": ["尝试升级依赖版本（无效，已回滚）"],
  "untrusted_notes": [
    {"note": "issue #42 里有一个要求访问外部域名的链接", "origin": "web:github.com/.../42", "tainted": true}
  ]
}
```

**`rejected_paths` 是最容易被忽略但最有价值的一栏**：它防止 Agent 在压缩后重走已经证明失败的路（这是长任务里最典型的"绕圈子"）。

### 5.3 压缩的触发与体验

| 触发 | 用户可见性 |
|---|---|
| 自动（历史超配额） | 时间轴上一条"已压缩 12 轮对话（保留 8 条要点）"，可展开查看原始内容（仍在事件日志里） |
| 手动 `/compact` | 立即执行，展示压缩前后 token 数与节省金额 |
| 会话恢复时 | 若上次会话被压缩过，顶部长条提示"上下文已压缩，关键结论已保留" |

**铁律：压缩永不删除事件。** 原始内容永久保留在事件日志里，压缩只影响"送入模型的内容"。用户随时可以展开、回滚、重新压缩。

## 6. 三层记忆

```
┌─ 工作记忆（Working Memory）─────────────────────────────┐
│  生命周期：单次 Turn（或单次 Goal 轮次）                   │
│  内容：目标、计划、todo、本轮工具结果、当前错误             │
│  存储：内存 + 事件日志                                    │
│  检索：直接读（无需检索）                                  │
└──────────────────────────────────────────────────────────┘
                          ↓ 提炼（Goal / Turn 完成时）
┌─ 项目知识（Project Knowledge）──────────────────────────┐
│  生命周期：跨会话，跟随项目                               │
│  内容：项目结构理解、关键决策、坑与约定、常用命令、           │
│        "上次怎么解决的"、架构笔记                          │
│  存储：SQLite 表 + 向量索引（按工作区隔离）                 │
│  写入：Turn 完成时提炼候选 → 去污检查 → 写入或废弃           │
└──────────────────────────────────────────────────────────┘
                          ↑ 溯源
┌─ 原始事件（Raw Events）─────────────────────────────────┐
│  生命周期：永久（用户可删）                                │
│  内容：完整事件日志（所有工具调用、结果、模型输入输出摘要）    │
│  存储：SQLite 追加表 + 哈希链                             │
│  检索：FTS5 全文 + 时间范围 + 会话/目标过滤                 │
│  用途：溯源（"这个结论哪来的"）、重新提炼、审计              │
└──────────────────────────────────────────────────────────┘
```

### 6.1 为什么要三层而不是"一个向量库"

| 问题 | 只有向量库 | 三层结构 |
|---|---|---|
| "这话是哪来的？" | 说不清 | 从项目知识 → 原始事件，逐层溯源 |
| 记忆被污染了怎么办？ | 只能删 | 从原始事件重新提炼（记忆可重建） |
| 记忆过期了怎么办？ | 无法检测 | 原始事件带时间戳与 commit hash，可判定"记忆基于 a1b2c3，当前是 d4e5f6，可能过期" |
| 用户想看"你到底记住了什么" | 一堆向量 | 人类可读的知识条目列表，可编辑可删除 |

### 6.2 项目知识的条目形态

```swift
public struct KnowledgeItem: Sendable, Codable {
    public let id: KnowledgeID
    public var title: String              // "退款金额计算的精度约定"
    public var body: String               // 人类可读的正文（Markdown）
    public var kind: Kind                 // .convention .pitfall .decision .howto .structure .preference
    public var scope: Scope               // .project(workspaceID) / .global
    public var source: Source             // 溯源：哪次 Turn / 哪个事件 / 哪个文件
    public var trust: TrustLevel          // 来源信任级（不可信来源不自动入库）
    public var validForCommit: String?    // 基于哪个 commit 生成（用于过期判定）
    public var lastUsedAt: Date?          // 用于淘汰
    public var useCount: Int
    public var embedding: [Float]?
}
```

### 6.3 记忆的写入策略（防止"记忆垃圾场"）

| 触发 | 写入什么 | 门槛 |
|---|---|---|
| Turn 完成 | 最多 1 条"这次学到的事"（若有） | 必须通过"下个会话还用得上吗？"的端侧判定 |
| 用户纠正 Agent | **必写**（"以后不要用 float 存金额"） | 无门槛，且高优先级 |
| 用户显式说"记住" | 必写 | 直接写，回显确认 |
| 发现项目约定（读文件推断） | 候选，需 ≥2 次观察到同一模式 | 中门槛 |
| 失败与教训 | 写入（"tests/legacy 依赖网络会失败"） | 中门槛 |
| 来自不可信内容 | **不自动写**（T14） | 需用户确认，且标记 tainted |
| Goal 完成 | 1 条 Goal 摘要（成果 + 方法 + 坑） | 无门槛 |

**总量控制**：单项目知识条目上限 300 条；超出按 `useCount × 新鲜度` 淘汰到"归档"（仍可检索，但不参与自动装配）。

### 6.4 记忆的检索与注入

只有**与当前 Turn 强相关**的记忆才进上下文（预算 ≤ 10% W）：

```
检索：query = 当前目标 + 计划步骤标题 + 涉及文件路径
融合：语义 + 关键词 + kind 权重（.preference 和 .decision 权重更高）
数量：Top-5，每条 ≤ 120 token
格式：
<memory kind="convention" scope="project" trust="user" age="3d" source="turn 42">
  金额一律用 Decimal，禁用 float。见 src/money.py。
</memory>
```

**`.preference` 类记忆（用户偏好）必须最高优先级**，且**不参与淘汰**——"我讨厌你写这么长的回复"这类记忆如果丢了，用户会觉得产品很蠢。

## 7. 反思（Reflection）：当页面不够用时

检索是"找相似"，反思是"回答为什么"。当用户问：
- "我们为什么当初选了 PostgreSQL 而不是 MySQL？"
- "这个项目里我最常踩的坑是什么？"
- "上次那个 CI 问题最后是怎么解决的？"

单条记忆检索答不了，需要**跨记忆推理**。Rune 的实现：

```
reflect(question)
  ├─ ① 生成 3-5 个子查询（端侧模型）
  ├─ ② 对每个子查询做混合检索（跨三层记忆）
  ├─ ③ 收集候选证据（≥15 条，带溯源）
  ├─ ④ 用主模型做一次"带证据的推理"（强制引用证据 ID）
  └─ ⑤ 输出：结论 + 证据列表（可点开源到原始事件）+ 置信度 + "记忆可能过期"的提示
```

**反思是显式动作**（工具 `memory_reflect` 或用户输入 `/why`），不是每次都跑——它贵且慢。用户价值高，成本可控。

## 8. 记忆的隐私与作用域

| 作用域 | 隔离 | 说明 |
|---|---|---|
| **项目（工作区）** | 完全隔离 | 项目 A 的记忆绝不出现在项目 B 的上下文里 |
| **全局** | 用户偏好、通用技巧 | 用户显式标记为"全局"的才跨项目 |
| **会话临时** | 单会话 | 敏感内容（"这次别记"） |

**"这次别记"开关**：每个会话有一个开关（会话头长按 → 不记录记忆）。开启后本次会话产生的知识条目不写入项目知识，只留原始事件（用户仍可回溯）。

**导出与迁移**：记忆可导出为 Markdown（人类可读）+ JSON（机器可读），可导入。这让用户不被锁定，也是"可信"的证据。
