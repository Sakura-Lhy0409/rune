## 2026-09-17 · 攻克本机构建环境（C2，耗时最长的一步）

**问题**：本机 `swift build` / `swift test` **完全不可用** —— 能加载 manifest、能生成构建图，但在调用 swiftc 编译目标时**静默退出（exit 1，零错误信息）**。

**排查过程（逐项排除）**
1. ❌ 中文路径？→ 把包复制到纯 ASCII 路径，同样失败。
2. ❌ 工具链损坏？→ 手动执行 **同一条 swiftc 命令完全成功**（产出 .swiftmodule 与 .o）。
3. ❌ 命名管道/匿名管道被禁？→ 两者都能正常创建。
4. ❌ batch mode / 索引库 / `-j 1` / `--disable-sandbox`？→ 全部同样失败。
5. ⚠️ `--use-integrated-swift-driver` 能走到 "Compiling …"，但仍在同一步失败（且该选项已废弃）。

**结论**：SwiftPM 在本环境的**子进程执行层**有问题，**与我们写的代码无关**。

**对策**：自建构建驱动 `Tools/rune.ps1`，直接用 swiftc 编译**被测模块**与**测试可执行文件**（含 swift-testing 入口）。
**连带发现并解决的 5 个坑**（全部写进 `PROJECT_STATE.md` §8.1）：
- 路径含中文 → swiftc 报 `error opening input file 'D:\??Ŀ\…'` → 建 **ASCII junction** `C:\Users\MSI-NB\rune-ws`；
- `link.exe` 不在 PATH → 必须先 `call vcvars64.bat`；
- 运行测试 exe 报 **0xC0000135**（DLL 找不到）→ PATH 需含 Swift Runtimes 与 `Testing-*/usr/**bin64**`（不是 `x86_64`，那里只有 .lib）；
- `Testing.__swiftPMEntryPoint` 有**两个重载** → 必须显式标注 `let code: CInt`；
- 写 `C:\` 根目录被沙箱拒绝 → 临时文件放用户目录。

**产出**：`Tools/rune.ps1`（`info` / `build` / `test` / `clean`）。

## 2026-09-17 · ✅ M0-2 完成：apply_patch 补丁引擎（C4）

**为什么先做它**：补丁引擎是编码 Agent 的心脏。模型改代码全靠它，**它写错 = Agent 会静默改错代码**。而且它完全平台无关，本机可测透。

**做了什么**（`Sources/RuneKernel/TextPatch.swift`，约 800 行）
- **双格式解析**：
  - Rune 原生（`*** File:` / `*** Create:` / `*** Delete:` + `@@ 锚点`）
  - **标准 unified diff**（`--- a/x` / `+++ b/x` / `@@ -10,3 +10,3 @@ fn`），含 `a/`、`b/` 前缀剥离、`/dev/null` 语义、`git diff --git`/`index`/`new file mode` 等元数据行忽略、`\ No newline at end of file` 忽略
  - 相对路径自动视为相对 `/workspace`（模型天然按仓库相对路径思考）
- **四级模糊匹配**：精确 → 忽略行尾空白 → 忽略首尾空白 → 忽略所有空白。**逐级放宽，但每一级都必须唯一**。
- **唯一性强制**：匹配到 0 处 → 给"最接近的位置"；匹配到 ≥2 处 → **拒绝并返回全部候选行号 + 上下文**。绝不猜。
- **原子性**：任一 hunk 失败 → 整份补丁（含其他文件）都不落地。有测试守护。
- **换行保真**：CRLF / LF / 无末行换行三向保真。
- **诊断可执行**：所有错误的 `modelFacingMessage` 都是"给模型看的、可直接据以修正"的说明，并附 `suggestion`。
- **`TextEdit.replaceUnique`**：`edit_file` 的引擎，唯一才替换（**多处匹配直接拒绝，绝不悄悄全改**——这是编码 Agent 最危险的失效模式之一）。

**验证方式**
```
pwsh -NoProfile -File Tools\rune.ps1 test RuneKernel
→ 通过 121 / 失败 0（累计 122 项断言全绿）
```

**过程中发现并修复的 4 个真实 bug**（都值得记录）
1. ⚠️ **Swift 字素簇陷阱**：`"\r\n"` 在 Swift 里是**单个 Character**，导致 `components(separatedBy: "\n")` 在 CRLF 文本上**完全不分割**——整个文件被当成一行，所有按行匹配的补丁会**静默失败**。修复：先归一化 CRLF 再分割。（已加进 `PROJECT_STATE.md` §8.2 T8）
2. `@@ 锚点`（Rune 原生，只有一对 `@@`）被误解析为空锚点——因为取锚点的函数只考虑了 unified diff 的两对 `@@`。修复：无第二对 `@@` 时取第一对之后的内容。
3. Create 块会保留与下一个指令之间的分隔空行 → 新文件多出空行。修复：flush 时裁掉尾部空行（并写明取舍）。
4. 替换文本的换行风格不跟随目标文件 → 在 CRLF 文件里插进 LF 行，diff 变整文件噪音。修复：`normalizeNewlines(_:to:)`。

另有 2 处是**测试自身写错**（`/workspace/tmp/...` 被解析成 workspace 下的 tmp 目录；`+ 标题` 在 unified diff 语义下确实要保留前导空格）→ 改成按**正确语义**断言，并把格式约定写进解析器的文档注释。

## 2026-09-17 · ✅ M0-3 完成：检索子系统 + 包骨架（C5 / C6）

## 2026-09-17 · ✅ M0-4 完成：网关纯逻辑（C7）

**为什么做它**：设计文档明确写着"流式工具调用拼装是**最容易写错的地方**"（docs/06 §4）。写错的后果是静默的——工具被调用时参数缺一块、或者同一轮里两个并行调用串了位。**必须先用测试把这块钉死**，否则后面接真实渠道时会花几倍时间去查。

**做了什么**（2 个源文件，约 800 行）
- **`JSONRepair`**：修复模型给出的坏 JSON——空参数→`{}`、被 `max_tokens` 截断、未闭合字符串/括号、**尾逗号（含闭合括号之前的那种）**、悬空键、未完成转义、中文标点。**修不好返回 nil**，交给运行时的"修正性重试"，而不是把半成品当参数用。
- **`ToolCallAssembler`**：
  - 四种协议形态：OpenAI 标准分片（按 `index`）/ OpenAI Responses / Anthropic blocks / Gemini 整块
  - **并行 index 交错到达**（两个工具调用的分片互相穿插）→ 必须正确归位
  - **7 种脏情况**全覆盖：空参数、JSON 截断、`name` 变成不同值、分片先于 start 到达、缺 name/id、重复 completed、`finish_reason` 缺失
  - **绝不重复产出**（重连 / 重放场景）
  - 诊断可观测：`allIssues` / `diagnostics` 让"这个渠道的流有多脏"变成数据
- **`ProviderQuirks`**：把渠道差异变成**声明式数据结构**（协议族 / 思考链字段 / **回传策略** / 缓存风格 / 流式用量 / 要不要打缓存断点 / 坑清单）。内置 6 个预设：openAICompatible / openAIResponses / anthropic / deepSeek / gemini / relay。**接入新渠道应该只是勾开关，不是改代码。**
- **`CostCalculator`**：缓存读 0.1× / 写 1.25× / DeepSeek 低谷 5 折 / OpenAI 长上下文 2×·1.5×；**并算出"因缓存省了多少钱"**（这是要给用户看的正反馈）。

**过程中发现并修复的问题（2 个真 bug）**
1. **真 bug：尾逗号修不掉**。`{"a": 1, "b": 2,}` 的尾逗号在最后那个 `}` **之前**，而我只从字符串末尾往前找 → 看到的是 `}`，直接放弃。修复：改成带字符串状态的**单遍扫描**，遇到逗号就向后跳过空白看是不是闭合括号（嵌套的 `{"a":{"b":1,},}` 也能修）。
2. **真 bug：诊断信息丢失**。`emit()` 把 issue 追加到了**局部副本** `issues`，而 `partials[index] = partial` 用的是追加之前的 `partial` → 返回值里能看到诊断，`allIssues` / `diagnostics` 里却看不到。这会让开发者面板**谎报"这个渠道很干净"**。
