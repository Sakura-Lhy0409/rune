**排查过程（逐项排除）**
1. ❌ 中文路径？→ 把包复制到纯 ASCII 路径，同样失败。
2. ❌ 工具链损坏？→ 手动执行 **同一条 swiftc 命令完全成功**（产出 .swiftmodule 与 .o）。
3. ❌ 命名管道/匿名管道被禁？→ 两者都能正常创建。

5. ⚠️ `--use-integrated-swift-driver` 能走到 "Compiling …"，但仍在同一步失败（且该选项已废弃）。

**结论**：SwiftPM 在本环境的**子进程执行层**有问题，**与我们写的代码无关**。

**对策**：自建构建驱动 `Tools/rune.ps1`，直接用 swiftc 编译**被测模块**与**测试可执行文件**（含 swift-testing 入口）。

## 2026-09-17 · ✅ M0-2 完成：apply_patch 补丁引擎（C4）

**为什么先做它**：补丁引擎是编码 Agent 的心脏。模型改代码全靠它，**它写错 = Agent 会静默改错代码**。而且它完全平台无关，本机可测透。

**做了什么**（`Sources/RuneKernel/TextPatch.swift`，约 800 行）
- **双格式解析**：
  - Rune 原生（`*** File:` / `*** Create:` / `*** Delete:` + `@@ 锚点`）
  - **标准 unified diff**（`--- a/x` / `+++ b/x` / `@@ -10,3 +10,3 @@ fn`），含 `a/`、`b/` 前缀剥离、`/dev/null` 语义、`git diff --git`/`index`/`new file mode` 等元数据行忽略、`\ No newline at end of file` 忽略
  - 相对路径自动视为相对 `/workspace`（模型天然按仓库相对路径思考）
- **四级模糊匹配**：精确 → 忽略行尾空白 → 忽略首尾空白 → 忽略所有空白。**逐级放宽，但每一级都必须唯一**。
- **唯一性强制**：匹配到 0 处 → 给"最接近的位置"；匹配到 ≥2 处 → **拒绝并返回全部候选行号 + 上下文**。绝不猜。
- **原子性**：任一 hunk 失败 → 整份补丁（含其他文件）都不落地。有测试守护。
- **换行保真**：CRLF / LF / 无末行换行三向保真。
- **诊断可执行**：所有错误的 `modelFacingMessage` 都是"给模型看的、可直接据以修正"的说明，并附 `suggestion`。
- **`TextEdit.replaceUnique`**：`edit_file` 的引擎，唯一才替换（**多处匹配直接拒绝，绝不悄悄全改**——这是编码 Agent 最危险的失效模式之一）。

**验证方式**
```
pwsh -NoProfile -File Tools\rune.ps1 test RuneKernel
→ 通过 121 / 失败 0（累计 122 项断言全绿）
```

**过程中发现并修复的 4 个真实 bug**（都值得记录）
1. ⚠️ **Swift 字素簇陷阱**：`"\r\n"` 在 Swift 里是**单个 Character**，导致 `components(separatedBy: "\n")` 在 CRLF 文本上**完全不分割**——整个文件被当成一行，所有按行匹配的补丁会**静默失败**。修复：先归一化 CRLF 再分割。（已加进 `PROJECT_STATE.md` §8.2 T8）
2. `@@ 锚点`（Rune 原生，只有一对 `@@`）被误解析为空锚点——因为取锚点的函数只考虑了 unified diff 的两对 `@@`。修复：无第二对 `@@` 时取第一对之后的内容。
3. Create 块会保留与下一个指令之间的分隔空行 → 新文件多出空行。修复：flush 时裁掉尾部空行（并写明取舍）。
4. 替换文本的换行风格不跟随目标文件 → 在 CRLF 文件里插进 LF 行，diff 变整文件噪音。修复：`normalizeNewlines(_:to:)`。

另有 2 处是**测试自身写错**（`/workspace/tmp/...` 被解析成 workspace 下的 tmp 目录；`+ 标题` 在 unified diff 语义下确实要保留前导空格）→ 改成按**正确语义**断言，并把格式约定写进解析器的文档注释。

## 2026-09-17 · ✅ M1-1 完成：ToolScheduler 工具调度器（C10）

**为什么做它**：一轮里模型可能一次给出多个工具调用。全串行 → 慢且浪费（只读操作本该并行）；全并行 → **会出事**。
调度的核心不是"并发度"，而是**冲突判定**。

**做了什么**（`ToolScheduler.swift`，约 300 行）
- **分波（wave）**：波内并行、波间串行；`exclusive` 操作单独成波
- **路径冲突检测**：路径相等、或一个是另一个的祖先目录 → 冲突。
  ⚠️ 必须提取**全部**路径——`apply_patch` 一次可能改多个文件，只取第一个就漏检。
- ⚠️ **执行类工具与任何写操作冲突**（最容易漏的一条）：边跑 `run_tests` 边 `apply_patch`，
  测试会读到半成品，产出**假失败**——而假失败会让模型去"修"一个根本不存在的 bug。
- **审批项批量摘出**：手机上一次弹一个审批是灾难；且审批项不阻塞只读操作。
- **预算延后**而非静默丢弃；**不重排**模型给出的顺序（模型有时依赖"先建目录再写文件"）。
- 并发度按设备核数推导但**封顶 6**（手机上并行意味着同时吃内存与 CPU）。

## 2026-09-17 · ✅ M1-3 完成：波次调度接入 TurnRunner（C12）

**先想清楚再写代码**：PROJECT_STATE 里留了一个待决问题 ——
「并行执行时，同一波里多个写操作如何取检查点？」。答案是：

> **以波次为单位，在整波结束后打一个检查点。**

理由：波内多个调用是**同时在飞**的，为每个调用各打一个会产出"不对应任何真实状态"的检查点
（时间戳几乎相同，但那些中间状态从未存在过）。这条已回写进 `docs/10 §12.4`。

**做了什么**
- **波次边界语义**：调度器（M1-1）负责分波，运行器负责"波内逐个写意图（每个都是独立的崩溃窗口）、
  波后统一收尾"。事件里带 `wave` / `waveSize`，供 UI 显示"第 2 批 · 3 个并行中"。
- **⚠️ 多路径授权**：`pathsOfCall` 从"返回第一个路径"改成"返回**全部**路径"，
  策略引擎对每一个路径判定并**取最严格的结果**。
  只查第一个是**真实的安全缺口**：多文件补丁里第二个文件越权就会被放行。
- **⚠️ 多悬空意图恢复**：一次崩溃可能留下**整批**"意图已落盘、结果未知"的调用。
  按幂等性分流：只要有一个不可重做 → **整批问用户**（不能先把能做的做了，那会改变工作区、
  让用户无法判断那个不可逆操作到底发生了什么）；全部可重做 → 自动重做全部。

**验证方式**
```
pwsh -NoProfile -File Tools\rune.ps1 test RuneKernel
→ 通过 341 / 失败 0（新增 13 项波次测试）
```
关键断言：3 个只读调用合成 1 波（`parallel: true`）；"跑测试 + 改文件"拆成 2 波；
**一波 3 个写调用只产生 1 个检查点**（不是 3 个）；只读波不产生检查点；
多文件补丁第二个文件越权 → 整次调用被拒且一个文件都没改；崩在第 2 个调用上时两个调用都写了事实；
**多调用轮次下遍历每一个切断点，恢复后最终状态仍与基线一致**。

**过程中修掉的 1 个真 bug（顺序问题）**
波次检查点的代码被放在 `.dispatching` 的「队列空就回模型」**早返回之后** →
最后一波完成时直接跳过了检查点。**收尾逻辑不能被早返回挡住** —— 已把波次管理提到最前，
并在代码里留了注释记录这个坑。

## 2026-09-18 · ✅ M1-6：修正性重试 + 对话历史协议不变式（C16/C17）

**一句话**：这一轮修掉了三个「设计文档里写得很漂亮、线根本没接上」的洞，其中两个是**真机上必崩**级别的。

### 洞一：`suggestion` 与 `candidates` 从来没到过模型（C16.1）

三家协议编码器都只发 `ToolResult.summary`（`ProtocolEncoders` 里三处），
而 `ToolResult.failure` 原先把 `summary` 填成 `error.modelFacingMessage` ——
**不含 `suggestion`，也不含 `candidates`**。

后果：`docs/04 §4.4` 承诺的「修正性重试」是**空转的**。模型永远只看到「参数不合 schema」，
看不到错在哪个字段、看不到我们辛苦算出来的最接近工具名、看不到相似路径候选。
它只能再猜一次 —— 于是"长任务成功率从看模型运气变成看工程质量"这句话根本没兑现。

修法：新增 `ToolError.modelFacingText`（`message` + `👉 建议` + `候选：…`），由 `ToolResult.failure` 使用。
教训写进 §8.2 **T17**：*给错误类型加字段时，先问"它到底会不会被发出去"*。

### 洞二：漏一个工具结果 → 会话后续**全部 400**（C17）

三家协议都要求 assistant 消息里的**每一个**工具调用都有配对结果。
而 Turn 循环有**十几条早返回路径**会留下孤儿：预算熔断、审批等待、用户插话、中断、修正熔断……
在手机上这不是边缘情况，是**主路径**（切后台 = 常态）。
报错信息还是 "roles must alternate" / "tool_call_id not found" 这种与真实原因隔着十万八千里的东西。

修法：`reapOrphanCalls`，**只在 `.reasoning` 入口做一次**。
`.reasoning` 是唯一会调用模型的地方，所以"在它之前修好"就等价于"不可能发出不合法的请求" ——
不变式由构造保证，而不是靠十几个分支各自记得处理。

⚠️ **第一版写错了**，而且错得很有教育意义：我按 `pendingIntents` / `currentWave` 这些队列字段判断孤儿。
测试直接把它打回来了 —— **"预算熔断后用户点继续"这条路径进来的新 Turn 只带着 `messages` 历史，队列是空的**，
于是两个孤儿的 tool_call 永远等不到结果。**判定依据必须是对话历史，因为历史才是"要发给模型的东西"。**

顺带修了两个同源问题：
- 补记的结果必须**插在那条助手消息的正后面**，不能统一追加到历史末尾（配对要求"相邻"）。
- `TurnState.canAdvance` 原先手写枚举减出来，**漏了 `.interrupted`** → `run()` 会对已中断的 Turn
  **空转 10000 次**。现在直接定义为 `!status.isStable`，新增状态只需回答"它稳不稳"。（T21）

### 洞三：`steerNotes` 从来没送进请求（C17.6）

`steerNotes`（用户中途转向）一直被持久化、界面也显示，**但从没有任何代码把它放进请求**。
用户说"顺便也改一下文档"，模型完全不知道。现在在 `.reasoning` 以 `.runtimeGuidance` 注入并清空。

### 新增的信任级：`.runtimeGuidance`（C16.8）

运行时往上下文里写话，**必须**与 `.userInstruction` 分开 —— 理由不是洁癖，是**权限**：
如果标成用户指令，`canDriveDangerousAction` 就会放行，运行时于是能**伪造用户授权**去推送/外发/删除。
那是提权，不是便利。现在它 `isInstruction == false`、`canDriveDangerousAction == false`。

### 修正性重试策略层（`Correction.swift`）

- 按**根因**（`错误种类:工具名`）分桶，不按具体参数 —— 模型路径写错时会每次试一个不同的错路径，
  按路径分桶则熔断永不触发。
- ⚠️ **逐字重复立刻止损**：参数一字未改又发一遍（按规范化 JSON 比对，键序无关），不等计数用完。
- ⚠️「模型改不了」的错误（越权/沙箱/网络/输出过大）**不记账** —— 否则正常的拒绝会被算成模型无能。
  **但逐字重复仍然上报**：明知会被拒还原样重发，说明它没在听。
- 乱试检测：连续 5 次失败且**每次根因都不同**（通常是"整个目录找错了"这类判断错误）。
- 第 2 次失败额外注明「这是最后一次机会」——挂在工具结果**正文**里（另加消息是协议违规）。
- 上报不是报错框，而是**三选一 + 一条出口**：定向提示 / 换个完全不同的做法 / 用户自己补参数 / 就在这里停下。
  用户选"继续"则给该根因**重新开一份额度**（沿用旧计数会立刻再熔断，等于用户的选择无效）。
- 用户的选择走**状态机**（`TurnRunner.resolve`）落成 `CorrectionResolved` / `GuidanceInjected` 事件 ——
  往上下文里加话必须有据可查。

## 2026-09-18 · ✅ M1-7：上下文预算制装配器 + L1 结构化裁剪（C18）

**为什么先做这个**：手机上跑 Agent，**上下文是最贵的资源** —— 它同时消耗钱（按 token 付费）、内存、延迟和电量。
它也是"体验能否超过桌面 Agent"的真正分水岭：桌面 Agent 敢把 200k 窗口用满，手机上那样做就是烧钱 + 卡顿 + 被系统杀掉。
`docs/07 §1` 早就写好了预算制装配管线，但一直只是文档。这一轮把它变成了有测试的代码。

### 一个会让中文用户多花 4 倍钱的陷阱（T22）

教科书上的经验值是"1 token ≈ 4 个英文字符"。**但这个系数对中文是灾难性的低估**：
CJK 不在 BPE 的合并收益区里，中文约 **1 字符 ≈ 1 token**。

用 `count / 4` 去估一段中文，会把 4000 token 的内容估成 1000 ——
装配器以为还很空、继续往里塞，直到真的撑爆窗口（请求 400）或账单比预期高 4 倍。
而 app 的主要用户群就是说中文的人。

`TokenEstimator` 现在按字符类别分开算：CJK（含假名/谚文/全角）按 1 字符 1 token，
其余按 **3.5 字符/token**（代码与 JSON 里标点缩进密集，实际接近 3），空白打 0.4 折。
**宁可略高估**：高估的代价是提前压缩，低估的代价是请求失败。

### 装配器**永不自己花钱**（T23）

L2（端侧摘要）走**注入的闭包** —— 零成本，而且在 Windows 上根本不存在端侧模型，本来就该注入。
L3（主模型全量压缩）装配器只**报告 `needsMainModelCompaction` + 候选 id**，不执行。

> 让一个叫"装配"的函数悄悄调模型花钱，是成本失控最典型的来源：
> 调用方以为自己只是在拼上下文，账单却翻了倍。
> **钱的决策必须留在能落事件、能弹卡片的那一层。**

有一个测试专门守这条：端侧摘要够用时不报 L3；端侧压不动时如实上报 L3 候选，而不是自己动手。

### 缺「当前目标」就不许把上下文发出去

`docs/07 §1.2` 第 6 步的硬性断言，现在落成了**六项自检**：

| 自检项 | 何时要求 | 不满足 |
|---|---|---|
| 含当前目标 | **无条件** | 不许发出 |
| 含未完成 todo | 素材池里有就必须进 | 不许发出 |
| 含最近一次失败 | 素材池里有就必须进 | 不许发出 |
| 含不可信内容边界标记 | 素材池里有就必须进 | 不许发出 |
| 输出预留 ≥10% | 无条件 | 继续压缩 |
| 总占用 ≤ 窗口 − 预留 | 无条件 | 降级重试（最多 3 轮，每轮缩到 75%） |

⚠️ 一个容易搞错的地方：自检失败**分两种**。额度不够可以靠降级解决；
**必进项本身就撑爆窗口**是解决不了的 —— 那种情况必须一直失败下去，
由 `passed == false` 告诉调用方"这份上下文不能发"。测试里专门验证了这条，
以及"必进项绝不能为了腾地方被丢掉"。

### 字节稳定 = 缓存命中 = 输入成本降到 0.1×

层 1+2 在两次装配之间必须**逐字节一致**，否则 Prompt Cache 永远命中不了。
两条具体做法：区块渲染顺序固定（`系统层1 → 系统层2 → 工作区 → 转向/引用 → 记忆 → 历史 → 工具结果`），
块内排序**确定性**（新鲜度降序 → id 升序兜底，不依赖字典遍历顺序）。
两个测试守着它：同一批素材装配两次字节全等；只追加工具结果时系统层的字节前缀不变。

### L1 结构化裁剪

`docs/07 §5.1` 说"工具结果只保留：结论 + 关键行 + 制品句柄"。现在实现了：

## 2026-09-18 · ✅ M1-8：工具注册表（86 个工具契约）+ **修掉一个静默的授权失效**（C19）

### 先说最重要的：相对路径的授权判定一直是**被跳过的**

做这一轮时顺手写了一条测试"写 `src` 之外的相对路径必须被拒" —— **它挂了**。

追下去发现：`CallPaths` 用 `VFSPath.parseOrNil` 解析模型给的路径，而 `VFSPath.parse`
**要求绝对路径且带挂载点**（`/workspace/src/a.py`）。可模型绝大多数时候写的是**相对路径**（`src/a.py`）。
于是路径一律解析失败 → 返回**空数组** → 策略引擎看到 `path == nil` →
按它自己的逻辑那是"**这个工具不涉及任何路径**"→ **作用域判定被整条跳过**。

后果链条（全是静默的）：

| 模块 | 原本会发生什么 |
|---|---|
| 策略引擎 | 越出授权范围的写入被**放行** —— 授权形同虚设 |
| 审批代理 | "记住选择"拿不到路径 → 退化成**整个工具在工作区里的白名单**（C14.5 修过的坑，在这里又漏了回来） |
| 调度器 | 路径冲突检测失效 |
| 工具实现 | 各写各的路径解析 → "被检查的路径"和"实际操作的路径"可能不是同一个 |

**修法**：`CallPaths` 成为唯一实现，相对路径按**工作区根**解析（`VFSPath.resolve`，
`..` 钳制在挂载点内）；`ToolExtractor` 的返回类型从 `[VFSPath]` 变成 `PathExtraction`，
多带一个 `outsideMounts` 字段。

### 第二个静默失效：「绝对但挂载点不认识」的路径

`/etc/passwd` 这种路径按相对路径处理会被悄悄映射成 `/workspace/etc/passwd` ——
**被检查的路径和工具实际操作的路径不是同一个**，这是典型的混淆代理漏洞。

它也不能被当成"解析失败、返回空"（那又回到上面那个洞）。正确做法是第三种：
显式标成 `outsideMounts`，由运行时**直接拒绝**，并给出可执行建议
（"改成相对路径，或先用 `set_workspace` 申请"）。

### 工具注册表：86 个工具，15 条校验规则

`ToolRegistry.swift` 是**整个工具系统的唯一契约**：风险级、幂等性、并发属性、路径参数名、
所需能力、审批策略、输出形态，全在这里声明。策略引擎、调度器、审批代理、上下文装配都从它读事实。
它同时是 macOS 阶段的实现清单 —— 每个 `ToolSpec` 对应一个待实现的 handler。

**为什么把"声明"单独做成模块并配一套校验**：
一处写错（把写文件标成 `parallelSafe`、漏声明一个路径参数）**不会报错，只会静默地少一层保护**。
所以 15 条规则把这类错误变成**测试失败**：

`duplicateName` / `humanOnlyDeclared` / `dangerousWithoutApproval` / `irreversibleWithoutAlways` /
`writerNotSerial` / `deleteNotDangerous` / `writerWithoutPathParameters` / `undeclaredPathParameter` /
`descriptionIncomplete` / `asciiQuoteInProse` / `schemaRequiredNotInProperties` / `inlineTooLarge` /
`safeButWrites` / `biometricNotIrreversible` / `nonIdempotentButSafe` / `missingExample` / `execOutputInline`

而且**校验器本身也被测**：用 14 条合成错误 spec 逐条验证"它真的会报"。
一个永远返回空的校验器比没有更糟。

规则一上线就又抓到三个真问题：
- `start_job`（执行类）输出内联 → 一次 `pytest` 能吃掉整个上下文
- `git_add` / `git_commit` / `git_checkout` 声明了 `["path"]`，但 schema 里还有 `files: [string]` →
  那些路径**完全不会被提取**。「声明了但不全」比完全没声明更危险，因为它看上去是对的（新增 T26 规则守住）
- `run_build` 的参数叫 `target` —— 而 `target` 在路径键名启发式里，会被当成路径解析。
  它其实是**构建目标名**，改名为 `build_target` 消除歧义（T27）

### 按信任档裁剪工具表（安全 + 省 token 双收益）

86 个工具的 schema 是几千 token —— 在手机上那是真金白银。
`visible(trustDial:granted:)` 按档裁剪：只读档不给任何写/执行/出口工具；协作档不给出口与不可逆；
但真正取决于"已授予的能力"（信任档 ≠ 授权）。

⚠️ 一个刻意的取舍：**"能看到工具"不等于"能随便用"**。
`run_shell` 在协作档里是可见的（这个档的定义就是"能改工作区、能执行"），
但它是 `.dangerous` → 每次调用仍会弹确认。可见性管的是**省 token 与表达能力**，
真正的闸门在策略引擎的审批分级上。

端侧反射子集固定在 5 个（`read_file` / `grep_search` / `list_dir` / `ask_user` / `todo_write`）——
端侧窗口只有 4096 token，工具 schema 给多了它反而一个都用不对。

### 一个反直觉但重要的结论：审批的真正防线是「作用域」，不是「弹窗」

测试一开始断言"所有写工作区的工具都必须至少 perProject 确认"，然后挂了 8 个。
想清楚之后改了测试，而不是改注册表：

**在手机上每次写文件都弹窗会让 Agent 不可用** —— 一次重构改二十个文件，
二十次弹窗换来的不是安全，而是用户习惯性地点"允许"。

分工应该是：

| 层 | 负责 | 机制 |
|---|---|---|
| 空间 | **能改哪里** | 能力令牌的作用域（`/workspace/src` 之外一律拒绝） |
| 批量 | **这一批改动同不同意** | 计划批准 = 一次性授权（`planApproved → 无需逐次确认`） |
| 时间 | **哪些动作不能"记住"** | 危险/不可逆操作每次确认 |
| 审计 | **事后能查** | 事件日志哈希链 + 出口记录 |

所以 `write_file` / `edit_file` 标 `.never` 是**故意的** ——
而这个设计**完全依赖路径能被准确提取出来**，这正是本轮开头那个洞的可怕之处：
它让整个审批模型的地基失效了，而且不报任何错。

### 顺手修掉的另一个坑（T28）

写工具描述时手打的 ASCII `"` 会**截断 Swift 字符串字面量**，而报错是
「expected ',' separator」这种和真实原因毫不相干的提示；在 `#"…"#` 里写出 `"#` 更会直接终止原始字符串。
这一轮总共撞了 14 次。已加 `asciiQuoteInProse` 校验规则 + 约定：**中文引号一律用 `「」`**。

## 2026-09-18 · ✅ M1-9：技能库 + 端到端场景测试（**场景测试挖出两个致命 bug**）（C20 / C21）

**这一轮的最大产出不是技能库，是端到端场景测试把两个"单元测试永远测不到"的 bug 挖了出来。**

### 先说 bug：① 审批路径是个**死循环**

写场景测试时加了一条「没有计划批准时，修改类工具应当停下来等确认，批准后继续」，它挂了 ——
状态一直卡在 `.dispatching`，永远跑不完。

追下去发现：**`PolicyEngine.approvalRequirement` 是纯函数**。
用户点了「允许」之后，调用被放回波次队头重新派发，而策略引擎**又算出同样的「需要确认」** ——
于是卡片无限弹，直到用户放弃。

**这意味着：任何需要审批的工具都永远执行不了。** 推送、删除、外发、开 PR、Shortcuts……全部瘫痪。
而单元测试从没组合出「批准之后会发生什么」，所以一路绿灯。

修法：`TurnState.approvedFingerprints` 记住「这一次已批准」。
⚠️ 指纹 = **callID + 工具名 + 规范化参数**，而不是只记 callID ——
callID 来自厂商，理论上可以被复用；只按 id 记的话，一个复用了旧 id、参数完全不同的调用会被
**自动放行**，那是提权。而且只跳过「审批」这一层：越出挂载点的检查**必须先执行**，
否则"曾经批准过一次"会变成永久的越权通行证。

### ② 状态机缺防御分支 = **崩溃**

另一个切断点暴露的：恢复一个「非幂等调用结果未知」的 Turn 时，恢复分支把状态置成 `.awaitingApproval`，
但那个调用在 `pendingIntents` 里、**不在** `currentWave` 里。
用户点「重新执行」之后（`approve` → `.dispatching`），波次管理的条件
`currentWave.isEmpty && pendingIntents.isEmpty` 不成立 → 整块被跳过 →
直接执行 `currentWave.removeFirst()` → **空数组越界，App 崩**。

修法两层：`approve` 按**相位**路由（权限审批 → `.dispatching`；结果未知确认 → `.executing`），
以及 `.dispatching` 加一条防御分支 —— **状态机必须是全函数，任何状态组合都不能崩**。

### 然后是技能库（C20）

`docs/04 §7` 的渐进式披露终于落地：L0 目录（每次装配，~35 token/条）→ L1 正文（`use_skill` 按需）→ L2 示例与夹具。

**一条从 API 设计上就焊死的红线：`SkillRegistry` 不提供"取全部正文"这种方便方法。**
一旦"顺手把正文也带上"，机制就退化成全塞 —— 而它退化之后**不会有任何报错**，
只是账单变贵、关键信息被淹没。

**12 个内置技能**（`ci-triage` / `pr-review` / `flaky-test-triage` / `sql-migration` / `api-client-gen` /
`data-cleaning` / `chart-report` / `i18n-sync` / `dep-upgrade` / `regex-craft` /
`incident-first-responder` / `screenshot-to-code`），每个都带**验证清单** ——
有清单的技能模型才会真的去验证，没有清单的技能它会在改完就宣布完成。

正文刻意**不写具体命令**（`pytest -q` 之类）：项目用的测试框架各不相同，写死会让模型照抄错的。
给的是**判断顺序与检查清单**。

### 一个实测校准：设计文档的 token 预算是英文尺子

`docs/04 §7.2` 写「L0 每条 ~15 token」。实现时按这个卡，**所有中文条目全部超标**。
原因：15 token 是**按英文估的**（英文 1 token ≈ 4 字符），而中文是 **1 字符 ≈ 1 token**，
同样信息量在中文里要 30–40 token。**不是条目写坏了，是尺子错了。**

换算之后的账：40 条 × ~35 token ≈ 1400 token。在 200k 窗口里 0.7%，32k 里 4.4%，都不成问题；
**但在端侧那 4096 token 的窗口里是 34%** —— 所以端侧反射模式不带技能目录。
已把实测值与推理回写进 `docs/04 §7.2`，上限设为 45。

顺带修掉一个预算实现 bug：**token 预算必须把标题行与提示行一起算进去**，否则它就不是硬预算 ——
只累加条目成本时，「预算 300」实际产出 306。

### 技能不能给自己提权（`docs/04 §7.4`）

* 技能永远不能申请人类专属区 —— 声明即拒绝注册；
* 权限必须在**加载正文之前**就位。不能「先加载、遇到越权再拒绝」：
  正文本身就会引导模型去申请那些权限，那已经是一次提权尝试了；
* 覆盖判定按**作用域包含**（授了 `/workspace/src` 覆盖 `/workspace/src/utils`），
  域名按**点边界后缀**（`example.com` 覆盖 `api.example.com`，但不覆盖 `evil-example.com`）。

### 端到端场景测试（C21）跑了什么

一个真实形状的任务：**定位 → 读 → 打补丁 → 跑测试 → 提交**。断言包括：

- 工具按顺序真的被用了、文件真的改了、**别的文件没被碰**
- ⭐ **协议不变式**：每个 tool_call 都有且仅有一个配对结果
- ⭐ **事件哈希链逐条可校验**，且首尾相接
- ⭐ **每一轮装配的上下文都通过自检**（缺目标/缺最近失败都会被抓到）
- ⭐ **系统层字节在整轮里完全稳定**（Prompt Cache 能命中的前提）
- ⭐ 测试失败后模型自己改好 → 记一次「自行修正」，且**补丁只实际改了一次**（幂等检查生效）
- ⚠️ 写到授权范围外 → 被拒，但**整个任务仍然继续**（模型会绕路）
- ⚠️ 补丁一直不合法 → 停下来问用户（只跑 3 次，而不是烧完 24 次预算），且**此时协议不变式仍成立**
- ⚠️【崩溃一致性】**在 0..23 每一个切断点**被杀后恢复，工作区最终状态与基线完全一致、协议不变式成立、仍跑到完成
- ⚠️ 审批作用域精确到**那一次调用**：同一 callID 换个参数必须重新确认

## 2026-09-18 · ✅ M1-10：Workflow 引擎（批处理编排）（C22）

**定位**：`docs/04 §8` —— Skill 解决「怎么做一件事」，**Workflow 解决「一次性跑一大片互相独立的事」**。
典型场景：发版前检查（17 项）、全仓库文档补全、批量重构。

### 核心决策：引擎**不执行任何东西**

与 `TurnRunner` 同一套哲学：引擎只回答「下一步该跑哪些」与「结果回来了怎么记」，
真正的执行（起子代理、并发、调模型）留给运行时。换来三件事：

1. **完全确定性** —— 同样的输入必然产出同样的决策，可以逐步骤断言，不用等并发；
2. **天然可恢复** —— 每个步骤的状态都在 `WorkflowRun` 里，被系统杀掉接着跑就行；
3. **并发策略可替换** —— 手机上限 3，将来放宽到 8 不用改引擎。

如果让引擎自己 spawn 并发任务，这三条会同时失去 —— 而它们恰恰是移动端最需要的三条。

### `pipeline` 的无屏障语义，靠「深度降序」实现

设想 17 个目标、每个要过"检查 → 修复 → 验证"：

* 按**书写顺序**调度 → 先把 17 个检查全跑完再开始修复。那其实是**三级屏障**，
  与 §8.1 写的 pipeline 语义直接矛盾；
* 按**深度降序**调度 → 某个 item 的检查一完成，它的修复步骤就**优先于其他 item 还没开始的检查**，
  流水线真的流动起来。

测试里把这个差别钉死了：只剩 1 个空位时，必须给 `fix-0`（深度 1），
而按书写顺序会给 `check-3` —— 对照组也写在测试里。

### 短路与失败必须严格区分

上游返回 `null` → 本步骤 `skipped`（结果也是 `null`），**并沿链传下去**。
`skipped` 与 `failed` 在三处都要区分：状态、汇总（`null` vs `{error}`）、进度看板（"跳过 3" / "失败 1"）。
用户要看得懂"这是判断不需要做"还是"这是没做成"。

### 一个会让脚本第二阶段**静默消失**的 bug（T32）

脚本的典型形状是 `phase("A"); await agent(x); phase("B"); await agent(y)`。
第一个 agent 完成时，**已知的全部步骤都终结了** → 运行被标成 `completed`；
等脚本走到 B 想加新步骤时，`advance` 开头的 `status == .running` 守卫直接返回 →
新步骤永远停在 `pending` → **整段 B 静默消失**。

而"脚本还在执行"这件事本身就证明运行没有结束 —— 是脚本在加步骤，不是引擎在猜。
修法：`addSteps` 先把运行**重新打开**。

### 一个必须写进设计文档的诚实声明（T33）

脚本静态安全检查会扫 `fetch` / `require` / `eval` / `setTimeout` / `globalThis` / `__proto__`，
但它**不是安全边界**。

> 真正的边界是 **JSC 宿主根本不暴露这些全局**。脚本就算写出 `fetch(...)`，
> 也只是"调用了一个 undefined"。
> 任何号称靠关键字黑名单拦住逃逸的方案都是自欺欺人 —— `this["fet"+"ch"]` 一行就绕过去了。

它的用途是两件事：**可用性**（用户写了注定跑不通的脚本，开跑前就告诉他，
别让他等 17 个子代理起来才发现）与**纵深防御**（导入的工作流明晃晃写着 `fetch("http://…")`，
多半是在偷数据，值得给用户看一眼）。

已把「命中 ≠ 攻击，只是值得提醒；不命中 ≠ 安全」写进 `docs/04 §8.5` ——
否则下一个人会把这条正则当成防线，然后放心地把 `fetch` 暴露出去。

### 其余实现要点

- **并发上限 3**（手机），步骤上限 200，阶段上限 8 —— 都是开跑前就能拦住的硬约束；
- **失败隔离**：17 项里一项失败，其余 16 项照跑完，终态是 `completedWithFailures`
  而不是整体失败 —— 这是"批量任务"与"单任务"最重要的体验差别；
- **上游失败 → 下游标 `failed` 而不是 `skipped`**（"从没做过" ≠ "判断不需要做"）；
- **瞬时失败重试**（可配，默认 2 次），真失败不重试；失败的那次**照样记账**（钱花了就是花了）；
- **schema 不符必须判失败**，不能"凑合用"：下游会按 schema 访问字段，
  塞一个形状不对的对象进去会在无关的地方炸，那时离真正原因已经很远；
- ⚠️ 整数校验要接受「数值上等于整数的小数」（JSON 里 `1.0` 与 `1` 是同一个数），
  否则子代理返回 `1.0` 会被无理由判失败；
- **成本上界必须先算**（`agent 数 × 平均 token × 单价 × 1.5`）：Workflow 最典型的形态是
  "一次起 17 个子代理"，而用户对"17 个子代理要花多少钱"完全没有直觉 ——
  没有开跑前的上界，用户第一次用就会被账单吓到，而那是**一次性的信任损失**；
- **环检测**：有环的话运行会**静默卡死**（`nextBatch` 永远返回空），
  是最难查的一类问题，必须在开跑前拦住，且报错要写出环上的步骤。

### 组合证明：每个步骤就是一次真实的 Agent Turn

新加的两条测试把 Workflow 与 TurnRunner 拼起来跑：6 个目标 × 每目标一轮真实 Turn
（走 `ToolRegistry` + `PolicyEngine` + `ToolScheduler`）。

- ⭐ 6 项全部完成，且**每项都拿到了自己那个文件的内容**（不是都拿到同一个结果）；
- ⚠️ 其中一项的目标文件不存在 → 5/6 成功，用户**拿到 5 份成果**，
  汇总里 5 份在、1 份是错误 —— 这就是"不因为一个失败丢掉全部成果"的实证。

顺手钉了一条纪律：子任务必须**自己证明它做完了**（拿到工具结果才算成功）。
只看"Turn 没报错"是不够的 —— **一个什么都没做的 Turn 也是 `completed`**。

## 2026-09-18 · ✅ M1-11：VFS 层（真实文件系统 + 内存，同一套一致性断言）（C23）

**为什么现在做这个**：前面 705 项测试里，**没有一行代码碰过真实文件**。
工具契约、策略引擎、调度器都建立在一个还不存在的文件系统语义上 ——
而"手机上跑 Agent"的绝大部分真实动作就是读文件、改文件、跑命令改文件。

`docs/05 §4` 把 VFS 的语义写得很清楚，但一直只是文档。这一轮把它落成了代码。

### 关键设计：一份契约，两份实现，**同一套断言**

`VFS` 是协议；内存实现用于测试与"只改副本"的沙箱场景，真实实现跑 `FileManager`。
**两套 suite 调用同一批 `assertXxx` 函数**。

这个做法立刻见效 —— 一上来就抓到四处不一致：

| 不一致 | 后果 |
|---|---|
| **二进制检测只在真实实现里有** | 内存实现会把 20MB 的 PNG 当文本读出来，白烧上下文 |
| **候选路径提示只在真实实现里有** | 内存实现下模型拿不到"你是不是想用 src/money.py"，修正性重试失效 |
| **回收站语义两边不同** | 一边把内容搬到 `.rune/trash/`（可列可恢复），另一边塞进一个旁路字典（列不出来） |
| **末尾换行只在一处保住**（见下） | 每次读→写往返都在改文件 |

只在内存实现上验证，真实实现里的走样永远不会被发现；只在真实文件系统上验证，
"越界/逃逸"这类用例很难构造。**两边都过才叫契约成立。**

### 真实 bug：读出来写不回去（差一个字节）

切片的实现是 `lines[lower..<upper].joined(separator: "\n")` ——
它**丢掉了 `endsWithNewline`**。于是"读出来再写回去"与原文差一个字节。

后果不是"小瑕疵"：每一次往返都在改文件（spurious diff），
而前一轮刚加的"补丁只实际改动一次"这类崩溃一致性断言会以**极难排查**的方式失败。

修法：只有切片真的取到文件最后一行时才补回换行，中间段落不该凭空多一个。
配套约定：**读出去的内容统一成 LF**（行尾 `\r` 会让行号与匹配产生噪音），
原始风格记在 `VFSContent.newline`，写回时靠 `.preserve` 还原。

### ⚠️ 我一开始的判断是错的：iOS 的文件名坑不是 NFC/NFD

我按惯例写了"APFS 存 NFD、模型给 NFC、字节不同就找不到文件"，并写了断言。
**`#expect(nfc != nfd)` 直接挂了。**

顺着查下去，两件事同时成立：

* **Swift 的 `String ==` 本身就是按 Unicode 规范等价比较的** ——
  `"café" == "cafe\u{0301}"` 在 Swift 里是 `true`。所以我们自己的比较天生没这个问题；
* **APFS / HFS+ 也是规范化不敏感的**，操作系统已经替我们兜住了。

**也就是说那个"坑"在 Swift + APFS 上基本不存在。** 我把判断改对了，并把纠正过程写进 `docs/05 §4.4` ——
留着这段比删掉它有价值：下一个人很容易重复同一个错误推理。

**真正会咬人的是大小写不敏感**：APFS 默认大小写不敏感，`README.md` 与 `readme.md`
在 iOS 上是**同一个文件**，而在 Windows/Linux 上是两个。后果很具体：
**模型"新建" `README.md` 时实际是覆盖掉已有的 `readme.md`**，而且不可撤销。
这类 bug 在 Windows 上开发时**永远看不到**。

所以它被做成一个**显式的、可注入的**属性 `FilenameComparison`，
并提供 `collidingEntry(named:among:)`：**写文件之前先问一句"这个目录里是不是已经有一个只有大小写不同的同名文件"**。

### ⚠️ 同一个性质，换个地方就是陷阱（一次踩了两处）

`lookupForms` 要返回**字节不同**的几种候选形式。第一版写的是：

```swift
if !forms.contains(decomposed) { forms.append(decomposed) }   // ✗ 永远为 false
```

`contains` 用规范等价比较，所以对 NFC 形式**永远为真** → 分解形式永远加不进来 →
**这段"多试几种形式"的兜底从来没生效过**。而代码看上去完全正确，
测试也只断言了 `forms.first` —— 一路绿灯。

同一个坑紧接着又在第二处出现：`for form in forms where form != name` ——
同样因为规范等价，`form != name` 永远 `false`，备选形式一个都不会被试。

> **结论（已写进 docs/05 §4.4 的检查清单）：凡是"我要的是不同字节形式"的地方，
> 都必须按 `Array(s.utf8)` 比，不能用 `==` / `contains` / `!=`。**
> 同一个性质在"判断两个名字是不是同一个文件"时是帮手，在"判断两个字节形式是不是同一个候选"时是陷阱。

### 其余落地内容

- **沙箱边界**：路径先过 `VFSPath`（拒 `..`），拼接后**再解析一次符号链接**确认仍在根内 ——
  工作区里一个指向 `/etc` 的链接就能架空整个沙箱。符号链接**永远不跟随**，只作为 `.symlink` 报告。
- **原子写**：先写同目录临时文件再改名（跨文件系统的 rename 不是原子的）。
  ⚠️ corelibs-foundation 上没有可靠的同目录原子替换，本机退化成"删掉再改名"，
  窗口极小但不为零 —— 这是本机验证的局限，iOS 上走 `replaceItemAt`。
- **删除默认进回收站**，不是真删（手机上没有"撤销"，而不可逆正是最该避免的）。
- **二进制识别**（前 8KB 出现 NUL）并给出正确替代做法（`ocr_image` / `read_pdf`）。
- **末尾换行/CRLF 保真**，行号对应文件里的**真实行号**（模型要拿它打补丁）。
- **快照**：这一版是整树复制（`clonefile` 写时复制是 Apple 专有，等 macOS），
  但把 `fileCount` 返回给调用方，让 UI 能说清影响面。
- 与上层接上了：**补丁引擎直接跑在 VFS 上**，且 `CallPaths` 提取出来的路径能在 VFS 上直接解析 ——
  **"策略引擎判定的路径"与"VFS 实际操作的路径"是同一条**（不能是两条）。
