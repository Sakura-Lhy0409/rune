# 14 · 工程路线图与测试策略

> **摘要**：Rune 的最大工程风险不是"模型不够聪明"，而是**前 6 周做不出一个可信的沙箱**、**第 3 个月才发现后台续跑根本接不上**、**上架前被 2.5.2 拦下**。因此路线图的设计原则是：**把三个致命未知（沙箱可行性、后台续跑、审核合规）全部前置到 M1 之前做 Spike 验证**，验证失败就调整产品形态，而不是写完全部代码再发现。

**一条必须在排期里就认下的成本**：内嵌原生 CPython 会让 **App 体积达到 1-2GB**（实测：Pyto 930MB、Pythonista 853MB、a-Shell 1950MB），且因 2.5.2 **不能改成"首次启动下载"**。这不是可优化项，而是**产品决策项**（[15 Q19](15-风险登记册与开放问题.md)）。排期上要预留：On-Demand Resources 的资产拆分、商店页与首启的体积说明、蜂窝下载引导。

## 2. M-1：五个致命未知（不做完不许进入 M0）

> **原则**：把"可能推翻整个产品设计"的未知全部前置。**每一个 Spike 的失败预案都已经写好**——失败就改产品形态，而不是写完十万行代码才发现路走不通。

### Spike 1 · 执行环境可行性（最高风险）

**问题**：能不能在 iOS App 里真的跑起用户的 Python 与脚本，并且性能与稳定性可接受？

> ⚠️ **本 Spike 的方案已按核实结果修正**：初版打算"把 Python 编译成 WASM 跑"，核实后是**死路**（CPython 的 WASI 构建为实验状态、约 150MB、**不支持线程/子进程/socket**）。正确路线是**原生 CPython XCFramework + 自研 no-fork 垫片**（Pyto / a-Shell / Pythonista 同款，均在架）。

| 验证项 | 通过标准 | 失败怎么办 |
|---|---|---|
| **原生 CPython 集成**：3.13/3.14 XCFramework 静态链入并在真机跑起 | `print(sum(range(1000)))` 正常输出；导入标准库正常 | 退回内置工具链 + JS，把 Python 降为"高级可选"（并改写产品文案） |
| **no-fork 垫片**：`subprocess` / `os.system` / `os.fork` / `os.exec*` 全部拦截并分发到原生命令表 | 拦截率 100%；**任何路径都不能产生真实子进程** | 无法拦截的调用一律抛错并给出替代建议；若拦截不完整则**禁止执行模型生成的脚本** |
| 启动开销 | 首次 import ≤ 300ms；后续脚本启动 ≤ 80ms | 常驻解释器实例 + 预热 |
| 数据处理性能（10 万行 CSV 分组聚合） | ≤ 8s（用随包预编译的科学计算包） | 用原生 Swift 数据工具替代（`read_table` + 原生聚合），Python 只做编排 |
| **稳定性** | 连续 200 次执行无崩溃、无内存泄漏、无句柄泄漏 | 每次执行用新解释器实例（牺牲速度换稳定） |
| 文件 IO 走 VFS 注入 | `open()` 能读写挂载目录且**可回滚**；`$HOME` 等环境变量已按 a-Shell 模式重映射 | 改为"执行前把所需文件复制进内存 FS，执行后写回"（牺牲大文件支持） |
| **WasKit 沙箱可用性**（环境 ②） | 能加载并执行 `.wasm`；限额与强杀生效；SIMD/线程基本可用 | 降级为 wasm3；仍不行 → 放弃"执行用户 wasm"，模型生成的脚本改走 CPython + 强制审批 |
| **内存天花板实测** | 在 6GB 设备上用 `os_proc_available_memory()` 实测可用上限并记录 | 按实测调整模型尺寸承诺（参考值：6GB 设备约 3.1GB，加 entitlement 约 4.2GB） |

### Spike 2 · 后台续跑

**问题**：Turn 被打断后，恢复逻辑真的能接上吗？（**这是"手机 Agent"的立身之本**）

| 验证项 | 通过标准 |
|---|---|
| **`BGContinuedProcessingTask` 真实行为** | 前台发起后能在后台持续数分钟；进度上报生效；用户取消时能优雅收尾落检查点 |
| 前台跑 Turn → 按 Home → 系统挂起 | 状态完好；回前台从检查点继续，**不重复执行已完成的写操作** |
| 从多任务界面强制退出（静默取消、无回调） | 重开后正确恢复；无半成品残留 |
| 静默推送唤醒 | 30 秒内能推进 1 步；超出配额时静默失败不崩溃 |
| **幂等重放** | **100 次随机中断-恢复测试中，文件最终状态与"不中断执行"完全一致（0 差异）** |
| 锁屏导致 SSE 断开 | 回前台后正确"按重发历史恢复"，且**不重复计费** |
| `BGProcessingTask` 在真机被调度 | 充电 + 空闲条件下 24 小时内至少被调度 1 次 |

> **Spike 2 的失败模式最隐蔽**：能跑通一次不代表可靠。必须做**随机中断注入测试**（在随机时刻杀掉进程，100 次），并把它固化进 CI。

### Spike 3 · 合规预沟通

| 动作 | 产出 |
|---|---|
| 逐条比对 Guideline 2.5.2 / **ADPLA §3.3.1(B)** / **1.2（AI 对话 UGC）** / 3.1.1 / 5.1.2(i) | 一份"逐条对应表"（[11 §1.3](11-AppStore合规与分发.md)） |
| 研究 8 个已上架先例（**a-Shell 自带 clang + WASI-libc**、Pyto、Pythonista、Working Copy、Scriptable、Geeps BYOK…） | 一份"先例功能矩阵" |
| **提交一个最小可审版本试探** | ⭐ **不要等到 1.0 才知道能不能过审**。M-1 期间就提一个"只含原生工具 + 示例项目"的版本，验证 4.2 与流程，并摸清审核对"随包解释器"的态度 |
| 准备审核说明与演示材料 | 英文 Review Notes（[11 §8.1](11-AppStore合规与分发.md) 模板）+ 90 秒演示视频 + 内置示例项目 |
| 申请 PCC entitlement | 尽早提交（有下载量门槛与资格审批，周期不可控） |

### Spike 4 · Foundation Models 的 4096 可行性

**问题**：4096 token 的窗口 + ≤3-5 工具，到底能承担哪些反射？

| 验证项 | 通过标准 |
|---|---|
| 在 4096 内完成"三选一分类" | 成功 ≥ 95%，且提示 + schema ≤ 1.5k token |
| 在 4096 内完成"结构化提取"（`@Generable`） | 成功 ≥ 90%，schema 精简后可行 |
| **中文场景** | 中文输入按 1 字符/token 估算后仍能放下（**实际只有约 2-3 千字**）→ 若不可行，中文反射提示必须进一步压缩 |
| 超限处理 | 抛 `exceededContextWindowSize` 后能自动换新会话并降级（**不能崩**） |
| 上下文装前检查 | 用 `.contextSize` / `.tokenCount(for:)` 预检，超限直接升级到 PCC/云端 |

### Spike 5 · 文件系统与 VFS 边界

| 验证项 | 通过标准 |
|---|---|
| security-scoped bookmark 持久化与失效处理 | 重启后仍可访问；目录被移动/删除时给出明确提示而非静默失败 |
| **`stopAccessing` 配对纪律** | 长时间运行后**沙箱扩展仍然可用**（不出现"资源泄漏导致所有扩展失效"） |
| **iCloud Drive + git worktree** | 复现已知损坏问题，并在 UI 上实现明确警告与"`.git` 留本地"选项 |
| 外部变更检测 | 用 `NSMetadataQuery` + `NSFilePresenter` + 前台全量比对，能正确发现"用户改了文件" |

### 6.2 黄金会话回放（核心资产）

**做法**：把真实会话的**模型请求/响应**录制成 cassette（脱敏后），测试时用假 Provider 回放；工具真实执行。

```swift
@Test func goldenSession_fixRefundTest() async throws {
    let cassette = try Cassette.load("fix_refund_test_2026_09_12")
    let env = TestEnvironment(fixtureRepo: "shop-api", provider: .cassette(cassette))
    let result = try await env.runtime.submit("退款测试失败，找一下原因", into: env.session)
    XCTAssertEqual(result.state, .completed)
    XCTAssertTrue(env.vfs.read("src/money.py").contains("currency.exponent"))
    XCTAssertTrue(env.lastToolRun("pytest").succeeded)
    XCTAssertEqual(env.injectionWarnings, 0)
}
```

**为什么这是最重要的测试**：Agent 的失败往往不是"崩溃"，而是"看起来完成了但做错了"。黄金会话把"正确性"变成可回归的断言。

**Cassette 的三条纪律**：
1. **必须包含失败案例**：模型给出错误参数的、拒绝执行的、跑偏的会话都要录进来（用来验证修正性重试有效）。
2. **必须包含注入案例**：夹具仓库里植入注入内容的会话（断言"0 次越权"）。
3. **每次线上发现严重 bug**，第一件事是把那个会话录成 cassette。

### 6.3 Provider 一致性测试

同一组 prompt + 工具，对**每个渠道**跑一遍，断言：
- 流式工具调用参数能正确拼装（按 index 合并 delta）
- reasoning/thinking 内容被正确归一化（各家字段不同）
- 缓存命中字段被正确读取并记账
- 错误分类正确（限流 → Transient、鉴权失败 → 配置错误并提示用户）
- 中断后不产生重复计费（幂等键生效）

用**录制 + 回放**避免每次都真调 API；每周跑一次真实调用（成本约 $2）。

### 6.6 性能基准（每次发版必须跑）

| 基准 | 目标 | 超标动作 |
|---|---|---|
| 冷启动到可输入 | ≤ 600ms P90 | 延后非关键初始化 |
| 首次 token 呈现 | ≤ 1.2s | 检查上下文装配耗时 |
| `grep_search` 10 万文件 | ≤ 3s | 优化并行度与预筛 |
| `grep_search` 1 千文件（常见） | ≤ 300ms | — |
| Git status（大仓库） | ≤ 500ms | 检查 libgit2 配置与索引缓存 |
| 上下文装配（含检索） | ≤ 200ms | 检查向量检索延迟 |
| 事件写入吞吐 | ≥ 5k/s | 批量提交调优 |
| 内存峰值（普通 Turn） | ≤ 350MB | 检查制品与流式缓冲 |
| 内存峰值（含端侧 4B 模型） | ≤ 2.2GB | 检查模型量化与 KV cache 上限 |

| 滚动帧率 | 120fps（无掉帧） | 检查列表与高亮 |

### 6.7 电量测试方法（必须有纪律）

用 Instruments Energy Log + 真机，固定脚本跑 30 分钟标准任务集，记录：
- 屏幕亮起 vs 息屏两种条件
- 纯本地工具任务 vs 大量模型调用任务
- 与"仅仅亮屏闲置"做基线对比

**发布门槛**：标准任务集（10 个中等任务）总耗电 ≤ 8%（iPhone 17 Pro，亮度 50%）。

| 核心逻辑单测 | **GitHub Actions Linux runner**（`RuneKernel`/`RuneStore`(GRDB 支持 Linux)/`RuneGateway` 纯逻辑部分）→ 快、便宜 |
| iOS 构建与 UI 测试 | macOS runner 或 Xcode Cloud；真机测试走本地设备农场（3 台：小内存 iPhone、主流 iPhone、iPad） |
| wasm 构建 | 独立仓库 + CI：用 wasi-sdk 构建 Python/Node/busybox 产物，产出 artifact 供 App 打包引用（版本锁定 + 校验和） |
| 模型转换 | MLX/Core ML 转换脚本 + 产物校验（体积、精度抽样） |
| 分发 | 内部：TestFlight（内外部组）；公开：App Store；Full 版：Enterprise 或自签 |
| 密钥与签名 | 证书与描述文件存 CI secret；模型渠道 key 全部用测试专用 key，且 CI 中通过环境变量注入（**绝不进仓库**） |
| 版本节奏 | 每周一个 TestFlight 构建；每两周一次"发布候选"（跑全量套件） |

## 9. 开发工作流约定

| 约定 | 内容 |
|---|---|
| 分支 | `main` 保护；`feat/*`、`fix/*`；每个 PR 至少 1 人 review |
| ADR | 任何架构级决策写一份 ADR（见 [03](03-总体架构.md) §8），落在 `docs/adr/` |
| 事件契约 | 新增/修改 `RuntimeEvent` 字段属于**兼容性敏感变更**，需同步更新回放夹具与迁移 |
| 工具新增 | 必须附带：ToolSpec、单测、黄金用例、能力声明、文档条目 |
| 调试 | 统一用"事件日志导出 + 回放"调试，不靠打日志猜 |
| 禁止 | 在 UI 层写业务逻辑；在工具里直接 `FileManager`/`URLSession`；跳过哈希链写入 |
| 性能回归 | 每个 PR 跑核心基准，退化 > 15% 阻断合并 |
