# 10 · 后台执行与可靠性

> **摘要**：iOS 不会让任何 App 常驻后台。**"Agent 一直在跑"必须被工程手段构造出来。**
> 但 2026 年出现了一个关键的新原语：**`BGContinuedProcessingTask`（iOS 26+）** —— 由用户在前台发起、可在后台继续"数分钟甚至更久"、允许联网与密集 CPU、进度以**系统级 Live Activity** 呈现且用户可随时取消。
> 这几乎就是为"长任务 Agent"设计的。Rune 的可靠性架构因此围绕它重建：**前台发起 → 后台延续 → 检查点边界落盘 → 随时可被杀 → 下次接上**。

> 📌 本文的所有时间预算与 API 行为均来自 Apple 官方文档核实（见 [附录 B](附录B-技术选型核实表.md)）。Apple **没有公布** BGProcessingTask、延续处理任务、jetsam 内存的具体数值 —— 本文凡涉及这些一律标注为"未公布/需实测"。

## 1. iOS 生命周期现实（核实版）

| 机制 | 官方量级 | Rune 如何利用 | 关键限制 |
|---|---|---|---|
| **前台** | 不受限（受温控影响） | 主力工作时间 | 用户切走即结束 |
| **`BGContinuedProcessingTask`**（iOS 26+） | **"数分钟或更久"**（Apple 未公布具体秒数）；可用网络与密集 CPU | ⭐ **长任务的主载体**：用户在前台点"开始"，任务在后台延续；进度以**系统 Live Activity** 展示，**用户可随时取消**；系统内存压力下**优先杀掉进展低的任务** | 必须**前台发起**；GPU 需 `.continued-processing.gpu`；**后台访问 Neural Engine 需 `.continued-processing.inference` 权限**；从多任务界面强制退出**直接取消且无回调** |
| **进入后台的过渡窗口** | 用 `backgroundTimeRemaining` 读取剩余时间；**不调用 `endBackgroundTask` 会被杀** | 完成当前工具调用 + 落检查点 + 更新 Live Activity | 有限且不可知 |
| **`BGAppRefreshTask`** | **最多 30 秒**，超时必须调 `setTaskCompleted`，否则 App 被终止 | 轻量推进（一次读操作、一次检查） | 时间到就结束 |
| **`BGProcessingTask`** | **"可运行数分钟"**（Apple 未公布数字）；仅在设备空闲时；**用户一开始使用设备就被终止** | 重活：索引构建、批量处理、大规模检索 | 需要 Background Modes `processing`；条件不满足不执行 |
| **静默推送**（`content-available:1`, `apns-priority:5`） | **30 秒**运行时间；**每小时不超过 2-3 条**；**不保证送达**，旧推送会被丢弃 | 尝试推进 1 步 | 完全不可依赖 |
| **后台 URLSession** | 传输在**独立系统进程**中执行，**可跨挂起与终止存活** | 大文件下载（模型权重、仓库克隆） | 仅 HTTP/HTTPS；重定向强制跟随；上传只能来自文件；每次恢复/重启后**有速率限制器延迟新任务**（回到前台重置） |
| **Live Activity** | **活跃最多 8 小时**，之后最多再 4 小时（锁屏），**合计 12 小时**；超过 160pt 会被截断 | 状态外显的"常驻感" | 有寿命上限；更新频率受限 |
| **进程回收** | 随时，内存压力下更早 | 事件日志 + 检查点 = 恢复基础 | — |

### 1.1 三个必须接受的硬事实

1. **锁屏 = 挂起。** Apple 没有为长连接提供任何豁免。**SSE / WebSocket 流在锁屏后必然断开**，唯一合规的模式是**回前台重连**（[06 附录 A §4.3](附录A-渠道与模型事实表.md) 的"按重发历史恢复"）。（唯一的"持续监听"后台模式是音频/定位/VoIP，而 Guideline 2.5.4 限定它们只能用于其本来用途 —— **Rune 不使用这类取巧手段**。）
2. **后台不能做"自主推进"的假设。** 静默推送有配额（每小时 2-3 条）、不保证送达；BGProcessingTask 要求设备空闲。**任何"它会在后台自己跑完"的承诺都是欺骗用户。**
3. **前台发起是长任务的唯一正确起点。** 这反而是好事：它把主动权交还用户（"我开始跑这个任务"），也符合 Rune 的信任模型。

### 1.2 一张决定架构的对照表

| 任务时长 | 载体 | 用户感知 |
|---|---|---|
| < 30 秒 | 前台直接跑 | 立即看到结果 |
| 30 秒 - 数分钟 | **`BGContinuedProcessingTask`**（前台发起） | "它开始跑了，我可以切走" |
| 数分钟、可等空闲 | `BGProcessingTask`（辅助） | "它在充电时会把索引建好" |
| 需要多轮推进的长期目标（Goal） | **检查点 + 下次唤醒续跑** | "它总能接上，不会重来" |
| 大文件传输 | 后台 URLSession | "下载继续着" |

## 2. Turn 的"可挂起性"设计

### 2.1 检查点边界（Checkpoint Barrier）

只有以下位置是"允许被中断"的边界（其余位置中断需回退到最近边界）：

| 边界 | 说明 |
|---|---|
| 工具调用**开始前** | 记录意图（`ToolCallRequested`），尚未产生副作用 |
| 工具调用**结束后** | 记录结果（`ToolCallFinished`）+ 文件快照 |
| 模型调用**结束后** | 记录归一化响应摘要 |
| 用户审批**待决时** | 状态 = `awaitingToolApproval`（天然稳定态） |
| 计划批准后 | "开始动手"前的干净点 |

**不允许在工具执行中途"假装完成"**：中途被杀时，该工具要么整体重做（幂等），要么标记为"结果未知 → 必须询问用户"（非幂等）。

### 2.2 三步落盘协议（防止"做了但没记"）

任何有副作用的工具调用，必须按顺序：

```
1. 写 ToolCallRequested（含参数哈希、幂等键）        ← 意图落盘
2. 执行
3. 写 ToolCallFinished（含结果摘要、制品引用、快照 id） ← 事实落盘
```

恢复时的一致性判定：

| 恢复时看到的状态 | 判定 | 动作 |
|---|---|---|
| 只有 Requested，无 Finished | 执行结果未知 | 幂等工具 → 安全重做；非幂等 → 询问用户 |
| 有 Requested + Finished | 已完成 | 跳过，直接采用记录的结果 |
| Requested 有、Finished 有，但快照缺失 | 文件状态可能不一致 | 用文件实际内容与期望哈希比对；不一致 → 提示用户选择回滚或保留 |

> **这个协议是"后台续跑不可靠"这一风险的核心缓解。** 它的正确性由"随机中断一致性测试"（100 次随机 kill）来证明（见 §8.1）。

## 3. 作业（Job）状态机

长任务（跑测试、构建、批量处理、索引）不进主循环阻塞，而是转为 Job。

```
        ┌────────┐  启动   ┌─────────┐  完成  ┌──────┐
        │ queued │────────▶│ running │───────▶│ done │
        └────────┘         └────┬────┘        └──────┘
                                │ 失败         ┌────────┐
                                ├─────────────▶│ failed │
                                │ 被杀/挂起     └────────┘
                                ▼
                          ┌───────────┐  唤醒后  ┌─────────┐
                          │ resumable │─────────▶│ running │
                          └───────────┘          └─────────┘
                                │ 用户取消 / 系统压力
                                ▼
                            ┌───────┐
                            │ killed│
                            └───────┘
```

| 设计点 | 说明 |
|---|---|
| 执行载体选择 | 前台 → 直接跑；用户点"在后台继续" → **`BGContinuedProcessingTask`**；长时间索引 → `BGProcessingTask` |
| 输出增量读 | 每个 Job 有 `lastOutputSeq` 游标，主循环只读新增输出 |
| 输出落制品 | 输出超过 64KB 自动转存 `artifacts/job-<id>.log`，上下文只放"最近 40 行 + 关键错误行" |
| 可断点续跑 | 沙箱 Job 支持"分段执行"：运行时在 VFS 里保存进度文件，恢复时从进度继续 |
| 进展上报 | 延续处理任务**必须持续上报进展**（`task.updateTitle` / `progress`），因为**系统在内存压力下优先杀掉进展低的任务** |
| 强杀 | 用户取消或超限 → 沙箱强杀 + 记录 `JobKilled` |
| 数量上限 | 同时活跃 Job ≤ 3（内存与 CPU 预算） |

### 3.1 `BGContinuedProcessingTask` 的正确用法（关键实现细节）

```swift
// 1) 由用户在前台显式发起（唯一合法起点）
BGTaskScheduler.shared.register(forTaskWithIdentifier: "app.rune.continue", using: nil) { task in
    guard let task = task as? BGContinuedProcessingTask else { return }
    Task {
        await self.runContinuedWork(task)
        task.setTaskCompleted(success: true)   // 必须调用，否则会被终止
    }
}
// 2) 提交任务时必须给出用户能看懂的名字与进度（系统会展示在 Live Activity 里）
let request = BGContinuedProcessingTaskRequest(identifier: "app.rune.continue",
                                              title: "修复 CI 失败：orders 退款测试",
                                              subtitle: "第 5/8 步 · 正在运行 pytest")
try BGTaskScheduler.shared.submit(request)
```

**五条纪律**：
1. **只在前台发起**，且必须有清晰的用户动作（"在后台继续"按钮 / 语音"继续跑"）。
2. **进度必须真实**：系统会展示并据此决定先杀谁 —— **不要把进度条做成装饰**。
3. **可被随时取消**：用户从系统 UI 取消时，我们要**优雅收尾**（落检查点、写事件），而不是留下半成品。
4. **多任务界面强制退出 = 无回调取消** → 所以**检查点必须在每一步都落盘**，不能指望收尾回调。
5. **GPU / Neural Engine 需要对应 entitlement**；App Store 构建中若未获批，**延续处理期间禁用 GPU/ANE 推理**（自动降级到 CPU 或暂停端侧推理）。

## 4. 唤醒与续跑调度

### 4.1 唤醒来源与优先级

| 来源 | 何时 | 能做什么 | 限制 |
|---|---|---|---|
| **用户在前台发起延续处理** | 用户点击 | ⭐ 数分钟级连续工作（可选网络、密集 CPU） | 需前台发起；可见可取消 |
| **用户打开 App** | 随时 | 全速续跑（前台不受限） | — |
| **BGAppRefreshTask** | 系统按使用习惯调度 | 30 秒内做一件事 | 硬上限 30s |
| **BGProcessingTask** | 设备空闲 + 满足条件 | 重活（索引构建、批量处理） | 用户一用设备就被终止 |
| **静默推送** | 不保证送达 | 30 秒推进 1 步 | **每小时 ≤ 2-3 条** |
| **后台 URLSession 完成回调** | 传输结束时 | 处理下载结果（例如模型权重就绪） | 仅传输 |

**因为没有自有服务器，Rune 没有任何"远程把手机唤醒"的手段。** 这是"无服务器"定位的代价，也是隐私保证的来源。产品上必须**如实告诉用户**：
> 长任务会在**你再次打开 App**、或在**设备空闲充电时**继续推进；如果任务在你离开时还没做完，我们会把它安全暂停，绝不丢失进度。

### 4.2 续跑调度器

```swift
public actor ContinuationScheduler {
    /// 前台进入 / 收到后台机会 / 延续处理任务被调度时调用
    func tick(trigger: WakeTrigger, budget: TimeBudget) async {
        // 1. 收集可续跑实体（按优先级）
        let candidates = await store.resumableEntities()
            .sorted { priority($0) > priority($1) }   // 延续处理 > Goal > Turn > Job > 索引

        // 2. 全局条件门槛
        guard await conditionsAllow(budget) else { return }
        //    · 预算类型允许（延续处理可联网；AppRefresh 只做本地）
        //    · 电量 > 20% 或充电中
        //    · thermalState 未到 .critical（端侧推理要求更严）
        //    · 未超成本/电量预算
        //    · 用户未关闭自动续跑
        //    · 距上次活动 < 24 小时（防僵尸任务半夜跑起来）

        // 3. 逐个推进到检查点边界，并在每一步后：
        //    · 上报进展（延续处理任务必须做，否则优先被杀）
        //    · 检查 Task.isCancelled 与剩余时间
        for entity in candidates {
            while budget.hasRemaining {
                if !(await advance(entity)) { break }      // 推进到下一个检查点
                await reportProgress(entity)               // 真实进度
                if await shouldYieldForUser() { break }    // 用户回来了，让位
            }
        }
        // 4. 落盘 + 更新 Live Activity + 必要时通知
    }
}
```

**`shouldYieldForUser`（让位）**：用户一打开 App 开始输入，后台续跑立即让出资源（避免"我打字它卡"）。移动端特有的礼貌。

## 5. 断点续跑：实现细节

### 5.1 恢复流程（进程重启后）

```
1. 打开数据库（WAL 自动恢复）
2. 校验哈希链（最近锚点 + 尾部）
3. 找 open 实体：turn(状态非终态) / job(queued|running|resumable) / workflow_run / goal(active)
4. 对每个 Turn：
   a. 读最后一个 Checkpoint
   b. 核对 VFS 快照与实际文件（哈希比对）
   c. 重放检查点之后的事件，重建内存状态：
      · 已完成工具 → 结果从事件取，不重跑
      · 未完成工具 → 按幂等性决定重做或询问
      · 模型调用 → 若已收完整响应则复用（含 requestFingerprint 去重），否则重发
   d. 状态置为可继续，触发一次续跑 tick
5. 更新 Live Activity / 可选发一条"已恢复"通知
6. UI 卡片告知：'任务在 09:14 被打断，已从检查点恢复（跳过 3 个已完成步骤）'
```

### 5.2 幂等性分级（工具契约）

| 级别 | 工具举例 | 恢复策略 |
|---|---|---|
| **天然幂等** | `read_file` / `glob` / `grep_search` / `git_status` | 直接重做 |
| **内容幂等** | `write_file` / `edit_file` / `apply_patch` / `make_dir` | 比对目标当前哈希：已是期望值则跳过 |
| **指纹幂等** | `run_python` / `run_tests`（无网络） | 用 `execFingerprint` 复用上次结果 |
| **非幂等（可询问）** | `run_shell`（可能带网络副作用）/ 任意 `http_request` POST | 默认不重做；提示"这一步的结果未知，是否重试？" |
| **不可重放（永不自动重做）** | `git_push` / `create_pull_request` / `notify_user` / 支付类 | 中断后标记需用户确认，并展示"上次是否已执行"的证据（查远端状态） |

**设计约束**：非幂等工具的列表必须**短且显式**。新增非幂等工具需在评审中说明为什么无法做成幂等。

**为什么这比桌面更重要**：桌面 Agent 假设进程一直活着，所以可以"先做后记"；iOS 上进程随时消失，因此**必须"先记意图、再做、再记事实"**。这条纪律一旦破，就会在真实用户那里产生"推送了两次"这种事。

## 6. 资源与预算（后台也要花钱）

| 维度 | 前台 | 后台 / 续跑 |
|---|---|---|
| 单步时限 | 120s | 尽量短（目标 5-10s/步），让"跑几步存一次"成为常态 |
| 网络 | 允许 | 延续处理任务允许；`BGAppRefreshTask` 期间只做本地 |
| 模型调用 | 按 Turn 预算 | **单独的后台日预算（默认 $0.50/天）**，超过则只做本地操作 |
| 端侧推理 | 允许 | **需 `.continued-processing.inference` 权限**；未获批则自动改用 CPU 或暂停 |
| 电量 | 无额外限制 | 后台累计电量预算（默认 15%/天）；电量 < 20% 自动停后台重活 |
| 热 | 温和降级 | `thermalState >= .serious` → 停止后台重活；`.critical` → 全停 |
| 磁盘 | — | 制品配额（默认 2GB），超限清理最旧且未 pinned 的制品 |

**成本熔断的后台特例**：后台续跑如果会花钱，**默认需要用户预先授权**（"允许后台自动续跑，每天最多 $0.50"）。不授权就只做本地步骤。**这是防止"用户在睡觉，Agent 在烧钱"的关键设计。**

## 7. 崩溃与异常的恢复体验

| 情况 | 用户看到 | 系统行为 |
|---|---|---|
| App 崩溃（前台） | 下次打开："上次任务在崩溃前已完成 X 步，是否继续？" | 从检查点恢复；崩溃信息本地保存（脱敏后可选上报） |
| 被系统回收（后台） | Live Activity 保持最后状态；下次打开显示"已从检查点恢复" | 在授权范围内自动继续 |
| **延续处理任务被系统取消**（内存压力/用户取消） | "任务已暂停（系统回收资源）。进度已保存。" | 落检查点，进入 `resumable` |
| **用户从多任务界面强制退出** | 下次打开："任务被强制结束，已从检查点恢复" | **无回调**，只能靠检查点恢复 |
| 数据库损坏（罕见） | 引导页：① 从备份恢复 ② 导出可读数据 ③ 重置 | 哈希链校验 + 隔离损坏表 + 尽力导出 |
| 沙箱反复崩溃（某脚本） | "该脚本连续 2 次异常退出，已停止。是否查看错误？" | 隔离该脚本执行 |
| 渠道全部不可用 | "所有云端渠道当前不可用。可用：本机模型（能力有限）" | 切端侧或暂停 |
| 磁盘满 | "工作区剩余空间不足（< 200MB），已暂停写入类操作" | 暂停 + 建议清理 |

## 8. 可靠性测试（必须自动化）

### 8.1 随机中断一致性测试（Release Gate）

```swift
@Test(arguments: 0..<100)
func crashConsistency(seed: Int) async throws {
    let env = TestEnvironment(fixtureRepo: "shop-api", provider: .cassette("fix_refund_test"))
    let reference = try await env.runToCompletionWithoutInterruption()   // 基线
    let interrupted = try await env.runWithRandomKill(seed: seed)        // 随机时刻杀 + 重启 + 续跑
    XCTAssertEqual(interrupted.finalFileTreeHash, reference.finalFileTreeHash)
    XCTAssertEqual(interrupted.commitCount, reference.commitCount)
    XCTAssertEqual(interrupted.egressRequests, reference.egressRequests)   // 无重复外发
    XCTAssertEqual(interrupted.totalCostMicroUSD, reference.totalCostMicroUSD)  // 无重复计费
}
```

**通过标准：100 个随机种子全部一致。任何一次不一致都是 P0 阻塞发布的问题。**

### 8.2 其他可靠性测试

| 测试 | 频率 |
|---|---|
| 后台过渡窗口内完成"落盘 + 更新 Live Activity" | 每次提交 |
| `BGAppRefreshTask` 在 30 秒内完成并调用 `setTaskCompleted` | 每次提交 |
| 延续处理任务被取消时的优雅收尾（落检查点、无半成品） | 每次发版 |

| `BGAppRefreshTask` / `BGProcessingTask` 条件不满足时不执行 | 每次提交 |
| 24 小时僵尸任务不自动续跑 | 每次发版 |
| 锁屏后流式请求断开 → 回前台正确重连或重发 | 每次发版 |

## 9. Live Activity：把"不可见的后台"变成"可见的陪伴"

Live Activity 是 Rune 后台体验的核心外显通道（[08 §8](08-交互与体验设计.md)）：

| 状态 | 锁屏 / 灵动岛呈现 | 可直接操作 |
|---|---|---|
| 运行中 | 进度环 + `5/8` + 当前步骤 | 暂停 |
| 需要决策 | ⚠ + 一句话问题 | **三个动作按钮**（批准/拒绝/查看） |
| 完成 | ✓ + 结果摘要 | 查看产物 |
| 受阻 | ⛔ + 阻塞原因 | "去做那件事" |
| 已挂起等唤醒 | 灰色 + "等待下次唤醒" | 回到 App |

**两条硬约束**：
1. **寿命上限 12 小时**（8 小时活跃 + 4 小时锁屏）→ 超过就结束活动并转为普通通知。**不要试图让 Live Activity 永久常驻**（做不到，且会浪费系统资源）。
2. **超过 160pt 会被截断** → 信息层级要按"160pt 内说完"来设计。

**更新纪律**：只在**检查点边界**更新（不是每个 token）。这与 §2.1 天然对齐——检查点边界本来就是"需要用户知道的状态变化点"。注意：延续处理任务自身的进度由**系统**展示（系统 Live Activity），我们的 Live Activity 负责补充业务信息，两者不要冲突。

## 11. 必须写进产品文案的诚实说明

> **关于运行时间**：iOS 不允许 App 一直在后台运行。所以当 Rune 的任务还没做完而你把 App 切走或锁屏时，它会**在安全的位置暂停**，并在**你再次打开 App、或在设备空闲充电时**继续。所有进度都已保存，不会丢失，也不会重复执行已完成的步骤。
> 对于较长的任务，你可以点"**在后台继续**"——iOS 会允许它在后台再跑一段时间，并在锁屏上显示进度，你可以随时取消。
> 如果你希望它在后台也能继续花钱调用云端模型，需要在设置里**预先授权后台预算**（默认关闭）。

**说清限制，比假装没有限制更值得信任。**
