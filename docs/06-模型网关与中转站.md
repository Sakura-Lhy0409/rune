# 06 · 模型网关与中转站

> **摘要**：Rune 不绑定任何一家模型。网关（RuneGateway）的职责是：**把 11 种协议族的差异全部吃掉，向上只暴露一套归一化类型**；同时把"钱、速度、能力、隐私"四个维度变成可配置的路由策略，并让用户随时知道"这一轮是谁在回答、花了多少、我的内容去了哪"。
> 本文给出协议矩阵、流式工具调用拼装算法、Prompt Caching 对齐策略、中转站接入规范与降级/重试/幂等设计。

---

## 1. 网关职责边界

```
        ┌────────────────────────────────────────────────────────┐
        │ AgentRuntime / ContextAssembler                        │
        │   只认：ChatRequest（归一化） → ModelEvent 流（归一化）    │
        └───────────────────────┬────────────────────────────────┘
                                ▼
   ┌──────────────────── RuneGateway ────────────────────────────┐
   │ Router：任务类型 → 模型（策略 + 预算 + 白名单 + 健康）          │
   │ Adapter：11 种协议族 ⇄ 归一化（序列化 / 流式解析 / 错误映射）    │
   │ Cache：Prompt Cache 断点规划 + 上下文稳定性对齐                 │
   │ Retry：幂等重试 / 降级 / 限流退避 / 断流续传                    │
   │ Ledger：token 与成本记账（含缓存折扣）+ 配额熔断                 │
   │ Secrets：唯一密钥注入点（Keychain → 请求头）                    │
   │ Egress：所有出站必过出口策略与审计（见 09 §6）                   │
   └─────────────────────────────────────────────────────────────┘
```

**一条铁律：`AgentRuntime` 里不允许出现任何厂商名称、任何厂商特有的字段名。** 违反这条的 PR 一律拒绝。

## 2. 协议族矩阵

| 协议族 | 代表厂商 | 端点 | 鉴权 | 流式 | 工具调用 | 思考链 | 缓存 |
|---|---|---|---|---|---|---|---|
| **OpenAI Chat Completions** | OpenAI、以及 90% 兼容端点 | `POST {base}/chat/completions` | `Authorization: Bearer` | SSE `data:` | `tools` + `tool_calls` delta | `reasoning_content`（部分）/ 无 | 自动（部分模型） |
| **OpenAI Responses** | OpenAI 新一代 | `POST {base}/responses` | 同上 | 事件化 SSE（`response.output_text.delta` 等） | `tools` + `function_call` items | `reasoning` items + summary | 自动 |
| **Anthropic Messages** | Anthropic、部分中转 | `POST {base}/v1/messages` | `x-api-key` + `anthropic-version` | 事件化 SSE（`content_block_delta` 等） | `tools` + `tool_use` blocks | `thinking` blocks（需 beta header） | **显式 `cache_control` 断点** |
| **Gemini generateContent** | Google | `POST {base}/v1beta/models/{m}:streamGenerateContent` | `x-goog-api-key` 或 query | SSE / JSON 数组 | `functionCall` parts | `thought` parts | 隐式 + 显式缓存 |
| **DeepSeek** | DeepSeek | `POST {base}/chat/completions`（OpenAI 兼容） | Bearer | SSE | `tools`（兼容层） | `reasoning_content` 字段 | **自动上下文缓存（命中即降价）** |
| **OpenAI 兼容变体** | Qwen / Kimi / GLM / Doubao / MiniMax / xAI / Groq / Cerebras / Together / Fireworks / vLLM / Ollama / LM Studio / OpenRouter / 中转站 | 同 Chat Completions | Bearer / 自定义头 | SSE | 大部分支持，个别不支持 | 各家自定义字段 | 个别支持 |
| **本地/端侧** | Apple Foundation Models / MLX / llama.cpp | 进程内 | 无 | 本地流 | 支持（能力弱） | 无 | 无 |

> 📌 **三条必须先知道的事实（2026-09 核对，详见 [附录 A](附录A-渠道与模型事实表.md)）**
> 1. **OpenAI 的推理 Agent 必须走 `/v1/responses`**：自 GPT-5.4 起，Chat Completions 在 `reasoning_effort ≠ none` 时**不支持工具调用**。因此 Responses 是 Rune 的 OpenAI 主路径，Chat Completions 仅作兼容与降级。
> 2. **状态化正在上移到厂商侧**（`previous_response_id` / `previous_interaction_id`）。Rune **默认不使用**，因为把上下文托管给厂商与隐私主张冲突；仅作为超长会话的可选加速项（§14）。
> 3. **没有任何厂商提供官方幂等键**：`X-Client-Request-Id` 只是追踪 id，不是去重令牌。重试安全必须靠"复用状态化 id + 依赖 Prompt Cache 让重放变便宜 + 本地记账去重"。

**实现策略：一个 `OpenAICompatibleAdapter` + 少量差异化开关（quirk flags）覆盖 7 家以上厂商**，而不是为每家写一个适配器。差异化用声明式配置表达：

```swift
struct ProviderQuirks: Sendable, Codable {
    var toolCallDeltaStyle: ToolCallDeltaStyle   // .openAIStandard / .singleShot / .anthropicBlocks / .geminiParts
    var requiresToolResultName: Bool             // 某些兼容端点要求 tool 消息带 name
    var reasoningField: ReasoningField           // .none / .reasoningContent / .reasoning / .thinkingBlocks / .thoughtParts
    var maxTokensField: String                   // "max_tokens" / "max_completion_tokens"
    var systemRolePlacement: SystemPlacement      // .systemMessage / .topLevelParam(anthropic) / .systemInstruction(gemini)
    var unsupportedFields: Set<String>           // 发送前剔除（某些端点不认识就报错）
    var cacheStyle: CacheStyle                   // .none / .automatic / .explicitBreakpoints / .implicitPrefix
    var streamingUsage: UsageStyle               // .finalChunk / .separateEvent / .absent（需本地估算）
    var toolChoiceSemantics: ToolChoiceStyle     // .auto / .required / .none / .unsupported
}
```

> **quirk flags 是新渠道接入的关键**：接入一个从未见过的新中转站，往往只需要在设置里勾几个开关，而不是改代码。这直接决定"支持市面上主流模型"这件事能不能规模化。

## 3. 归一化类型

```swift
// MARK: 请求
public struct ChatRequest: Sendable {
    public var systemBlocks: [SystemBlock]      // 分层系统提示（见 04 §13），带 cacheable 标记
    public var messages: [Message]              // 归一化消息（role + content blocks）
    public var tools: [ToolSpec]
    public var toolChoice: ToolChoice           // .auto / .required / .none / .specific(name)
    public var maxOutputTokens: Int
    public var temperature: Double?
    public var reasoning: ReasoningRequest?     // .effort(low|medium|high) / .budget(tokens) / .off
    public var stopSequences: [String]
    public var metadata: RequestMetadata        // 会话/轮次标识、渠道、估算成本、缓存断点规划
    public var stream: Bool
    public var idempotencyKey: String?          // 用于重试去重
}

// MARK: 流式事件（归一化）
public enum ModelEvent: Sendable {
    case started(modelID: String, providerID: String)
    case textDelta(String)
    case reasoningDelta(String)                  // 各家思考链统一到这里
    case reasoningSignature(Data)                // Anthropic 的 signature / 加密思考块回传
    case toolCallStarted(index: Int, id: String, name: String)
    case toolCallArgumentsDelta(index: Int, jsonFragment: String)
    case toolCallCompleted(index: Int, id: String, name: String, argumentsJSON: Data)
    case usage(Usage)                            // 可能出现在中间或末尾
    case cacheInfo(cachedTokens: Int, writtenTokens: Int)
    case finished(reason: FinishReason)          // .stop / .length / .toolCalls / .contentFilter / .error
    case providerError(ProviderError)            // 分类后的错误（可重试/需配置修复/致命）
}

public struct Usage: Sendable, Codable {
    public var inputTokens: Int
    public var outputTokens: Int
    public var cachedInputTokens: Int            // 缓存命中（读取）
    public var cacheWriteTokens: Int             // 缓存写入（Anthropic 语义）
    public var reasoningTokens: Int?
    public var estimated: Bool                   // 厂商未返回时按本地 tokenizer 估算
}
```

**为什么 `toolCallArgumentsDelta` 必须逐片上报**：UI 可以实时展示"正在构造参数"，用户能看到 Agent 在写一个 200 行的补丁；同时避免在网关层累积大 buffer。

## 4. 流式工具调用拼装（最容易写错的地方）

### 4.1 三类协议的差异

| 协议 | 形态 | 拼装难点 |
|---|---|---|
| **OpenAI 标准** | 同一 `index` 的多个 delta 分片，`arguments` 是**字符串片段**需要拼接；`id`/`name` 通常只在首个分片出现 | 必须按 `index` 分组；`id`/`name` 可能缺失或重复出现；空字符串 delta 需忽略 |
| **Anthropic blocks** | `content_block_start`（含 id/name）→ 多个 `input_json_delta`（partial_json）→ `content_block_stop` | 一个消息里可能同时有 text block 与 tool_use block，需按 block index 路由；`input_json_delta` 的累积结果可能是**合法 JSON 但语义不完整**（例如流中间） |
| **Gemini parts** | `functionCall` 常**一次性给全参数**（非流式拼装），但 functionCall parts 之间可能有 thought parts 交错 | 不拼装，直接取值；需处理 thoughtSignature 回传 |

### 4.2 拼装算法（骨架）

```swift
final class ToolCallAssembler {
    private struct Partial { var id: String?; var name: String?; var json = ""; var completed = false }
    private var byIndex: [Int: Partial] = [:]
    private var order: [Int] = []

    func ingest(_ ev: ModelEvent) -> [AssembledToolCall] {
        switch ev {
        case .toolCallStarted(let i, let id, let name):
            if byIndex[i] == nil { order.append(i) }
            byIndex[i, default: .init()].id = id
            byIndex[i, default: .init()].name = name
        case .toolCallArgumentsDelta(let i, let frag):
            if byIndex[i] == nil { order.append(i); byIndex[i] = .init() }
            byIndex[i]?.json += frag
        case .toolCallCompleted(let i, let id, let name, let args):
            // 某些端点只给完整结果（Gemini 风格）——直接以完整值覆盖，避免重复拼装
            byIndex[i] = .init(id: id, name: name, json: String(decoding: args, as: UTF8.self), completed: true)
        case .finished(let reason) where reason == .toolCalls:
            return flush()
        default: break
        }
        return []
    }

    private func flush() -> [AssembledToolCall] {
        order.compactMap { i in
            guard let p = byIndex[i], let name = p.name else { return nil }
            // ★ 容错：JSON 可能不完整（被截断/模型写坏）→ 尝试修复，失败则交给"修正性重试"
            let repaired = JSONRepair.repair(p.json)            // 补括号、去尾逗号、转义修复
            return AssembledToolCall(index: i, id: p.id ?? UUID().uuidString,
                                     name: name, rawJSON: p.json, repairedJSON: repaired)
        }
    }
}
```

### 4.3 必须处理的 7 个脏情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | `arguments` 为空字符串 | 视为 `{}`（无参数工具） |
| 2 | JSON 被截断（`finish_reason == length`） | 尝试修复；失败则视为"参数不完整"，触发修正性重试并提示模型缩短参数 |
| 3 | 同一 index 的 `name` 多次出现且不同 | 以最后一次为准，并记录 warning（可能被中转站篡改） |
| 4 | 工具名不存在 | 走"工具名幻觉"修正路径（[04](04-Agent运行时核心.md) §4.4） |
| 5 | 参数不合 schema | 回灌校验错误让模型重发（最多 2 次） |
| 6 | 流在工具调用中途断开 | 记录部分参数；重连后如果厂商支持续传则续，否则**重发整个请求**（用幂等键避免重复计费） |
| 7 | `finish_reason` 缺失（部分中转站不发） | 以"收到 `[DONE]`"或"连接正常关闭"作为结束信号；超时兜底 |

## 5. 思考链（Reasoning / Thinking）归一化

| 厂商形态 | 归一化 |
|---|---|
| DeepSeek `reasoning_content`（独立字段，需在下一轮回传或不回传） | `reasoningDelta` → `ReasoningBlock(text:)`；**默认不回传**（多数端点会报错），仅在模型要求时回传 |
| OpenAI Responses 的 `reasoning` items + encrypted content | 保留 `id` 与加密载荷，下一轮**原样回传**（不回传会显著掉能力） |
| Anthropic `thinking` blocks + `signature` | 保留 `thinking` 文本与 `signature`，**工具调用轮必须原样回传**（缺少 signature 会报错） |
| Gemini `thought` parts + `thoughtSignature` | 同上，保留 signature |
| 无思考链的模型 | 无 |

**三条规则：**
1. **思考链默认不显示给用户**（占屏幕），但可一键展开；**思考链永远不进入记忆库**。
2. **回传策略按模型声明**（`ProviderCapabilities.reasoningReplayPolicy`），不是全局统一——这是"换模型能力不塌"的关键细节。
3. **思考链不计入输出成本展示的主项**（但如实计入 token 与费用）。

## 6. 中转站（Relay）一等公民支持

中文开发者生态里，中转站是刚需。Rune 不禁止它，而是把它做成**功能完整、风险透明**的一等渠道。

### 6.1 渠道配置模型

```swift
public struct ProviderConfig: Sendable, Codable {
    public var id: ProviderID
    public var displayName: String
    public var protocolFamily: ProtocolFamily        // 见 §2
    public var baseURL: String                       // ★ 任意，含路径前缀（/v1 或 /api/v1）
    public var auth: AuthConfig                      // .bearer(keyRef) / .header(name, keyRef) / .query(name, keyRef) / .none
    public var extraHeaders: [String: String]        // 某些中转需要自定义头（如 X-Relay-Token）
    public var category: ProviderCategory            // .official / .officialCloud / .thirdPartyRelay / .selfHostedLAN / .onDevice
    public var riskNote: String?                     // 展示给用户的风险提示
    public var dataPolicyNote: String?               // 数据是否用于训练（用户可改）
    public var modelAliases: [String: String]        // 本地别名 → 远端模型名
    public var priceOverrides: [String: PriceTable]  // 中转价格与官方不同，必须能覆盖
    public var quirks: ProviderQuirks
    public var allowInsecureTLS: Bool                // 默认 false；局域网自签场景可开（需显式确认）
    public var allowPrivateNetwork: Bool             // 局域网地址（Ollama/LM Studio/自建）
}
```

### 6.2 接入流程（用户视角，目标 ≤ 2 分钟）

```
设置 → 模型渠道 → 添加
 ① 选择协议族（OpenAI 兼容 / Anthropic / Gemini / DeepSeek / 其他）
 ② 填 Base URL（提供常见预设：官方 / OpenRouter / 常见中转格式提示）
 ③ 填 API Key（写入 Keychain，界面只显示尾部 4 位）
 ④ 点「探测」 → 自动：
     · 请求 /v1/models（或等效端点）拉取模型列表
     · 对每个模型做一次最小调用（1 token）验证可用性
     · 尝试识别上下文窗口、是否支持工具调用、是否支持视觉
     · 测延迟与首 token 时间
 ⑤ 展示探测结果表格 → 用户勾选要启用的模型 → 可为每个模型设别名与价格
 ⑥（可选）保存为"渠道模板"，可分享给同事（不含 key）
```

**探测的降级**：若 `/v1/models` 不存在（部分中转站不支持），允许用户**手动输入模型名**，并允许"跳过验证"（仍会在首次真实调用时验证）。

### 6.3 中转站专项功能

| 功能 | 说明 |
|---|---|
| **风险标注** | 渠道列表上明确标签：`第三方中转 · 服务方可见你的全部内容`。首次使用弹一次说明（可勾"不再提示"） |
| **敏感项目隔离** | 工作区设置里可勾"本项目的任务只允许官方直连或端侧模型"，此时中转渠道不出现在可选列表（并解释原因） |
| **响应来源标记** | 会话中每个助手回复带渠道徽标；长按显示渠道详情与本次花费 |
| **健康探测** | 后台每 6 小时轻量探活（1 token 请求），失败 3 次标记 `failing` 并从路由中移除，同时通知用户 |
| **模型名映射** | 中转常用别名（如 `gpt-4o` 实际指向别家模型）。Rune 支持"声明式映射"并在 UI 提示"你选的 `gpt-4o` 在该渠道实际映射为 X"——**让用户知道自己在用哪个模型** |
| **价格覆盖** | 中转价格通常高于官方。Rune 成本账本默认用官方价估算，但可覆盖为渠道实际价（用户填或从渠道文档导入） |
| **一键切回直连** | 若某个渠道回答异常，会话内可"用官方直连重跑这一轮"做对比 |
| **不合规提示** | 部分中转可能违反上游厂商条款。Rune 在说明中提示该风险由用户与渠道之间承担（我们不做技术性规避，也不代持 key） |

### 6.5 四类主流中转实现的差异（实现依据）

接入中转不是"填个 base URL"就完了。市面上的中转实现行为差异明显，适配器必须识别：

| 实现 | 特点 | 必须处理的差异 |
|---|---|---|
| **one-api** | 暴露标准 OpenAI 格式；`Bearer KEY-CHANNEL_ID` 可指定渠道；额度 = 分组倍率 × 模型倍率 × token；非流式带真实 usage | 流式常缺 usage；`/v1/responses` 支持情况不明 |
| **new-api** | 同时提供 Responses / Claude Messages / Gemini 端点与协议互转；有缓存计费统计 | **Gemini → OpenAI 的函数调用不支持**；`STREAM_SCANNER_MAX_BUFFER_MB` 默认 64 → **大 base64 图片会打断流** |
| **uni-api** | 端点最全（含 `/v1/models`、`/v1/moderations`、`/v1/search`）；模型别名映射；多种调度与 cooldown；每模型价格 | 会发 `: keepalive` SSE 注释行；上游 base_url 必须以具体端点结尾；可用 `X-Uni-API-Provider` 指定上游 |
| **OpenRouter** | slug `vendor/model`；`:nitro` / `:floor` 后缀；`provider{...}` 路由偏好；usage **总是返回**（含 `cost`、`cached_tokens`） | 流中途错误以带顶层 `error` 对象的 chunk 到达；402 = 余额不足；BYOK key 会先于 `order` 被尝试 |

完整的端点、字段、限额与风险清单见 **[附录 A §3](附录A-渠道与模型事实表.md)**。这份表就是"支持市面上主流模型与中转站"的施工图。



支持的广度分三层：

| 层 | 覆盖 | 接入成本 |
|---|---|---|
| **L1 一等公民（我们主动适配并测试）** | OpenAI（Chat + Responses）、Anthropic、Gemini、DeepSeek | 高（每个都有 quirk 与测试） |
| **L2 兼容层（能用但不保证全特性）** | 任何 OpenAI 兼容端点：Qwen/DashScope、Kimi、GLM、Doubao/Ark、MiniMax、xAI、Groq、Cerebras、Together、Fireworks、Mistral、vLLM、Ollama、LM Studio、OpenRouter | 低（配置 + quirks） |
| **L3 任意中转** | 任何暴露 OpenAI/Anthropic/Gemini 风格端点或能通过"自定义协议"描述的服务 | 极低（用户配置） |

**L3 的关键设计**：提供一个"自定义协议"模式，允许用户用声明式 JSON 描述非标准端点：

```json
{
  "family": "custom",
  "request": {
    "method": "POST",
    "path": "/api/v2/chat",
    "headers": { "Authorization": "Bearer {{key}}", "Content-Type": "application/json" },
    "body": {
      "model": "{{model}}",
      "msgs": "{{messages}}",              // 使用归一化消息数组
      "max_new_tokens": "{{max_output}}",
      "stream": true
    }
  },
  "stream": { "textPath": "$.delta.content", "doneMarker": "[DONE]" },
  "response": { "textPath": "$.choices[0].message.content", "usagePath": "$.usage" }
}
```

> 这是"把长尾接进来"的最终手段。它不需要我们为每个小众服务改代码，用户自己能接。

## 7. Prompt Caching：手机上省钱的最大杠杆

### 7.1 为什么对移动端尤其重要

缓存命中的输入 token 通常只按 **10%-25%** 计费（各厂商不同），而 Rune 的系统提示 + 项目指令 + 工具清单是**每次调用都重复发送**的大头（常见 5k-20k token）。命中缓存能把单 Turn 输入成本降低 **60-85%**。

### 7.2 各厂商缓存机制与 Rune 的对齐策略

| 厂商 | 机制（2026-09 事实） | Rune 的适配 |
|---|---|---|
| **Anthropic** | `cache_control:{type:"ephemeral"}` 逐块标记；也可在顶层写一个字段启用自动缓存（断点自动前移）。TTL 默认 **5 分钟**（使用即续期），`"ttl":"1h"` 为**2×** 输入价；写入 5m=1.25×、读取 0.1×（Fable 5.1 / Mythos 5.1 读取低至 **0.025×**）；**最多 4 个断点**，且 1h 断点必须排在 5m 之前；**最小可缓存长度因模型而异**（512 / 1,024 / 2,048 / 4,096 token，不足则静默不缓存）；用量字段 `cache_creation_input_tokens`、`cache_read_input_tokens`，`total_input = read + creation + input` | 在层 1（身份契约）、层 2（项目指令 + 工具清单）打**最多 4 个**断点；**注意：修改 thinking 配置或 effort 会使断点全部失效**；缓存条目在首次响应开始后才存在；长会话可用 `max_tokens:0` 预热（扩展思考下不允许） |
| **OpenAI** | 隐式前缀缓存，**但没有显式断点就不会产生缓存写入**。GPT-5.6+：写入 1.25×、读取 0.1×（最高省 90%），**每请求最多 4 次写入**，通过 `prompt_cache_options.mode` / `prompt_cache_breakpoint` 控制，可选 `ttl:"30m"`；更早的模型用 `prompt_cache_retention`（`in_memory` 5-10 分钟 / `24h`，默认 24h，实际常见约 30 分钟）+ `prompt_cache_key` 做路由亲和。用量：`usage.input_tokens_details.cached_tokens` / `.cache_write_tokens`（`cached_tokens` 会对齐到 128 的整数倍） | 层 1+2 字节级稳定是前提；对支持断点的模型**主动打断点**，否则等于白丢 90% 折扣 |
| **DeepSeek** | **全自动磁盘缓存，无任何控制项**；按请求边界持久化 + 公共前缀检测；几小时到几天内清除；命中价与未命中价差距巨大（flash 命中 $0.006 vs 未命中 $0.30，v4-pro 命中 $0.044 vs 未命中 $1.32） | 把"重复出现的长稳定片段"（项目指令、工具清单、常用文件）放在**前缀位置**以提高命中；同时利用**低谷时段 5 折**做后台批量任务的时间调度 |
| **Gemini** | 2.5+ **默认隐式缓存**，节省自动传递（读 `usage.total_cached_tokens`，最小输入 4,096 / 2,048 token 因模型而异）；显式缓存 `POST /v1beta/cachedContents`（有 TTL 与存储费，**Interactions API 不支持**） | 短会话用隐式；稳定前缀 >32k 的长会话才考虑显式缓存，并算清"存储费 vs 节省" |
| **兼容端点 / 中转** | 多数无缓存；部分（OpenRouter、new-api）可**透传并统计**缓存用量 | 无缓存时主动**缩短稳定前缀**（精简工具描述、项目指令按相关性裁剪），把钱花在刀口；有统计的渠道要在账本里体现缓存收益 |

### 7.3 上下文稳定性对齐（工程师必须遵守）

```
层 1（身份与契约）       ← 会话内字节级不变
层 2（项目指令/结构/技能目录）← 会话内不变；项目文件变化时重建整个会话前缀
────────────────── 缓存断点 ──────────────────
层 3（Turn 目标/todo/记忆命中）← 每轮变
层 4（用户输入 + 工具结果）    ← 每轮变
```

**禁止事项**（会破坏缓存，直接导致用户多花钱）：
- ❌ 在层 1/2 里放时间戳、随机 ID、"当前时间"
- ❌ 把 todo 列表放进层 2
- ❌ 每轮重排工具顺序（工具顺序变化 = 前缀变化）
- ❌ 在层 2 里放"最近使用过的文件"

**度量**：成本账本里单列"缓存命中率"，并在设置页给出"本周因缓存节省 $X"的正反馈（让用户知道我们在替他省钱）。

## 8. 路由、降级、重试

### 8.1 路由策略（任务类型 → 模型）

```toml
# ⚠️ 下面的模型名仅作示例。模型阵容变动极快（2026-09 已与一年前完全不同），
#    实现上必须：① 以渠道探测出的模型清单为准 ② 用别名（alias）间接引用 ③ 价格表可更新。
[[route]]
task_kind = "triage"        # 意图分类、标题生成、脱敏判定
model     = "on_device:apple-fm"
fallback  = ["deepseek:flash"]        # 端侧不可用时

[[route]]
task_kind = "plan"          # 规划、架构决策
model     = "anthropic:opus"          # 别名 → claude-opus-5 / 用户指定的强推理模型
max_cost  = 0.05

[[route]]
task_kind = "code"          # 写代码、改代码（成本敏感，默认给便宜的强编码模型）
model     = "deepseek:v4-pro"
fallback  = ["openai:codex", "anthropic:sonnet"]

[[route]]
task_kind = "long_context"  # 大文件分析、全仓库理解
model     = "gemini:3.8-flash"        # 长窗口 / 长上下文优先
min_context = 200000

[[route]]
task_kind = "vision"        # 图片理解
model     = "openai:astra"            # 或 gemini / claude 视觉模型

[[route]]
task_kind = "cheap"         # 摘要、分类、格式化、commit message
model     = "on_device:apple-fm"
fallback  = ["deepseek:flash"]

[[route]]
task_kind = "verify"        # 独立验证（必须与执行用不同模型/不同上下文）
model     = "anthropic:sonnet"
must_differ_from = "executor"
```

**默认策略内置一套**（用户开箱即用），高级用户可完整覆盖。**`verify` 必须与执行模型不同**是硬规则：同模型自我验证几乎没有价值。

### 8.2 降级链与可见性

```
主渠道失败（可重试错误 ×2）→ 备用渠道
   ↓ 必须做的事：
   1. 发 ModelDegraded 事件 → UI 显示"因限流，本轮从 A 降级到 B（能力可能变化）"
   2. 若降级跨越了"思考链支持"，重建上下文（去掉 A 的 reasoning blocks）
   3. 若降级导致上下文窗口变小，触发压缩
   4. 记账时按实际渠道计价
```

**禁止静默降级**。用户付费买的是特定模型的能力，换了就必须说。

### 8.3 重试与幂等

| 错误 | 重试策略 |
|---|---|
| 429 / 限流 | 指数退避（1s, 2s, 4s，最多 3 次），读取 `Retry-After` |
| 5xx / 网关错误 | 退避重试 2 次 → 换渠道 |
| 连接中断（流中途） | 优先原生续传；否则带 `idempotencyKey` 重发 |
| 超时（首 token 未到） | 8s 无首 token → 重试一次（可能是渠道卡住），仍失败换渠道 |
| 401 / 403 | **不重试**，标记配置问题，提示用户去设置修 key |
| 400（参数错） | 不重试；解析错误信息，剔除非法字段后重试一次（常见于兼容端点） |
| 内容过滤 | 不重试；把过滤原因如实告知用户（不要偷偷改写 prompt 绕过） |
| 上下文超限 | 触发压缩后重试一次 |

**关于幂等（已按事实修正）**：**没有任何厂商提供官方幂等键**，`X-Client-Request-Id` 只是追踪 id。因此 Rune 的重试安全由三件事共同保证：

1. **本地请求指纹去重**：`requestFingerprint = SHA256(providerID + modelID + serializedBody)`。若同一 Turn 内出现相同指纹且已有完整响应，直接复用，不再发请求（省一次计费）。
2. **依赖缓存让重放变便宜**：Anthropic/OpenAI 的缓存读取价是原价 0.1×，所以"重发整个 turn"的代价远小于桌面时代的直觉（这也是 [附录 A §4.3](附录A-渠道与模型事实表.md) "按重发历史恢复"可行的原因）。
3. **副作用落盘三判**：重发之前先用 [10 §2.2](10-后台执行与可靠性.md) 的三步落盘协议判断"这一步究竟做没做"——**这是唯一能避免重复副作用的手段**，也是 Rune 不依赖厂商幂等键的底气。

## 10. 密钥管理

| 规则 | 实现 |
|---|---|

## 11. 端侧模型作为 Provider

端侧模型不是特殊分支，而是**实现同一 `ModelProvider` 协议的一个 Provider**：

```swift
public final class OnDeviceProvider: ModelProvider {
    public let id: ProviderID = "on_device"
    public var capabilities: ProviderCapabilities {
        .init(streaming: true, tools: true, vision: false,
              contextWindow: 4096,          // Apple FM 的窗口（实际值以 API 查询为准）
              reasoning: false, caching: false,
              maxConcurrent: 1,             // 端侧串行，避免争抢 ANE
              costModel: .free)
    }
    // 实现：Apple Foundation Models / MLX / llama.cpp 三种后端
}
```

**关键设计：端侧 Provider 的成本为 0，于是"路由策略"天然会优先用它**——这正是我们想要的（免费的活先给免费的模型）。但要在 UI 上明确标注"本轮由本机模型完成（能力有限）"，避免用户误解质量下降。

**并发限制**：端侧模型同一时刻只服务一个请求（`maxConcurrent: 1`），避免内存与 ANE 争抢导致整机卡顿。当端侧模型在跑时，UI 上显示"本机模型工作中"。

详见 [13](13-端侧模型与性能预算.md)。

## 12. 网络层（SSE 与弱网）

| 能力 | 设计 |
|---|---|
| SSE 解析 | 自研增量解析器：按 `\n\n` 划分事件、支持 `event:`/`id:`/`data:` 多行、忽略注释行与心跳、处理跨 chunk 断开的 UTF-8 |
| 连接复用 | 每个渠道一个 `URLSession`，配置 `httpMaximumConnectionsPerHost`、`waitsForConnectivity=false`（快速失败并降级） |
| 弱网策略 | 检测到高延迟（>3s 首字节）→ 自动切非流式短请求或切换渠道（可配置） |
| 后台行为 | 退到后台时：若已开始流式请求，用 `beginBackgroundTask` 争取时间完成；若被挂起，检查点记录已收内容；回前台时用"续传或重发"策略 |
| 代理 | 尊重系统代理设置；支持用户自配 HTTP 代理（企业网络场景） |
| 局域网 | 允许访问私有网段**仅当**用户显式开启 `allowPrivateNetwork`（Ollama/LM Studio 场景）；明文 HTTP 仅在该情况下允许 |
| 证书 | 默认强制 TLS 校验；自签场景需用户显式开启 `allowInsecureTLS`，并做证书指纹固定（防止中间人） |
| **ATS 现实（必须绕过的坑）** | ATS 例外在 Info.plist 里是**按域名静态声明**的，而中转站的 base URL 是**用户在运行时输入的**。因此：① 内置渠道用精确域名例外；② 用户自填的 `http://` 主机只能靠 `NSAllowsArbitraryLoads`（过审风险）或 `NSAllowsLocalNetworking`（仅局域网）覆盖 → **设计上要求：非局域网一律强制 HTTPS；确需明文时必须用户显式打开"不安全连接"开关并承担提示** |
| **Cloudflare JS 挑战** | `URLSession` **无法**通过 JS 挑战。部分中转站前置了 CF。方案：提供显式的"渠道登录"流程——用 `WKWebView` 打开该站点完成挑战，抓取 `cf_clearance` cookie 注入 URLSession 的 cookie 存储，并设置过期重取逻辑。**这是"支持任意中转站"必须实现的一块拼图** |
| NDJSON 兼容 | Ollama 原生端点返回的是 **NDJSON 而非 SSE**；适配器需按协议族分支选择解析器 |
| SSE 注释与心跳 | uni-api 等实现会发 `: keepalive` 注释行；解析器必须忽略注释行、空行与非标准字段，否则会中断流 |

## 14. 战略裁决：要不要用厂商的服务端工具

2026 年最大的变化是**模型厂商把工具搬到了自己服务端**：OpenAI Responses 内置 `web_search` / `file_search` / `code_interpreter` / `hosted_shell` / `apply_patch` / `computer_use` / `mcp`；Anthropic 提供 server tools（tool search、code execution、web search/fetch、MCP connector、服务端压缩）；Gemini 的 Interactions API 把状态也托管了。

这带来一个诱惑：**"既然厂商能跑代码，我们何必自己做 WASM 沙箱？"**

**Rune 的裁决（写进产品原则，不可被单方面推翻）：**

| 能力 | 默认 | 理由 |
|---|---|---|
| 服务端**网页搜索/抓取** | ✅ 允许（可选择） | 它不违反端侧执行的核心主张；但默认走本地实现以保证出口策略与可审计性，服务端搜索作为用户可选的加速项 |
| 服务端**代码执行**（`code_interpreter` / `hosted_shell` / `code_execution`） | ❌ **默认关闭** | 与 [01 铁律 1](../README.md) 直接冲突。它把用户代码送到第三方执行，且用户无法审计。开启时必须逐次确认并在会话中明确标注"本步骤在远端执行" |
| 服务端**结构化补丁**（`apply_patch`） | ❌ 不用 | 我们自己的 `apply_patch` 与检查点/回滚深度绑定，无法被替代 |
| 服务端**状态托管**（`previous_response_id` / `previous_interaction_id` / Conversations） | ❌ 默认关闭 | 上下文托管给厂商 = 用户的历史会话存在别人服务器上。仅在"超长会话 + 用户显式同意"时作为加速项 |
| 服务端**压缩**（Anthropic `compact_*`） | ⚠️ 备选 | 本地压缩优先（可控、无外发）；服务端压缩作为"本地压缩失败/成本过高"时的后路 |
| 服务端**工具检索**（`tool_search`） | ✅ 评估后可用 | 解决工具爆炸问题有价值，但需与本地技能检索保持一致，避免两套语义 |
| **MCP 作为插件 ABI** | ✅ 采用 | 两家厂商原生支持 MCP，MCP 已成为事实标准。但注意：**中转站通常会剥掉 `mcp_servers`**（DeepSeek 明确忽略），因此不能把 MCP 依赖建立在"经由中转"的链路上 |

**一条产品文案级别的承诺**：

> Rune 的核心工作（读写文件、执行脚本、跑测试、Git、检索、记忆）**永远在你的设备上完成**。
> 只有当某项能力我们确实做不了（例如需要联网搜索最新资料），才会请求云端协助，且在界面上一目了然。
