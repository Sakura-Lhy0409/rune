# 13 · 端侧模型与性能预算

> **摘要**：端侧模型在 Rune 里不是"主力的廉价替代"，而是**神经系统**——它负责所有高频、廉价、私密的判断（路由、分类、标题、摘要、脱敏、离线兜底），让云端大模型只在"真正需要智力"的地方被调用。
> 这个分工同时解决了四个问题：成本、延迟、隐私、断网。本文给出模型分工、设备分档、内存与电量账本、加载策略与离线闭环。

> 本文中标 `【待核实】` 的具体数值以 Apple 官方文档为准，核实结果见 [附录 B](附录B-技术选型核实表.md)。

**本文最关键的一条结论先放在这里**：Apple Foundation Models 的端侧会话窗口是 **4096 token**（指令、工具 schema、输入输出全部计入，Apple 建议工具数 ≤ 3-5 个），**它装不下一个自由 Agent 循环**。因此端侧在 Rune 里的角色是"神经系统"而非"小号大脑"，离线的主力形态是**确定性运行时编排 + 端侧模型只做分支决策**（§5.2）。

## 1. 定位：为什么端侧模型不做主力

| 维度 | 端侧 3-4B 级模型 | 云端前沿模型 | 结论 |
|---|---|---|---|
| 复杂任务成功率 | 低（长链工具调用容易崩） | 高 | 主力必须云端 |
| 上下文窗口 | 小（几千 token） | 几十万到百万 token | 端侧做不了长上下文 |
| 速度 | 慢（十几到几十 token/s） | 快（百 token/s 级） | 端侧做不了交互式长文 |
| 内存占用 | 数 GB（挤占沙箱与索引） | 0 | 端侧不能常驻 |
| 电量 | 高（GPU/ANE 满载） | 中（网络为主） | 端侧不能长时间跑 |
| 成本 | **0** | 按 token 付费 | **端侧的最大优势** |
| 隐私 | **完全本地** | 内容离开设备 | **端侧的第二个优势** |
| 离线可用 | **是** | 否 | **端侧的第三个优势** |

**结论：端侧模型在"高频 × 简单 × 短输出 × 敏感"的象限里是无敌的；一旦离开这个象限，就该让云端上。**

```
        高频
          │
   ┌──────┼──────────────────────────┐
   │ 端侧 │  端侧优先（若够用）        │
   │ 独占 │  · 标题/摘要/分类          │
   │      │  · 脱敏/敏感判定           │
   │ ─────┼──────────────────────────┤  低频
   │ 云端 │  云端独占                  │
   │ 优先 │  · 规划/架构/复杂编码       │
   │      │  · 长上下文分析            │
   └──────┴──────────────────────────┘
        简单 ────────────────▶ 复杂
```

## 2. 四类端侧/近端后端与分工

Rune 把每一个都抽象为 `ModelProvider`（[06 §11](06-模型网关与中转站.md)），只是成本与隐私级别不同：

| 后端 | 载体 | 谁提供 | 成本 | 定位 | 启用条件 |
|---|---|---|---|---|---|
| **A. Apple Foundation Models · 端侧系统模型** | 系统 on-device System Language Model | 系统，**不占我们内存、不占包体积、不需下载** | **0** | **默认端侧后端**：分类、结构化提取（`@Generable`）、短摘要、**少量工具的调用**（`Tool` 协议）、脱敏判定、内容过滤。⚠️ **硬上限：每会话 4096 token（含 Instructions、工具 schema、@Generable schema 与响应），Apple 建议工具数 ≤ 3-5 个** —— 详见 §5.3 | 设备支持 Apple Intelligence |
| **B. Apple Private Cloud Compute（PCC）** | `PrivateCloudComputeLanguageModel`（iOS 27+） | Apple 的隐私保护云端 | 由系统配额决定（**无需 API key**；**首 200 万次下载免费**，另有 `quotaUsage` 查询） | **"中间档"**：32,000 token 上下文 + 推理档位。当端侧不够、而用户没配任何云端渠道时使用；也适合"不想交出 API key 但需要更强模型"的用户 | 设备支持 Apple Intelligence **且需申请托管 entitlement `com.apple.developer.private-cloud-compute` 并通过资格审批** |
| **C. Core AI（iOS 27+）** | `AIModel` / `AIModelAsset` / `ComputeUnitKind`，**CPU / GPU / Neural Engine**，支持 CLI 预编译（AOT） | 我们分发模型资源 + 用户可导入自有模型 | 0（本地） | 需要**自定义/更强本地模型**且希望吃到 ANE 加速的正式路径 | 设备支持；内存达标；**后台访问 ANE 需 `.continued-processing.inference` entitlement** |
| **D. MLX / llama.cpp** | `mlx-swift` / `llama.cpp` XCFramework + 量化权重 | 我们 + 用户 | 0（本地） | 需要**最灵活的模型选择**（GGUF 生态、任意量化）时的路径 | 内存 ≥ 阈值（§3），用户显式下载 |

**优先级规则**：`A > B > C/D > 外部云端`——但**只在能力足够时**（见 §5.1 的"够用判定"）。若 A 的窗口或能力不足，**不要硬撑**，直接上 B 或云端（硬撑导致任务失败 + 重试，比直接调用更贵、更耗电）。

> ⭐ **B（PCC）的定位需要精确表述**：它是**Apple 的云**，不是我们的云。因此对用户的产品叙事依然成立（"Rune 没有自己的服务器"），但必须在 UI 上如实说明"这一步由 Apple 的隐私保护云端完成，内容会离开设备"。**它同时解决"新手没有 key"与"隐私敏感用户不想发给商业 API"两个问题**，且成本由系统承担（首 200 万次下载免费）。
> ⚠️ **但它是托管 entitlement**：需申请 `com.apple.developer.private-cloud-compute` 并通过 Apple 的资格审批。**这可能在审核/资质环节受阻**，因此架构上必须把它当成"可选增强"而非默认依赖——**没有它时，未配置渠道的用户只能走端侧 A**。

### 2.1 为什么默认押注 Apple 自家栈（A/B/C）

| 理由 | 说明 |
|---|---|
| **零体积** | 不需要下载数 GB 权重，不撑大 App 包，不触发"下载"相关的任何合规疑虑 |
| **零内存压力（A）** | 由系统托管，不受 App 内存上限挤压（**这是手机上最关键的优势**） |
| **零成本** | A/C/D 免费，B 由系统配额承担 |
| **隐私叙事一致** | A/C/D 完全本地；B 是 Apple 的隐私保护云端（可向用户解释清楚） |
| **系统级优化** | 与 ANE 协同，功耗与延迟由 Apple 调优；C 支持 AOT 预编译（无 JIT 也能吃到加速） |
| **合规友好** | 端侧处理的数据按 Apple 定义**不算"收集"**，不进隐私标签（[11 §6.2](11-AppStore合规与分发.md)） |

**代价**：A 能力弱、窗口小、可控性差（Apple 升级我们就变）；C/D 需要用户付出下载与内存成本；B 有系统配额上限且不完全受我们控制。
→ **因此四档并存，按能力与隐私需求分级使用，而不是只押一个。**

### 2.2 关于 C（Core AI）与 D（MLX/llama.cpp）的取舍

| 项 | C：Core AI（`.aimodel`） | D：MLX / llama.cpp |
|---|---|---|
| 硬件利用 | **CPU/GPU/ANE，正式支持的路径** | MLX 走 Metal；llama.cpp 走 Metal |
| 编译 | **CLI 工具做 AOT 预编译**（无 JIT 也能快） | 运行时加载权重 |
| 生态 | Apple 官方格式，需转换 | **GGUF / safetensors 生态最丰富** |
| 包体积/内存 | 资源随包或下载，可裁剪 | 权重较大 |
| 结论 | **优先采用**（长期主线） | 作为"模型选择自由度"的补充，尤其面向愿意折腾的用户 |

**两者都不是默认开启**：默认路径是 A（端侧）+ B（云端兜底）。C/D 是"用户显式选择的增强"，UI 上要写清内存与耗电代价。

## 3. 设备分档与启用策略

| 档位 | 典型设备 | 可用端侧后端 | 默认策略 |
|---|---|---|---|
| **T0 受限** | 老机型 / 内存 < 6GB | 仅 A（若支持 Apple Intelligence），不提供 B/C | 端侧只做分类与标题 |
| **T1 主流** | iPhone 15 Pro / 16 / 17 系列（8GB 级） | A + B/C（≤2.5GB 模型） | 默认 A；B/C 需用户显式开启 |
| **T2 大内存** | iPhone 17 Pro Max 级 / iPad Pro（12-16GB） | A + B/C（≤5GB 模型） | 可默认启用 3-4B 级模型 |
| **T3 iPad 专用** | iPad Pro M 系列 + 多窗口 | A + B/C（最大档）+ 更高并发 | 允许多窗口并行 |

**分档探测方式**（不依赖具体机型白名单，避免新机型不被识别）：

```swift
struct DeviceTier {
    let physicalMemory: UInt64            // ProcessInfo.processInfo.physicalMemory
    let availableMemory: UInt64           // ⭐ os_proc_available_memory()：系统允许本进程使用的真实上限
    let hasAppleIntelligence: Bool        // SystemLanguageModel.default.availability
    let hasPCC: Bool                      // PrivateCloudComputeLanguageModel 可用性
    let thermalLevel: ProcessInfo.ThermalState
    let isLowPowerMode: Bool

    var canRunLocalLLM: Bool { availableMemory >= 1_500_000_000 }   // 以"可用"而非"物理"判断
    var maxLocalModelBytes: UInt64 { min(availableMemory / 2, 6_000_000_000) }
}
```

> ⚠️ **Apple 不公布 jetsam（内存回收）的按设备上限**。因此**不要写死任何绝对阈值** —— 用 `os_proc_available_memory()` 在运行时问系统"我还能用多少"，并在首次启用端侧模型时做一个**探针**（生成 32 token，记录内存峰值与 tok/s），把结果缓存为"本机画像"。这样新设备无需更新 App 就能正确分档。
> 另注：`com.apple.developer.kernel.increased-memory-limit` 只在部分设备上有效且无保证，**不作为设计前提**。

## 4. 内存与性能预算

### 4.1 内存账本（8GB 级设备；Apple 未公布 jetsam 上限，故以下为**设计目标**而非系统常数）

| 组成 | 目标占用 | 说明 |
|---|---|---|
| App 基础（UI + 框架） | 120-180MB | SwiftUI + 图像缓存 |
| SQLite（含 WAL） | 40-80MB | mmap 64MB 上限 |
| 索引（L1 符号 + L2 向量） | 80-250MB | 分片加载，可随时释放 |
| 沙箱 VM 池 | 100-300MB | 视运行中的脚本而定 |
| 制品与流式缓冲 | 50-150MB | 全程流式，不整读大文件 |
| **小计（不含端侧模型）** | **≈ 400MB-900MB** | 目标 P95 < 900MB |
| 端侧模型（若启用） | 1.5-5GB | 按档位；**启用时其他部分必须让位** |
| **总计上限** | 见下 | 超过系统限制会被杀掉 |

**内存压力应对（分级降级）**：

| 信号 | 动作 |
|---|---|
| `didReceiveMemoryWarning` | 立即卸载端侧模型、释放 L2 向量索引、清空制品缓存、暂停后台索引 |
| `ProcessInfo.thermalState == .serious` | 停止端侧模型推理与后台重活，只保留云端调用与轻量工具 |
| `.critical` | 暂停一切后台工作，UI 提示"设备过热，任务已暂停" |
| 前台内存接近上限 | 主动结束最低优先级的沙箱实例与 Job |

**一个必须承认的事实**：在 8GB 设备上同时跑"端侧 4B 模型 + WASM 沙箱 + 大仓库索引"是不现实的。**Rune 的做法是让这些能力互斥调度**：端侧模型在跑时，沙箱 Job 必须等待或降级；索引构建必须推迟。

### 4.2 性能预算（端侧）

| 项 | 目标 | 备注 |
|---|---|---|
| Apple FM 单次分类/摘要延迟 | ≤ 500ms | 用于 Triage 与标题 |
| 本地 LLM 首 token（3-4B，4bit） | ≤ 1.5s | 含预填充 |
| 本地 LLM 生成速度 | ≥ 15 tok/s | 低于 10 tok/s 时应提示用户"建议改用云端" |
| 端侧 embedding（系统） | ≥ 200 段/秒 | 用于索引与记忆 |
| 端侧模型加载（3-4B） | ≤ 4s | 冷加载；预热后为 0 |
| 端侧推理内存峰值 | ≤ 模型体积 × 1.4 | KV cache + 激活开销 |

### 4.3 电量与热

| 场景 | 目标 |
|---|---|
| 纯云端调用任务（10 分钟） | ≤ 2% 电量 |
| 纯本地工具任务（10 分钟，无 LLM） | ≤ 1.5% |
| 端侧 LLM 持续生成 | **≤ 0.6%/分钟**（这是最耗电的操作，必须限制） |
| 端侧 LLM 单次任务总时长上限 | 默认 3 分钟（超时自动建议切云端或暂停） |
| 后台累计电量预算 | ≤ 15%/天（超过则只做本地零耗操作） |

**散热策略**：端侧推理默认使用较短的单次生成（≤ 512 token 输出），长文本生成拆成多段并穿插其他工作，避免持续满载触发降频。

### 4.4 实测基线与可用的模型尺寸（决定我们能承诺什么）

以下是核实到的实测数据（iPhone 17 Pro，第三方基准）：

| 方案 | 吞吐 | 备注 |
|---|---|---|
| MLX · Qwen3-0.6B-4bit | **158.8 tok/s** | 小模型极快 |
| LiteRT-LM · Gemma-4-E2B QAT | **61.1 tok/s** | 权重约 **497MB** |
| MLX · Gemma-4-E2B | 49.1 tok/s | |
| **Core AI（ANE）· Gemma-4-E2B** | 47.1 tok/s | ANE 路径 |
| llama.cpp（Metal）· Gemma-4-E2B Q4_K_M | 38.8 tok/s | |

**热墙（600 秒持续生成）**：

| 路径 | 掉速 |
|---|---|
| GPU（Metal/MLX） | **掉 50-62%** |
| **ANE（Core AI）** | **仅掉 33%** |

→ **结论：能放 ANE 就放 ANE**（Core AI 的 `ComputeUnitKind` 优先选 ANE），这直接决定"端侧能不能长时间干活"。

**内存天花板（硬数字）**：

| 设备 | `os_proc_available_memory()` |
|---|---|
| iPhone 13 Pro（6GB 物理内存） | **3.12 GB** |
| 同上 + `kernel.increased-memory-limit` + `extended-virtual-addressing` | **4.20 GB** |

- 社区实测：**单模型超过约 5GB 就装不下**；有报告称 **iPadOS 26.4 把 8GB iPad 的单 App 上限从 6GB 降到 3GB** `[不确定]`
- ⇒ **安全区是 ≤2-3B 参数的 Q4 模型（1-2GB 权重）**

**因此 Rune 的端侧模型承诺必须收窄为**：

| 档位 | 模型尺寸 | 可行性 |
|---|---|---|
| ✅ 推荐 | 0.6B - 2B（Q4，约 0.5-1.5GB） | 流畅（50-160 tok/s），可与沙箱共存 |
| ⚠️ 可用 | 3-4B（Q4，约 2-2.5GB） | 可用（20-40 tok/s），但必须与沙箱互斥调度 |
| ❌ 不承诺 | ≥8B | 超出内存天花板，或在热墙下变为不可用 |

**许可提示**：**Qwen 系列为 Apache-2.0（最干净）**；Gemma 4（2026-04）已转为 **Apache-2.0**；Llama 3.2 为社区许可。**内置推荐模型优先选 Apache-2.0**，避免许可争议。

### 4.5 后端成熟度评级（决定先做什么）

| 后端 | 评级 | 说明 |
|---|---|---|
| Apple Foundation Models（端侧） | ✅ 生产可用 | 但 4096 上下文 + 无代码执行 API |
| Core AI（`.aimodel`） | ⚠️ **仅实验** | iOS 27 新框架，存在 **KV 深度墙（2048 即可能触发 jetsam）** → **不作为 1.0 的依赖** |
| MLX Swift | ✅ **自研首选** | 模型族最广、4/8-bit affine、有 wired-memory 管理；**模拟器不可用**（必须真机） |
| llama.cpp（GGUF） | ✅ 引擎可用、胶水需自研 | **GGUF 走 mmap，footprint ≠ resident**（内存账本要按此计算） |
| Core ML 手写转换 | ⚠️ 需自研兜底 | 3+ StateType 在 ANE 上会结构性损坏 |
| ExecuTorch / MLC-LLM | ⚠️ 仅实验 | 不排期 |
| ONNX Runtime GenAI | ❌ 不可行 | 无 Swift API |

**排期结论**：1.0 的端侧路径是 **Apple FM（默认）+ MLX Swift（BYO 模型）**；Core AI 与 llama.cpp 作为 M4 之后的增强项。

## 5. 端侧路由：七类"神经反射"

| 反射 | 输入 | 输出 | 为什么端侧 |
|---|---|---|---|
| **R1 Triage** | 用户输入 + 会话简述 | 任务类型（问答/单步/多步/危险）+ 是否需要计划 | 每次交互都要跑，云端成本占比高；且**用户输入本身最敏感** |
| **R2 会话标题** | 首轮对话 | ≤ 12 字标题 | 纯装饰性成本，不该花钱 |
| **R3 摘要与压缩（L2）** | 历史轮次 / 工具结果 | 结构化要点（见 [07 §5.2](07-上下文与记忆引擎.md)） | 压缩调用频繁，云端成本高 |
| **R4 脱敏判定** | 即将发送的内容 | 命中的敏感片段 + 替换建议 | **敏感内容必须先本地判定**，不能先发出去再判断 |
| **R5 变更说明** | diff | 一句话"这行为什么改" | 用户在手机上高频使用；延迟要求高 |
| **R6 离线兜底** | 完整任务 | 受限但可用的 Agent 循环 | 断网可用是核心卖点 |
| **R7 内容过滤（合规必需）** | 即将展示给用户的自然语言输出 | 违规判定 + 处理动作 | **Apple Guideline 1.2 要求过滤必须实现在二进制内**，不能依赖上游模型厂商的过滤器（[11 §4](11-AppStore合规与分发.md)）。这条必须端侧跑，否则既不合规也来不及 |

### 5.1 "够用判定"（何时必须升级到云端）

端侧模型只在一个反射上"够用"时才使用；否则**直接走云端**，不做无效尝试：

| 判定条件 | 阈值 |
|---|---|
| 输入长度 | ≤ 端侧窗口的 50% |
| 需要工具调用 | 工具数 ≤ 3 且参数简单（无长文本参数） |
| 输出长度 | ≤ 512 token |
| 任务类型 | 属于 R1-R7 白名单 |
| 历史长度 | ≤ 端侧窗口的 40% |
| 置信度（模型自评或格式校验） | 结构化输出通过 schema 校验 |

**任一不满足 → 直接路由到云端**（并在事件日志里记录"因 X 升级到云端"，便于调优）。

### 5.2 离线模式的真相（含 Apple FM 的 4096 硬上限）

**必须先承认一个事实**：Apple Foundation Models 的端侧会话窗口是 **4096 token**，且 **Instructions、全部提示、工具 schema 及其输入输出、`@Generable` 的 schema 与响应全部计入**；Apple 建议**工具数不超过 3-5 个**；超限会抛 `exceededContextWindowSize`，**该会话随后完全无法响应**。

**结论：4096 token 装不下一个完整的自由 Agent 循环**（光工具 schema 与系统指令就会吃掉大半）。因此"离线闭环"不能靠"让端侧小模型自由发挥"，而必须分成三种形态：

| 离线形态 | 谁在编排 | 端侧模型做什么 | 能达到什么 |
|---|---|---|---|
| **L1 反射模式** | 不涉及（无任务执行） | 分类 / 摘要 / 脱敏 / 标题 / 内容过滤 | 只有"非 Agent 能力"：读文件、看状态、回答问题 |
| **L2 引导模式（离线主力）** | ⭐ **确定性运行时**（本地计划执行器，不依赖模型） | 只在分支点做**极小决策**（三选一）与生成短文本（commit message） | **能完成结构化多步任务**（限内置配方覆盖的场景） |
| **L3 自由模式**（仅 C/D，大内存设备 + 已下载模型） | 端侧大模型（8k-32k 上下文） | 完整 Agent 循环 | 接近云端体验（质量略降） |

**L2 的具体做法（这是本设计中最重要的一条离线策略）**：

- 用户使用**内置 Workflow / Skill 骨架**（声明式，不需要模型当场生成计划）
- 运行时按骨架逐步执行工具；**只在"分支点"把极小的问题交给端侧模型**
- 每次端侧调用的预算硬约束：**输入 ≤ 512 token、输出 ≤ 64 token、选项 ≤ 3 个**

```
Step 1  跑 pytest                                 ← 本地执行，不用模型
Step 2  解析失败用例与堆栈                        ← 本地正则，不用模型
Step 3  失败原因属于哪一类？                       ← 唯一一次模型调用
          A) 断言值不符   B) 导入/依赖错误   C) 超时
          （输入：失败摘要 ~300 token；输出：一个字母）
Step 4  按类别套用预置修复配方                    ← 声明式 Skill，不用模型
Step 5  重新跑测试并比对                          ← 本地执行
Step 6  生成 commit message                       ← 端侧模型（输入 diff 摘要 ~400 token）
```

**收益**：① 完全绕开 4096 限制；② 端侧模型只做它真正擅长的小判断；③ 可预测、可复现、可回放测试；④ 电量与延迟都极低；⑤ **用户看到的是一条真实可用的离线任务流，而不是一个会胡说的小模型**。

**这是"手机上离线可用"唯一诚实且可行的形态**——而不是"端侧跑一个 4B 模型假装自己是 Claude Code"。

### 5.3 在 4096 token 里正确使用 Apple Foundation Models

| 约束 | 应对 |
|---|---|
| 窗口 4096，Instructions 也计入 | Instructions 压到 ≤ 200 token；不放"人格描述"，只放"输出格式契约" |
| 工具 schema 计入且贵 | **每次会话只挂 1-3 个工具**；不同反射用不同的 `LanguageModelSession`，不要试图一个会话搞定所有事 |
| 建议工具数 ≤ 3-5 | 把 45 个工具切成"反射专用小工具集"，按需选择 |
| `@Generable` schema 也计入 | 结构体字段越少越好；用枚举代替自由文本 |
| 超限后会话报废 | **每次反射用一个新会话**（建会话成本低），绝不复用长会话 |
| 无"系统提示"概念 | 用 `Instructions`；不要指望它像云端那样有强约束力 |
| 上下文大小可查 | iOS 26.4+ 有 `.contextSize`，可用 `.tokenCount(for:)` 做**装前检查**（超出就不要发，直接升级到 PCC/云端） |
| 不支持的设备 | `.availability == .unavailable(.deviceNotEligible / .modelNotReady)` → 自动降级到 PCC 或提示用户配置渠道 |
| ⚠️ **中文用户的隐形缩水** | 英文约 **3-4 字符/token**，但**中日韩约 1 字符/token** → **4096 的窗口对中文实际只有约 2-3 千字**。这意味着：中文项目的反射提示必须**比英文再压缩一半**；代码与中文混排时要按"最坏情况"估算 |

**iOS 27 带来的新能力（要尽早用上）**：`ToolCallingMode`（`.allowed` / `.disallowed` / `.required`）、`DynamicProfile` / `DynamicInstructions` / `historyTransform`、**Vision 输入**、内置 OCR / 条形码工具、**Spotlight 支持的本地 RAG 检索工具**、每会话 usage 统计。
其中 **`historyTransform` 与 `DynamicInstructions` 对我们价值最大**：它们让我们能在有限窗口内做"上下文裁剪"，而不必重建会话。
**并且：Foundation Models 框架已开源，并定义了开放的 `LanguageModel` 协议（已有 Core AI / MLX / Anthropic / Google 的实现）** —— Rune 的网关应当**实现/适配该协议**（见 [06 §11](06-模型网关与中转站.md)），这样我们的 Provider 能被系统与其他 App 复用，也能直接吃到 Apple 的抽象演进。

### 5.4 离线可用性矩阵

```
无网络检测（NWPathMonitor）
  ├─ 端侧后端：优先 A；不足则 C/D（若已下载）；都没有 → L1 反射 + 提示
  ├─ 能力矩阵：
  │    · 完全可用：读/写/编辑文件、原生搜索、Git 本地操作、沙箱脚本、测试运行、
  │              L2 引导模式下的内置配方任务、端侧摘要/分类/过滤
  │    · 受限：需要模型自由规划的任务（降级为 L2 或提示"联网后可用"）
  │    · 不可用：网页搜索/抓取、云端模型（含 PCC 在无网时也不可用）、PR 创建、需联网的 MCP
  ├─ UI：顶部细条"离线中 · 引导模式（能力受限）"，并给出"恢复网络后自动补做"的选项
  └─ 排队：需要联网才能完成的步骤记入"待联网队列"，恢复后询问是否补做
```

**离线指标（已按事实修正）**：

| 指标 | 目标 |
|---|---|
| **L2 引导模式**完成"改一个函数 + 跑测试 + 写 commit"（限内置配方覆盖的任务） | ≥ 90% |
| **L3 自由模式**完成同类任务（仅大内存设备 + 已下载模型） | ≥ 70% |
| **不承诺** | 无网络时用端侧小模型完成任意开放任务 |

## 6. 端侧 vs 云端的决策矩阵（实现用）

```swift
func selectModel(for task: TaskDescriptor, env: RuntimeEnvironment) -> ModelSelection {
    // 1. 硬约束：离线 / 敏感项目 / 用户强制端侧
    if env.isOffline || task.project.requiresLocalOnly || task.forceLocal {
        return localOrFail(task, env)
    }
    // 2. 神经反射：白名单 + 够用判定
    if let reflex = task.reflexKind, env.localAvailable, reflex.isWithinLocalCapacity(task) {
        return .init(provider: env.localProvider, reason: "本地反射 \(reflex)")
    }
    // 3. 任务类型路由表（用户可配）
    if let route = env.routes.match(task.kind, cost: env.remainingBudget) {
        return route.selection
    }
    // 4. 兜底
    return env.defaultCloudSelection
}
```

**每次选择都要记录理由**（`ModelSelected` 事件带 `reason`），这样用户可以回答"为什么这次用了这个模型"，我们也能持续优化策略。

## 7. 隐私收益的量化（值得展示给用户）

端侧反射直接减少外发内容。可量化的展示：

```
本周本机模型承担了 1,284 次调用
├ 其中 863 次（67%）包含了你的文件内容或输入原文
├ 这些内容没有离开这台设备
└ 若改用云端，预计多花 $0.94，并外发约 412k token

已脱敏后外发：21 处（手机号 12、内网域名 6、密钥 3）
```

**这是"端侧执行"这件事唯一能被用户看见的价值形式。** 不展示，用户就感觉不到差异。

## 8. 端侧模型的加载与生命周期

```
                    用户开启"本机模型"
                            │
              ┌─────────────┴──────────────┐
              ▼                            ▼
      权重未下载（B/C）              已就绪（A 或已下载）
              │                            │
   显示体积与内存需求 → 用户确认        冷加载（≤4s，显示进度）
              │                            │
       下载（Wi-Fi，可暂停，校验哈希）      ▼
              └───────────────▶      热态（可服务请求）
                                       │
                    ┌──────────────────┼──────────────────┐
                    ▼                  ▼                  ▼
            3 分钟无请求         收到内存警告        切换 App 到后台
            或低电量模式                            （超 5 分钟）
                    │                  │                  │
                    └──────────────────┴──────────────────┘
                                       ▼
                                 卸载（释放内存）
```

**加载互斥**：加载端侧模型期间，暂停沙箱 Job 与索引构建（避免峰值内存叠加）。

## 9. 下载权重、编译与合规（重要，结论已被核实）

### 9.1 下载权重 ≠ 下载代码

Apple 2.5.2 禁止的是"下载、安装或**执行**会引入或改变 App 功能的**代码**"。模型权重是**数据**，且业界已有大量在架先例（LLM 客户端、以及官方支持的 Core AI `.aimodel` / MLX 模型分发）。因此：

| 规则 | 说明 |
|---|---|
| 只加载**已知格式** | `.aimodel`（Core AI）/ safetensors（MLX）/ GGUF（llama.cpp） |
| **不执行模型文件中携带的任何自定义代码** | 不加载自定义算子插件、不以模型文件作为代码源；`.aimodel` 只作为数据资源加载 |
| 校验 | 下载后校验哈希与来源；只从我们维护的清单或用户显式指定的 URL 获取 |
| 审核说明 | 明确写"only model weight data is downloaded; no code is downloaded or executed" |
| **CI 静态检查** | 保证"下载模型"这条路径**不会**与任何执行路径相连（[11 §3.3](11-AppStore合规与分发.md)） |

### 9.2 无 JIT 下的性能路径（这是 iOS 的硬约束）

**iOS 不存在通用 JIT 权限**（`allow-jit` 是 macOS 专属；唯一的官方 JIT 通道是 EU 限定的浏览器引擎 entitlement，Agent 不可用）。因此本地模型的加速必须靠：

| 手段 | 说明 |
|---|---|
| **AOT 预编译** | Core AI 的 CLI 工具可把模型预编译为 `.aimodel` 资源 → **这是 iOS 上"编译一次、运行多次"的正道**，也恰好与 [05 §3.1](05-工具系统与执行沙箱.md) 的 WASM AOT 思路同构 |
| 量化 | 4bit 权重 + 可选 KV cache 量化 |
| **ANE 卸载** | Core AI 明确支持 CPU/GPU/Neural Engine；优先把算子放到 ANE 以省电 |
| 批处理 | 索引/embedding 走批量推理，减少 kernel 启动开销 |
| 互斥调度 | 推理期间不跑沙箱重活（避免 GPU/内存争抢） |

### 9.3 大文件下载体验

后台传输（`URLSession` background）+ 断点续传 + 校验；Wi-Fi 优先；可在"充电 + Wi-Fi"条件下自动下载；存储标记为**不备份**（可重新下载）；总量配额（默认 8GB），超限提示清理。

**默认不下载任何权重**：Apple 自家栈（A/B）让用户开箱即得端侧能力，**不需要下载**——这也是选它做默认后端的核心理由之一。

## 10. 性能基准与验收

| # | 基准 | 目标 | 失败处理 |
|---|---|---|---|
| 1 | 冷启动到可输入 | ≤ 600ms P90 | 端侧模型**绝不参与**启动路径 |
| 2 | 前台普通 Turn 内存峰值 | ≤ 900MB P95 | 检查索引与制品缓存 |
| 3 | 启用 3-4B 端侧模型后内存峰值 | ≤ 3.2GB（8GB 设备） | 提高量化等级 / 降低上下文 / 互斥调度 |
| 4 | 端侧 Triage 延迟 | ≤ 300ms P95 | 若超，改用更小的提示或规则引擎兜底 |
| 5 | 端侧标题生成 | ≤ 800ms，不阻塞主流程 | 异步生成，先显示"新会话" |
| 6 | 本地 LLM 生成速度 | ≥ 15 tok/s（3-4B 4bit） | 低于 10 时 UI 提示建议用云端 |
| 7 | 端侧推理电量 | ≤ 0.6%/分钟 | 降低单次输出上限 |
| 8 | 离线闭环成功率 | ≥ 90%（简单任务） | 缩小离线承诺范围 |
| 9 | 内存警告后恢复 | ≤ 2s 内完成卸载并回到可用状态 | 修正卸载路径 |
| 10 | 索引构建（1k 文件） | ≤ 5 分钟（后台、充电） | 降低分块数 / 延后 |
