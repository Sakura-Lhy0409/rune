# 03 · 总体架构

> **摘要**：Rune 是**单进程、多 Actor、事件溯源**的架构。整个 App 只有一个 Swift 进程（加上系统强制的扩展进程），Agent 运行时是一组 `actor`，UI 是这些 Actor 事件流的纯函数投影。三条独立数据流：**推理流**（网络 ⇄ Gateway ⇄ Runtime）、**执行流**（Runtime ⇄ 沙箱 ⇄ VFS）、**事实流**（一切 → 事件日志 → UI/记忆/审计）。

---

## 1. 分层视图

```
┌─────────────────────────────────────────────────────────────────────────┐
│ L5  交互层 RuneUI                                                        │
│   SwiftUI 场景 · 卡片/时间轴/Diff 审阅 · 语音 · 手势 · 键盘扩展             │
│   App Intents / Siri / Shortcuts / Share Extension / Widget / Live Activity│
├─────────────────────────────────────────────────────────────────────────┤
│ L4  编排层 RuneCore                                                      │
│   AgentRuntime(actor)  Turn 状态机 · 规划 · 调度 · 预算 · 熔断             │
│   GoalEngine · JobEngine · WorkflowEngine(JSC) · SubagentPool             │
│   SkillRegistry · HookEngine · PolicyEngine · ApprovalBroker              │
├──────────────────┬───────────────────┬──────────────────────────────────┤
│ L3a RuneContext  │ L3b RuneGateway   │ L3c RuneTools                    │
│  上下文装配器     │  协议族适配器      │  ToolRegistry                    │
│  压缩器/摘要器    │  流式解复用        │  CapabilityToken 校验            │
│  混合检索         │  路由/降级/重试    │  工具实现（原子工具 + 沙箱桥）      │
│  三层记忆         │  成本账本/配额     │  MCP 客户端                      │
├──────────────────┴───────────────────┴──────────────────────────────────┤
│ L2  执行层 RuneBench                                                     │
│   RuneVM (WASI 解释器) · VFS(写时复制/快照) · JS 宿主桥 · 原生能力桥        │
│   资源限额器(CPU/内存/写入/时长/出口) · 进程内调度队列                      │
├─────────────────────────────────────────────────────────────────────────┤
│ L1  基础层 RuneStore / RuneNet / RuneCrypto / RuneLog                    │
│   SQLite(WAL, FTS5, sqlite-vec) · 事件日志 · 检查点                        │
│   URLSession + SSE 复用器 + 断流续传 · Keychain/Secure Enclave · 脱敏      │
└─────────────────────────────────────────────────────────────────────────┘
                              ⇅ HTTPS（唯一出口）
        OpenAI · Anthropic · Gemini · DeepSeek · 兼容端点 · 中转站 · 局域网
```

**依赖方向严格单向向下**：L5 可以依赖 L4/L1，L4 可以依赖 L3/L2/L1，**L1/L2 绝不反向依赖**。跨层通信一律通过协议 + 事件，不用单例、不用 NotificationCenter 传业务数据。

## 2. 进程与线程模型

### 2.1 进程清单（iOS 强制的形态）

| 进程 | 必需性 | 职责 | 内存预算 |
|---|---|---|---|
| **主 App** | 必需 | 全部 Agent 运行时、沙箱、UI | 设备相关（见 [13](13-端侧模型与性能预算.md)） |
| **Share Extension** | 必需 | 接收分享内容，落库后**立即退出**，用 URL Scheme 唤起主 App 接力 | ≤ 120MB（系统限制） |
| **Keyboard Extension** | 可选（后续） | 在任意输入框内唤起 Rune 生成文本 | ≤ 60MB 量级，**绝不加载运行时** |
| **Widget Extension** | 必需 | 只读展示 + 一键触发（App Intent） | ≤ 30MB |
| **Live Activity** | 必需 | 由主 App 通过 ActivityKit 更新，无常驻进程 | — |
| **File Provider Extension** | 可选 | 把 Rune 工作区暴露给"文件"App | ≤ 100MB 量级 |
| **Intents Extension** | 可选 | 后台响应 Siri/快捷指令 | 短生命周期 |

**铁律：Agent 运行时只存在于主进程。** 所有扩展都是"薄壳"——采集输入、写事件、拉主进程、或展示只读结果。任何在扩展里跑模型的尝试都是错的（内存不够、会被杀）。

**长任务的唯一合法载体是主进程 + `BGContinuedProcessingTask`**（iOS 26+）：由用户在前台发起，可在后台继续"数分钟或更久"，允许联网与密集 CPU，进度以**系统 Live Activity** 呈现且用户可随时取消。**这是 Rune"任务在后台继续跑"的全部实现基础**（详见 [10 §3.1](10-后台执行与可靠性.md)）。它同时带来一条 entitlement 约束：后台使用 GPU / Neural Engine 需要 `.continued-processing.gpu` / `.continued-processing.inference`，未获批时必须在后台自动降级到 CPU 或暂停端侧推理。

### 2.2 并发模型（Swift 6 严格并发）

```
MainActor
  └─ RuneUI（视图状态 = 事件流的投影）
        ↑ AsyncStream<RuntimeEvent>（单一事件通道）
        │
Actor 岛（各自串行，通过 async 消息通信，不共享可变状态）
  ├─ AgentRuntime        会话唯一所有者；Turn 状态的唯一真相源
  ├─ TurnScheduler       工具调度、并发度控制、超时与取消
  ├─ GatewayRouter       渠道选择、降级、配额
  ├─ StreamDemux         每路 SSE 一个 actor，负责增量解析与背压
  ├─ BenchSupervisor     VM 实例池、资源限额、超时强杀
  ├─ VFS                文件事务、快照、回滚
  ├─ EventLog            事件追加（唯一写入 SQLite 的入口）
  ├─ ContextAssembler    上下文窗口预算分配与压缩
  ├─ MemoryIndex         检索（FTS5 + 向量）
  ├─ CostLedger          成本/电量/配额记账
  └─ ApprovalBroker      审批请求与决策（含"记住这次选择"）
专注队列（非 Actor，受控并行）
  ├─ WASM 执行队列       并发度 = min(4, 性能核数)
  ├─ 网络队列            URLSession 自带
  └─ 检索队列            并发度 2
```

**四条不可违反的并发规则：**

1. **只有 `AgentRuntime` 能改变 Turn 状态**。其他 Actor 发意图（intent），不收状态。
2. **所有跨 Actor 传递的类型必须 `Sendable`**；工具结果一律走值类型（`struct`），不传引用。
3. **取消是协作式的**：每个长操作循环里检查 `Task.isCancelled` 与 `BudgetExceeded`，不用 `Thread.cancel`。
4. **UI 永不阻塞在运行时上**：UI 只消费事件流；任何"我要拿当前状态"的请求都走"事件流重放 + 快照"。

```

│  ├─ RuneVM/              # WASI 解释器、模块缓存、AOT 热点、资源限额

│  ├─ RuneCore/            # AgentRuntime、Goal、Job、Workflow、Skill、Hook、Policy
│  ├─ RuneTools/           # 工具实现集合（依赖 RuneBench + RuneCore 协议）
│  ├─ RuneMCP/             # MCP 客户端与服务端
│  └─ RuneUI/              # 可复用视图组件（不依赖 App target）
├─ Apps/
│  ├─ Rune/                # 主 App（薄：组装依赖 + 场景）
│  ├─ RuneWidgets/
│  ├─ RuneShare/
│  └─ RuneIntents/
```

## 4. 三条数据流

### 4.1 推理流（模型 ⇄ 客户端）

```
ContextAssembler ──ChatRequest(归一化)──▶ GatewayRouter
                                            │ 选渠道（策略+配额+健康）
                                            ▼
                                       ProviderAdapter
                                            │ 厂商协议（SSE）
                                            ▼
                                       StreamDemux
              ┌─────────────────────────────┴───────────────────────┐
              │ 增量产出：TextDelta / ReasoningDelta / ToolCallDelta │
              │ （工具调用参数按 index 拼接，直到 finish_reason）      │
              └─────────────────────────────┬───────────────────────┘
                                            ▼
                              AgentRuntime（组装完整 assistant turn）
```

要点：
- **协议差异全部在 `ProviderAdapter` 内消化**，`AgentRuntime` 只见归一化类型（见 [06](06-模型网关与中转站.md)）。
- **SSE 解析必须容错**：厂商会发心跳、注释行、非标准 `event:`、跨 chunk 断开的 JSON。`StreamDemux` 用增量字节缓冲 + 逐事件边界解析，绝不"攒完再 parse"。
- **断流可续**：记录已收字节数与最后事件 id；重连时优先用厂商支持的原生续传，否则**重发请求但把已生成的文本作为 prefix 注入**（`prefill`/`assistant prefix` 策略），避免重复计费与重复输出。

### 4.2 执行流（运行时 ⇄ 沙箱）

```
ToolCall(归一化) ──▶ PolicyEngine 判定（信任刻度盘 + 能力令牌 + 策略文件）
                        │
        ┌───────────────┼────────────────┬──────────────────┐
        ▼               ▼                ▼                  ▼
  允许直接执行      需要审批          直接拒绝          需要脱敏后外发
        │               │                │                  │
        └──────▶ ApprovalBroker ─────────┘                  │
                        │（用户决策，可"记住并写策略"）          │
                        ▼                                   │
                  BenchSupervisor                           │
        ┌───────────────┼────────────────┐                  │
        ▼               ▼                ▼                  ▼
    RuneVM(WASI)   JSC 宿主桥      原生能力桥           RuneNet
   sh/py/node/git   JS 脚本        Files/Photos/...     出口白名单校验
        └───────────────┴────────────────┘
                        ▼
                 ToolResult（截断 + 摘要 + 制品引用）
                        ▼
                   EventLog（不可变事实）
```

**关键设计：工具结果永不完整回灌上下文。** 大输出（日志、文件、搜索命中）走"制品（Artifact）"：磁盘留存全文，上下文里只放**摘要 + 结构化切片 + 制品句柄**，模型需要更多时用 `read_artifact(handle, range)` 主动拉取。这是手机上能处理大输出的唯一办法（A6）。

### 4.3 事实流（一切 → 事件日志）

```
任何 Actor ──append(Event)──▶ EventLog(actor)
                                │ 单写者，追加式，WAL
                                ├─▶ UI 投影（AsyncStream → SwiftUI 状态）
                                ├─▶ 记忆索引（异步增量：文本 → embedding 任务队列）
                                ├─▶ 审计（出口请求、文件写入、密钥使用）
                                └─▶ 检查点锚点（Checkpoint = 事件序号 + VFS 快照 id）
```

**事件是不可变的**：任何"修正"都是新事件（`PlanRevised`、`TodoStatusChanged`、`ToolResultAmended`），永不原地改写。好处：时间轴回滚、分叉、审计、崩溃恢复到最后一个事件，全部免费获得。

## 5. 核心协议（Swift 签名草案）

```swift
// MARK: - RuneKernel：零依赖的事实层

public enum Role: String, Sendable, Codable { case system, user, assistant, tool }

public struct ContentBlock: Sendable, Codable {
    public enum Kind: Sendable, Codable {
        case text(String)
        case image(ref: ArtifactRef, mime: String)      // 端侧压缩后引用，不塞 base64
        case reasoning(String, signature: Data?)         // 各家 thinking/CoT 归一化
        case toolCall(ToolCall)
        case toolResult(ToolResult)
        case artifact(ArtifactRef)                       // 大输出/生成物句柄
    }
    public var kind: Kind
    public var origin: TrustLevel      // .system / .user / .model / .untrustedContent
}

public struct ToolCall: Sendable, Codable, Identifiable {
    public let id: String                 // provider 侧 id（跨轮引用必需）
    public let name: String
    public let argumentsJSON: Data        // 原始 JSON，延迟解码（部分厂商会流式半成品）
}

public struct ToolResult: Sendable, Codable {
    public let callID: String
    public let status: Status             // .ok / .error / .denied / .timeout / .truncated
    public let summary: String            // 给模型看的压缩文本（≤ 预算）
    public let artifacts: [ArtifactRef]   // 全文另存
    public let metrics: Metrics           // 耗时、字节数、退出码、成本
}

public struct Capability: Sendable, Codable {
    public var paths: [PathScope]         // 允许读/写的路径前缀（含 .readOnly / .write）
    public var egress: [EgressRule]       // 允许的域名与方式（含"仅 GET"）
    public var nativeAPIs: Set<NativeAPI> // photos / calendar / location / contacts / health
    public var expiresAt: Date
    public var maxCalls: Int?
    public var requiresBiometric: Bool
}
```

```swift
// MARK: - RuneCore：运行时

public actor AgentRuntime {
    public func submit(_ input: UserInput, into session: SessionID) async throws -> TurnID
    public func steer(_ turn: TurnID, with: UserSteer) async throws     // 转向
    public func interrupt(_ turn: TurnID, mode: InterruptMode) async    // .soft / .hard
    public func resume(_ turn: TurnID) async throws                     // 唤醒后续跑
    public nonisolated var events: AsyncStream<RuntimeEvent> { get }
}

/// ⭐ 战略机会：Foundation Models 框架已于 iOS 27 开源，并定义了开放的 `LanguageModel` 协议
/// （已有 Core AI / MLX / Anthropic / Google 的实现）。Rune 的 Provider 应实现/适配该协议，
/// 这样我们的渠道（含中转站）能被系统与其他 App 复用，也能直接吃到 Apple 的抽象演进。
/// 注意：Apple 的协议是"最小公共集"，Rune 的内部协议仍是超集（保留缓存语义、思考链回传策略、
/// 渠道 quirk 等 Apple 协议不表达的字段）。
public protocol ModelProvider: Sendable {
    var id: ProviderID { get }
    var capabilities: ProviderCapabilities { get }       // 流式/工具/多模态/缓存/思维链
    func send(_ req: ChatRequest) -> AsyncThrowingStream<ModelEvent, Error>
    func countTokens(_ msgs: [ContentBlock]) async throws -> Int
    func listModels() async throws -> [ModelDescriptor]
}

public protocol Tool: Sendable {
    static var spec: ToolSpec { get }                    // 名称、描述、JSON Schema
    var requirements: Set<CapabilityKind> { get }        // 声明所需能力（用于策略判定）
    func call(_ args: ToolArguments, in ctx: ToolContext) async throws -> ToolResult
}
```

```swift
// MARK: - RuneBench：执行沙箱

public protocol VFS: Sendable {
    func open(_ path: VFSPath, mode: OpenMode) async throws -> FileHandleRef
    func read(_ path: VFSPath, range: Range<Int64>?) async throws -> Data
    func write(_ path: VFSPath, data: Data, atomic: Bool) async throws
    func list(_ path: VFSPath, recursive: Bool, limit: Int) async throws -> [DirEntry]
    func stat(_ path: VFSPath) async throws -> FileStat
    func snapshot() async throws -> SnapshotID                 // 写时复制快照
    func restore(_ snapshot: SnapshotID, paths: [VFSPath]?) async throws
}

public protocol Sandbox: Sendable {
    func run(_ invocation: Invocation, limits: ResourceLimits) async throws -> ExecutionResult
}
// 三个实现：WASMSandbox(sh/python/node/git/rg)
//           JSSandbox(JavaScriptCore)
//           NativeSandbox(系统框架能力，无代码执行)
```

**注意 `VFS.snapshot()`**：这是"每次工具调用可回滚"的地基。实现用 APFS 的 `clonefile`（同卷秒级、零拷贝）或回退到"只记录本次写入的原始字节"（写前日志）。见 [05](05-工具系统与执行沙箱.md) §7。

## 6. 依赖注入与构建配置

### 6.1 组装根（唯一）

```swift
public struct RuneContainer: Sendable {
    public let store: EventLog
    public let vfs: VFS
    public let bench: BenchSupervisor
    public let gateway: GatewayRouter
    public let context: ContextAssembler
    public let runtime: AgentRuntime
    public let policy: PolicyEngine
    public let approvals: ApprovalBroker

```

三种容器（live / preview / test）是"UI 可测 + Agent 可回放"的全部秘密。

### 6.2 双构建配置

| 配置 | 用途 | 差异 |
|---|---|---|
| `AppStore` | 上架版 | 关闭 JIT；WASM 走解释器 + 打包 AOT 热点；插件仅声明式；出口策略更保守；审核模式开关 |
| `Full` | 自签/企业/TestFlight 内部/EU 替代市场 | 可开启 AOT 全量、附加本地网络发现、附加"仅本地模型"默认档、附加开发者审计面板 |
| `Debug` | 开发 | 大量断言、事件全量落盘、假模型（cassette 回放）、时间加速器（把 30s 后台窗口虚拟成 30 分钟测续跑） |

**编译期开关**用 Swift 条件编译 + 运行时能力探测双保险：

```swift
enum FeatureGate {
    static var wasmAOT: Bool { BuildConfig.isFull && DeviceCapability.supportsAOT }
    static var declarativePluginsOnly: Bool { BuildConfig.isAppStore }
}
```

## 7. 错误模型

统一的错误分类，决定"谁来处理"：

| 类别 | 例子 | 处理者 | 用户可见性 |
|---|---|---|---|
| `Transient` | 网络抖动、429、5xx、超时 | GatewayRouter 自动重试/降级 | 静默 + 轻提示 |
| `Budget` | token 超预算、电量低、成本熔断 | Runtime 暂停 Turn 并存检查点 | 卡片提示"已暂停，是否继续" |
| `Capability` | 越权访问、出口被拒、无授权目录 | PolicyEngine（直接拒绝，不重试） | 明确拒绝原因 + 一键申请授权 |
| `Approval` | 需要用户确认 | ApprovalBroker | 审批卡 |
| `Sandbox` | 脚本崩溃、超时、内存超限 | BenchSupervisor（含强杀） | 折叠的错误详情 + 重试按钮 |
| `Model` | 模型拒绝、工具名幻觉、参数不合 schema | Runtime（修正性重试：把错误回灌让模型自己改） | 折叠，可展开 |
| `Fatal` | 数据库损坏、密钥丢失 | 恢复流程 | 引导式修复 |
| `UserAbort` | 用户取消 | 正常路径，非错误 | 无需提示 |

**规则：`Model` 类错误至少要给模型一次自我修正的机会**（回灌 schema 校验错误），这是长任务成功率的关键差异之一（桌面 Agent 常在这里放弃）。

## 8. 架构决策记录（ADR 摘要）

| ID | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-01 | 沙箱用 WASI 解释器而非自研 shell 解释器 | 纯 Swift 写 sh 解释器 | 生态：python/node/git/rg 已有 wasm 构建；自研 shell 无法支撑真实任务 |
| ADR-02 | 单进程多 Actor，不做多进程 | XPC 拆分沙箱 | iOS 单进程是常态；进程拆分只增加内存与复杂度，不增加隔离（同沙箱） |
| ADR-03 | 事件溯源而非状态表 | 直接存消息表 | 断点续跑、时间轴、审计、同步四件事一次解决 |
| ADR-04 | 上下文里放制品句柄而非全文 | 大输出回灌 | 内存与成本（A6）；也让"引用了什么"可审计 |
| ADR-05 | 模型网关自己实现协议适配，不引入第三方 SDK | 直接用各家官方 Swift SDK | 官方 SDK 多数不存在或不支持全特性；且我们要统一 reasoning/缓存语义 |
| ADR-06 | 存储用 GRDB(SQLite) 而非 SwiftData | SwiftData/Core Data | 需要 FTS5、sqlite-vec、精细索引与迁移控制；SwiftData 在复杂查询与迁移上不够 |
| ADR-07 | Workflow 脚本用 JavaScriptCore | 自研 DSL / Lua | JSC 系统自带、无需打包、无需 JIT 也可用；生态（isomorphic-git 等）直接受益 |
| ADR-08 | 端侧模型只做"神经反射"不做主力 | 端侧跑 7B 干主力活 | 内存/电量/速度（见 [13](13-端侧模型与性能预算.md)）；主力仍走云端 API |
| ADR-09 | 不引入云端同步作为必需路径 | iCloud 强同步 | 隐私与离线优先；同步是可选增强（E2E 加密） |
| ADR-10 | 工具集"厚"而非"薄" | 只给 shell | 无 fork，shell 能力边界更窄；且厚工具更容易做策略与审批 |
