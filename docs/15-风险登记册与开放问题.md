# 15 · 风险登记册与开放问题

> **摘要**：这份文档的作用是**让项目死得明白**。每条风险都写明：概率、影响、早期信号（怎么在变严重之前发现）、缓解手段、以及"如果发生了我们怎么办"的降级方案。

---

## 1. 风险登记册

排序依据：`影响 × 概率`。P0 = 可能导致项目无法成立；P1 = 严重但可绕；P2 = 影响体验。

### P0 级（可能导致项目不成立）

| ID | 风险 | 概率 | 影响 | 早期信号 | 缓解 | 降级方案 |
|---|---|---|---|---|---|---|
| **R1** | **App Store 以 2.5.2（下载/执行代码）或 4.2 拒绝** | **中高 → 已上调** | 致命：无法通过主渠道分发 | ① 自家提交被拒并引用 2.5.2；② **2025-12 起 Apple 已阻止 Replit/Vibecode 更新，2026-03 两次下架 Anything，2026-06 收紧 4.3(b)** —— **方向明确是收紧**；③ Apple 公开表示引用的是 **2.5.2 + ADPLA §3.3.1(B)** | ① 双轨构建（App Store 版**零网络代码获取路径**）② **机械式清理**：二进制里不得含远程代码加载器（死代码也算）③ 不做 App 生成/自修改行为 ④ 完备的审核说明（[11 §8.1](11-AppStore合规与分发.md) 模板）+ 内置示例项目 ⑤ 借鉴先例话术（**a-Shell 已证明"随包 clang + WASM 运行时 + 用户编译执行"可上架**）⑥ **预置"移除下载能力"的降级开关**（[Q20](#3-开放问题需要产品负责人拍板)）—— shell/解释器类是**高波动审核品类**，要能在 24 小时内出一个合规构建 | **Xcode 自签**（唯一真正可用的 Full 轨）+ TestFlight 内测。**注意：企业分发是违约，EU 替代市场零能力增益**（[附录 B §8](附录B-技术选型核实表.md)），所以自签脚本必须在 1.0 前就绪 |
| **R1b** | **被 1.2（UGC）拒审** —— **2026 年最可能的实际拒审理由** | **中高** | 严重：延误上架 | 审核员长按 AI 回复找"举报"→ 找不到 | ① **在二进制内实现内容过滤**（不能依赖上游厂商过滤器）② 每条 AI 消息可举报 ③ 可屏蔽渠道/模型/人格 ④ 支持邮箱在 ASC 与 App 内都可见（[11 §4](11-AppStore合规与分发.md)） | 若被拒：按拒审意见补齐四项机制后重新提交（这是可修复项，不是死局） |

| **R3** | **后台续跑不可靠**（恢复后状态错乱、重复副作用） | 中 | 致命：用户不敢把长任务交给它 | 随机中断测试出现 1 次文件不一致；用户反馈"任务重复执行了推送" | ① 幂等工具契约（非幂等工具必须声明并默认不自动重做）② 事件日志 + 检查点 + 哈希链 ③ 每次 CI 跑 100 次随机 kill 一致性测试 ④ 危险的网络副作用一律要求重新确认 | 长任务改为"用户在场时跑"，Live Activity 只做通知不做续跑；把 Goal 的自动续跑默认关闭 |
| **R4** | **内存不足**（尤其启用端侧模型时被系统回收） | 中高 | 严重：崩溃、后台被杀、体验崩塌 | 内存峰值基准超 2.2GB；Instruments 中出现多次内存警告 | ① 端侧模型默认只在 ≥ 8GB 内存设备启用 ② KV cache 上限可配 ③ 全程流式、制品外置 ④ 收到内存警告立即释放索引与非活跃会话 ⑤ 端侧模型可在不活跃 3 分钟后卸载 | 端侧模型降级为"仅 Apple Foundation Models（系统托管，不占我们的内存）" |

| **R8** | **模型厂商 API 频繁变更导致渠道失效** | 高 | 中等：部分功能不可用 | 某渠道错误率突然升高；字段解析失败 | ① 协议适配层隔离（变更只影响一个 Adapter）② 渠道健康探测 + 自动降级 + 用户可见 ③ Provider 一致性测试每周真实调用一次 ④ 不依赖任何厂商的私有 SDK | 单渠道失效不影响其他渠道；UI 提示"该渠道当前不可用，已切到备选" |

| **R10** | **iOS 系统更新改变后台/权限行为** | 中 | 中等：功能退化 | 新 beta 上后台续跑失效或权限弹窗变化 | ① 每个 iOS beta 周期做一次兼容性回归 ② 后台策略做成可降级的（不依赖单一机制）③ 关注 Apple 开发者论坛与 release notes | 降级为"用户在场时运行"模式 |

| ID | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| **R11** | 用户理解成本高（"为什么它不能像 Cursor 那样一次改 20 个文件"） | 中 | 中等：转化率低 | ① Onboarding 用真实任务展示能力边界 ② 内置技能让"开箱即用" ③ 文案强调"移动场景"而非"桌面替代" |
| **R12** | 电量与发热导致卸载 | 中 | 中等 | ① 端侧模型按需加载 ② 后台工作只在充电时做重活 ③ 低电量模式自动降级 ④ 电量预算可见可控 |
| **R13** | wasm 工具链维护负担（每次升级 Python/Node 都要重建） | 高 | 中等（工程成本） | ① 版本锁定 + 构建脚本化 + CI 自动产出 ② 不追新版本，只在必要时升级 ③ 把 wasm 产物作为独立可替换 artifact |
| **R14** | 官方 Agent App 竞争（Anthropic / OpenAI 出 iOS 原生 Agent） | 中 | 高（商业模式） | ① 差异化扎根在"端侧执行 + 模型无关 + 隐私"，这三点官方不会做 ② 反向 MCP（手机当工具箱）是他们不会做的生态位 ③ 保持 BYOK 与中转站支持（官方不会支持） |
| **R15** | AI 生成代码的责任与合规 | 低中 | 中等 | ① 产物标注"AI 生成，需人工确认" ② 危险操作强制人工确认 ③ 明确的免责与使用条款 |
| **R16** | 单人/小团队交付能力不足 | 高 | 高（执行风险） | ① M-1 Spike 前置验证，尽早砍掉不可行部分 ② 工具集分批（核心 20 个先做，其余按需）③ 大量复用开源（WasmKit/GRDB/libgit2/tree-sitter） |
| **R17** | **原生 CPython 与宿主同进程 → 隔离强度弱于 WASM，模型生成的脚本可能越权** | 中 | 严重：安全模型被削弱 | 红队用例中出现"模型生成的 Python 读到了非授权路径" | ① **来源分级**：模型生成的脚本走 WasmKit 沙箱，用户自有代码才走 CPython（[05 §3.1.1](05-工具系统与执行沙箱.md)）② 包裹 `os`/`open`/`subprocess` 全套 API ③ 能力令牌在 API 层强制 ④ 沙箱逃逸测试覆盖 CPython 路径 | 若 API 层拦截被证明不完整 → **禁止执行模型生成的 Python**，只允许用户自有脚本 |
| **R18** | **FTS5 中文静默失效 → 中文项目的全文检索返回零结果且不报错** | **高（若不处理）** | 严重：中文用户体验直接崩塌（但可在开发期发现并修复） | 中文语料的 recall 测试为 0；用户反馈"搜不到自己刚写的东西" | ① 按语料选择 **CJK 分词器** 或 **`trigram`**（[07 §4.1](07-上下文与记忆引擎.md)）② 上线前用中文语料做 recall 验证 | 若 CJK 分词器不可用 → 全部改用 `trigram`（体积换正确性） |
| **R19** | **端侧模型的内存天花板低于预期（6GB 设备实测可用约 3.1GB）** | 中高 | 中等：端侧承诺缩水 | 首次探针实测发现只能跑 1-2B 模型 | ① 承诺收窄为 **≤2-3B Q4**（[13 §4.4](13-端侧模型与性能预算.md)）② 端侧与沙箱/索引**互斥调度** ③ 必要时卸载其他组件 | 端侧只保留 Apple Foundation Models（系统托管，不占我们内存） |
| **R20** | **用户把工作区选在 iCloud Drive → `.git` 被 FileProvider 损坏** | 中 | 严重：用户数据损坏（最不可接受的一类事故） | 用户报告仓库损坏 | ① 挂载时**明确警告** ② 提供"仅代码在 iCloud、`.git` 留本地"的选项 ③ 默认推荐本地容器 | 直接禁止选择 iCloud 目录（牺牲便利换安全） |
| **R21** | **App 体积达到 1-2GB（内嵌 CPython 的必然结果）→ 下载转化率下降** | **高（已确定会发生）** | 中等：影响获客，不影响功能 | 首下转化率明显低于同类；用户评论抱怨体积 | ① 用 On-Demand Resources 剥离**纯数据**（示例项目、库集合），但**解释器必须随包**（2.5.2）② 商店页与首启明确说明"为什么这么大"（"它把 Python 和你需要的库都装进来了，所以它离线也能干活"）③ 蜂窝下载引导 | 若转化率不可接受 → 启动 [Q19](#3-开放问题需要产品负责人拍板) 的 B 方案（App Store 版不含 CPython） |

## 2. 早期信号看板（工程需要盯的几个数）

| 指标 | 健康值 | 危险信号 |
|---|---|---|
| 随机中断恢复一致性测试失败率 | 0 | > 0（立刻停止其他工作修复） |
| 注入套件越权成功次数 | 0 | ≥ 1 |

| "它说做了但没做"类反馈 | 0 | ≥ 1（信任问题，最高优先级） |

## 3. 开放问题（需要产品负责人拍板）

以下 14 个问题会显著改变架构或工作量，需要在 M-1 期间定下来：

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| Q1 | 是否有自有服务器？ | A. 完全没有（纯本地 + 许可校验）B. 有（用于托管通道/同步/账号） | **A**。这是产品最大的信任资产，且大幅降低合规与运维成本 |
| Q2 | 商业模式 | A. 一次性买断（$49-79）B. 订阅（$5-9/月）C. 免费 + 托管通道内购 D. 开源核心 + 付费 App | **A + C 可选**。BYOK 之下卖订阅缺乏说服力；买断 + 可选托管通道（走 IAP）最匹配定位 |
| Q3 | 首发市场 | A. 中国优先 B. 全球同步 C. 海外优先 | **B（中文一等公民 + 英文完备）**。中转站与中文渠道是差异化，但全球付费意愿更高 |
| Q4 | 是否开源 | A. 全闭源 B. 核心闭源 + 工具/Skill 开源 C. 全开源 + 付费分发 | **B**。开源 Skill 库与策略格式能形成生态，同时保护运行时 |
| Q5 | App Store 版是否包含"运行 Python" | A. 包含（预置解释器 + 内置库）B. 不含（仅原生工具 + JS）| **A**，但严格遵守"不下载执行代码"：解释器随包、库随包、用户自带脚本属用户内容 |
| Q6 | 端侧模型的范围 | A. 仅 Apple Foundation Models B. + MLX 4B 级 C. + MLX 8B 级（限 iPad）| **A + B**。C 只作为开发者选项 |
| Q7 | 是否支持 SSH / 远程开发机 | A. 支持（作为"用户自己的远端"）B. 不支持（严守"端侧"） | **B 首版不做**，但架构上留接口。理由：一旦支持，产品叙事会被误解为"又一个远程 Agent" |
| Q8 | 品牌与域名 | 待定 Rune / 其他 | 需尽快做商标与域名查重（见 [01](01-产品定义与愿景.md) §7） |
| Q9 | 是否做 Apple Watch 伴侣 | A. 1.0 不做 B. 1.0 做通知 + 批准 | **A**（B 放 1.1）。Watch 的语音与批准体验很好，但不是 1.0 的阻塞项 |
| Q10 | 内置技能与 Workflow 的数量 | A. 少而精（8-12 个）B. 多（30+） | **A**。质量比数量重要，且要能持续维护 |
| Q11 | 是否提供"托管通道"（我们卖 token） | A. 不提供 B. 提供（走 IAP，价格含服务费） | **B 但后置**。它能降低新手门槛，但引入成本与合规负担；先做 BYOK |
| Q12 | 多用户/团队能力 | A. 单用户 B. 通过共享 Git 仓库共享策略与技能 | **B（不需要账号系统）**。共享策略文件就能实现"团队一致"，几乎零成本 |
| Q13 | 数据是否默认加密 | A. 默认开（性能略降）B. 默认关（用户可开） | **A**（会话与记忆默认加密，密钥在 Secure Enclave） |
| Q14 | 是否允许 Agent 修改自己的策略文件 | A. 完全禁止 B. 允许但需生物识别 | **A**。这条是安全模型的基石，不能松 |
| **Q15** | **是否接受"原生 CPython 与宿主同进程"的隔离强度**（决定"模型生成的 Python 能不能跑"） | A. 接受，但模型生成的脚本强制走 WasmKit（多数跑不了 → 体验下降）B. 接受并允许模型生成的 Python 走 CPython + 强制审批（体验好，隔离弱）C. 不允许执行模型生成的 Python（最安全，能力最弱） | **B**（体验优先，但必须配"来源分级 + 全 API 包裹 + 红队验证"）。**这是本设计中最需要你拍板的一条安全取舍** |
| **Q16** | 内容过滤的尺度（Guideline 1.2 强制，但会误伤代码场景） | A. 只过滤面向人的自然语言输出，代码块与文件内容完全豁免（推荐）B. 全量过滤（安全但会破坏代码任务） | **A**，并在设置页给出开关与说明 |
| **Q17** | 是否自研 Diff 视图与代码编辑器（**工作量最大的两块 UI**） | A. 自研（体验最好，工时约 4-6 人周）B. 先做简化版（纯文本 diff + 逐块接受），1.1 再升级 | **B（1.0）→ A（1.1）**。这直接影响 M2 的时间线 |
| **Q18** | 是否把 `.rune/libs` 用户自带库的**路径与格式**固定为公开约定 | A. 固定并写进文档（用户可预期）B. 内部实现，后续可改 | **A**，因为它其实是产品 API |
| **Q19** | ⭐ **App Store 版是否包含原生 CPython（≈1GB 体积）** | A. 包含（App Store 版体积约 1-1.5GB，用户开箱能跑 Python）B. 不含（体积回到数百 MB，但 App Store 用户无法跑 Python，只有原生工具 + WASM）C. 包含但把重量级纯 Python 库做成 On-Demand Resources（**只能下数据，不能下解释器**） | **A + C**。理由：**"能在手机上跑我的 Python"是核心承诺，砍掉它产品就不成立了**；体积是必须接受的代价，但要用 On-Demand Resources 把可下数据（示例项目、库集合）从首包剥离，并做好体积说明与 Wi-Fi 引导。**这条需要产品负责人明确拍板** |
| **Q20** | 是否预置"**移除下载能力**"的降级开关（应对审核波动） | A. 预置（构建期可关掉所有网络获取路径）B. 不预置 | **A**。shell/解释器类 App 属**高波动审核品类**（2020 年 iSH 曾被通知下架后撤回，2026 年执法再度收紧），有开关就能在 24 小时内出一个"零下载能力"的合规构建 |

## 4. M-1 必须回答的技术问题（附推荐答案）

| 问题 | 推荐答案 | 验证方式 |
|---|---|---|
| WASM 解释器的实际性能倍数？ | 相对原生约 5-15 倍慢（计算密集），启动延迟是主要瓶颈 | Spike 1 基准 |
| Python 包能在 wasm 上跑多少？ | 纯 Python 100%；numpy/scipy 可（预编译）；pandas 可行但重；torch/tensorflow 不可行 | 逐个验证 35 个目标库 |
| 能否用 libgit2 原生而非 wasm git？ | 能，且必须原生（性能与凭据集成） | 大仓库基准 |
| 后台静默推送能否可靠唤醒？ | 能，但时机不可控（系统决定），必须假设"可能不被唤醒" | 真机 48 小时观测 |
| Apple Foundation Models 能否满足工具调用？ | 能满足简单工具调用与分类，复杂规划交给云端 | 用真实任务对比 |
| 端侧 embedding 质量够不够？ | 系统 `NLEmbedding` 对代码检索偏弱，建议同时建 FTS5 并以 BM25 为主 | 用 50 个真实查询评测 recall@10 |
| iOS 键盘扩展的内存限制是否允许调用模型？ | 允许发起轻量请求，但**禁止**加载运行时会话 | 真机测试扩展内存水位 |
| 是否有办法在 App Store 版里做热更新？ | 没有（也不该有）。所有能力随包分发 | — |

## 5. 如果只能做三件事

如果资源被迫砍到极限，保留这三件，其余全部可延后：

1. **可信的本地执行**（VFS + 沙箱 + 检查点 + 事件日志）—— 这是全部差异化的地基。
2. **iOS 生命周期的续跑能力**（Goal + Job + 检查点恢复）—— 这是"手机 Agent"区别于"桌面 Agent"的唯一不可替代之处。
3. **透明与可控**（模型/成本可见、审批可批量、一切可回滚、审计可导出）—— 这是用户敢把活交给它的前提。

**可以砍的**：多模态原生能力、Watch、键盘扩展、记忆反思、Workflow、iPad 多窗口、图表生成、中转站高级特性。
