# 05 · 工具系统与执行沙箱

> **摘要**：iOS 上不能 `fork`/`exec`，所以"给模型一个 Bash"这条路是死的。Rune 的答案是**三层工具实现策略**：
> **① 原生 Swift 工具**（快、可审计、覆盖 90% 需求）→ **② WASM 沙箱**（跑模型/用户写的任意脚本）→ **③ 原生能力桥**（iOS 系统能力）。
> 本文定义完整工具目录、VFS 语义、VM 设计、依赖管理，以及每条"在手机上不可能"的正面回答。

---

## 1. 设计起点：三个错误的直觉

| 直觉 | 为什么错 | Rune 的做法 |
|---|---|---|
| "给模型一个 shell 就够了" | iOS 没有 shell 可给；即使套一个解释器，`ls/cat/grep` 这些最常见的操作每次都要启动一个 VM，慢且费电 | **把最常见的操作做成原生工具**：`read_file`/`glob`/`grep_search` 直连 Swift，微秒级 |
| "所有东西都塞进 WASM 最安全" | WASM 解释执行比原生慢一个数量级；`rg` 10 万文件在解释器里要几十秒 | **原生工具**负责重活，**WASM** 只负责"任意代码"这一类无法预知的任务 |
| "模型写的代码必须有 root" | 手机上"root"意味着毁掉用户数据且不可恢复 | 每个执行都是**带能力令牌的沙箱调用**，写路径白名单 + 出口白名单 + 快照兜底 |

**一句话原则：能原生就原生，必须跑任意代码才进沙箱，进沙箱必须带能力令牌。**

---

## 2. 工具目录

命名用 `snake_case`（对各家模型最友好）。`[N]` = 原生实现，`[W]` = WASM 沙箱，`[S]` = 系统能力桥。

### 2.1 文件与工作区

|---|---|---|---|

| `read_file` | N | 读文件，支持行范围 / 字节范围 / 尾部 N 行；自动识别二进制并拒绝；返回带行号文本 | safe |

| `apply_patch` | N | **结构化补丁**：一次调用完成多处编辑，支持上下文锚定与模糊容错，失败时整体不落地 | modifying |
| `delete_path` | N | 删除（默认进"回收站"目录而非真删，保留 N 天） | dangerous |

### 2.2 检索（原生引擎，这是速度的生命线）

| 工具 | 实现 | 说明 |
|---|---|---|
| `glob` | N | 通配匹配（`**/*.swift`），结果按 mtime 排序，带数量上限 |
| `grep_search` | N | 正则内容搜索：并行遍历 + 内存映射 + 字面量预筛；支持 `-i`、上下文行、文件类型过滤、`--count` |
| `find_symbol` | N | 轻量符号索引（tree-sitter Swift/Python/TS/Go/Rust 语法层），按名字找定义位置 |
| `semantic_search` | N | 向量检索工作区（端侧 embedding），自然语言找代码/文档 |
| `git_log_search` | N | 在历史提交信息与 diff 中检索（"这个函数什么时候改的"） |
| `outline_file` | N | 文件结构大纲（类/函数/段落），让模型不必读全文 |

> `grep_search` 是 Rune 性能的核心资产：目标 **10 万文件 ≤ 3s**、单文件 ≤ 20ms。实现要点：`mmap` + SIMD 字面量预筛（memchr 路线）+ 只在候选文件上跑正则 + 多核并行 + 跳过二进制与 `.git`。

### 2.3 执行

| 工具 | 实现 | 说明 | 默认审批 |
|---|---|---|---|
| `run_python` | **原生 CPython** | ⭐ **不用 WASM**。走 **CPython XCFramework（`Python-Apple-support`）+ 自研 no-fork 垫片**（Pyto / a-Shell / Pythonista 的同款路线，App Store 已验证）。支持 pip 安装**纯 Python 包**；**C 扩展不可用** | 协作档起免批 |
| `run_javascript` | **JSC / quickjs-ng** | JavaScriptCore 仅 LLInt 解释器（第三方无 JIT）；需要更可控的沙箱时用 quickjs-ng（活跃、无 JIT、可 SwiftPM 嵌入） | 同上 |
| `run_shell` | **自研命令解释器** | ⚠️ **不做"通用 POSIX shell"**。参照 a-Shell 的 `ios_system` 模式：shell 由我们实现，**命令表映射到原生实现或 WASM 模块**，**全程无 fork/exec**。覆盖模型最常用的管道表达 | 需批（默认） |
| `run_wasm` | **WasmKit 沙箱** | 执行用户/模型编译出的 `.wasm` 模块（a-Shell 已证明"随包编译链 + 执行用户 wasm"可上架） | 需批 |
| `run_tests` | N+沙箱 | **智能测试入口**：自动探测项目类型（pytest/npm test/swift test/go test/cargo test）→ 选对命令 → 执行 → 解析成结构化报告（通过/失败/耗时/首个失败用例） | 协作档免批 |
| `run_build` | N+沙箱 | 构建入口（含编译错误结构化解析） | 协作档免批 |
| `start_job` / `job_status` / `job_output` / `job_kill` | N | 后台作业管理：长任务转后台，增量读输出，支持 wait 与取消 | safe |
| `sandbox_snapshot` / `sandbox_restore` | N | 显式创建/恢复沙箱快照 | modifying |

**为什么 `run_shell` 是"自研解释器"而不是"随包一个 sh"**：iOS 上没有真正的 shell 可给（`bash`/`zsh` 都需要 fork 子进程）。a-Shell 的做法是把每个命令注册成原生函数，由自研解释器调度 —— 这是唯一可行的路，也是我们已经验证过的路（[附录 B §4](附录B-技术选型核实表.md)）。

**为什么同时提供 `run_python` 和 `run_shell`**：模型对 shell 的肌肉记忆很强，硬性禁止会显著降低其表现。但两者都在受控环境内，且 `run_shell` 默认需要审批——把"方便"和"安全"分成两档，而不是二选一。

## 3. 四类执行环境

```
                        ┌──────────────────────────────────┐
   模型/用户代码 ─────▶ │  BenchSupervisor (actor)          │
                        │  能力令牌校验 · 限额 · 超时强杀     │
                        └───┬────────┬────────┬────────┬────┘
                            │        │        │        │
        ┌───────────────────┘        │        │        └──────────────────┐
        ▼                            ▼        ▼                           ▼
┌──────────────────┐  ┌──────────────────┐ ┌────────────────┐ ┌────────────────────┐
│ ① 原生 CPython   │  │ ② WasmKit 沙箱   │ │ ③ JS 沙箱      │ │ ④ 原生能力桥        │
│ XCFramework +    │  │ 用户/模型编译的   │ │ JSC(LLInt) /   │ │ Photos/Calendar/   │
│ no-fork 垫片     │  │ .wasm 模块        │ │ quickjs-ng     │ │ Camera/Speech/OCR  │
│ 纯 Python 包可用 │  │ 少量 WASI CLI     │ │ 无 JIT         │ │ 无代码执行          │
│ C 扩展不可用     │  │ 无 socket / fork  │ │ 无 fetch/无 IO │ │ 仅令牌授权范围      │
└──────────────────┘  └──────────────────┘ └────────────────┘ └────────────────────┘
        └───────────────────────┴────────────────┴──────────────────────┘
                                       ▼
                            VFS（唯一文件入口）
                   /workspace · /user-docs · /tmp · /artifacts
```

> ⭐ **与初版设计的关键修正**：初版打算"把 Python 编译成 WASM 在 WASI 里跑"。核实后这是**死路**：CPython 的 wasm 构建是实验状态（最后提交 2024-03）、默认单文件打包约 **150MB**，且 **WASI 不支持线程、子进程与 socket**，大量测试失败。
> **正确路线是原生 CPython**（CPython XCFramework，PEP 730 已把 iOS 列为支持平台），配合自研的 no-fork 垫片 —— 这正是 Pyto、a-Shell、Pythonista 用的路线，**且都在 App Store 在架**。

### 3.1 环境 ①：原生 CPython（Python 的主力环境）

| 维度 | 设计 |
|---|---|
| 运行时 | CPython 3.13/3.14/3.15 的 **XCFramework**（`Python-Apple-support` 构建，iOS 13+ / arm64 + 模拟器；**Pyto 的二进制就来自它**），静态链接进 App |
| ⚠️ **结构性约束（官方文档明确）** | iOS 上**没有 `python` 可执行文件，也没有 REPL**；且 **App Store 要求所有二进制模块必须打包成 framework（`.so` 需后处理）** → **动态加载第三方 C 扩展在 iOS 上结构性不可行，所有二进制模块必须随包预置**。这直接决定了 §5.2 的依赖管理策略，也决定了 App 体积（见下） |
| ⚠️ **体积代价（实测）** | **内嵌 CPython 的 iOS App ≈ 1GB 起步；带完整工具链 ≈ 2GB**。实测：Pyto **930.5MB**、Pythonista **852.9MB**、**a-Shell 1950MB**（因 iOS 动态库规则生成了 2000+ 个 framework）。**这是本项目必须接受的体积成本**，并直接影响下载转化率与渠道策略（见 [15 Q19](15-风险登记册与开放问题.md)） |
| no-fork 垫片 | 自研：把 `os.system` / `subprocess` / `os.fork` / `os.exec*` **全部替换为"命令分发到原生实现或 WASM 模块"**（a-Shell 的 `ios_system` 模式）。**不允许任何路径产生真实子进程** |
| 文件访问 | 通过 `sys.path` 与 `os` 层拦截，重定向到 VFS；`open()` 落到 VFS 事务，可回滚 |
| 网络 | 默认**不注入 socket**；需要网络的脚本必须声明，且出口过白名单（走宿主代理） |
| 包管理 | ✅ **纯 Python 包**可安装（用户自带 wheel / 目录，见 §5.2）；❌ **C 扩展不可用**（且必须随包预置，无法运行时加载） |
| 隔离强度 | ⚠️ **弱于 WASM**：CPython 与宿主同进程，通过 API 层面拦截而非硬件隔离。因此它**只对"可信来源的代码"开放**（用户自己写的 / 我们内置的工具链），**模型自由生成的 Python 走环境 ②** |
| 限额 | 通过 `sys.settrace` 级钩子 + 子线程超时 + 内存水位监控实现软限额；**强杀靠独立执行线程 + 主动中止**（不如 WASM 的计数器干净，这是已知代价） |

**为什么还要保留它**：因为用户要的是"能跑我的 Python"，而不是"能跑一个 Python 的子集"。**数据科学生态（numpy/pandas 的纯 Python 替代或预编译版本）是 C 类用户的核心诉求**，而 WASM 路线的 150MB 包体与生态缺失无法满足。代价是隔离强度下降——用"来源分级"来补偿（下方 §3.1.1）。

#### 3.1.1 来源分级（弥补 CPython 隔离弱于 WASM）

| 代码来源 | 执行环境 | 理由 |
|---|---|---|
| 用户自己写的脚本（在工作区里、由用户创建） | ① 原生 CPython | 等价于用户在编辑器里按"运行" |
| 内置技能/夹具携带的脚本 | ① 原生 CPython | 随包分发，已审计 |
| **模型生成的临时脚本** | **② WasmKit 沙箱**（若无法编译为 wasm 则降级为 ① + 强制审批） | 模型生成 = 半可信，用更强的隔离 |
| 来自工作区但来源不明的脚本（例如克隆来的仓库里的 `setup.py`） | ① + 强制审批 + 污点标记 | 这是供应链攻击的典型入口 |

> **这条分级是本设计里最重要的安全补偿机制之一**：不假装 CPython 沙箱和 WASM 一样强，而是**按来源选择隔离强度**。

### 3.2 环境 ②：WasmKit 沙箱

| 维度 | 设计 |
|---|---|
| 运行时 | **WasmKit**（纯 Swift 实现，MIT，随 Swift 工具链分发官方 WS 工具）。备选 **wasm3**（iOS 为官方平台，作为兜底）。⚠️ **WasmKit 的实际最低部署目标为 iOS 18**（`Package.swift` 声明 `platforms: [.iOS(.v18)]`，需 Swift 6.3 工具链）—— 对我们不是问题（我们目标 iOS 26+），但**若将来要下沉到 iOS 16/17，必须退回 wasm3（代价：无 SIMD）** |
| 为什么不用 Wasmtime/WAMR/Wasmer | Wasmtime 的 Cranelift/Winch **需要运行时生成可执行页** → iOS 不可用（Pulley 解释器可用但明显更慢）；WAMR 的 iOS 配置是纯解释器（AOT/JIT 全关，**SIMD 在 iOS 上实际不可用**）；**Wasmer 的 iOS 示例整段被注释掉**，SwiftyWasmer 已归档 → 不可行（详见 [附录 B](附录B-技术选型核实表.md)） |
| 提案支持 | WasmKit 支持 **Bulk memory、Fixed-width SIMD、Threads & Atomics、Exception Handling、Tail call、Memory64、Multi-value**；**GC 不支持**；**组件模型仍在开发中**；WASI 0.1 覆盖"大部分系统调用"（非全部） |
| 性能预期 | WasmKit 第 3 代寄存器机在 CoreMark 上约 **2,150 iter/s**（2020 M1，release），相对 Wasmtime JIT **慢约 5-6×**，相对原生 C 慢一个数量级（`[不确定]`）。**这意味着：计算密集任务应走原生工具或原生 CPython，WASM 用于"必须隔离"的场景** |
| 用途 | ① 模型生成的临时脚本（隔离更强）② 用户编译的 `.wasm`（a-Shell 已证明此模式可上架）③ 少量随包 WASI CLI（`zip`/`unzip`/`xz` 等 —— a-Shell 已用 `pkg install zip` 的方式验证） |
| 限制 | **无 socket、无 fork**（WASI 规范本身就没有）。因此 wasm 里的"git"、"网络请求"都不可行 —— **这也再次证明 git 必须走原生 libgit2** |

### 3.3 环境 ③：JS 沙箱

| 维度 | 设计 |
|---|---|
| 运行时 | **JavaScriptCore（系统自带）** 作为默认；需要更强可控性时用 **quickjs-ng**（活跃维护、无 JIT、可 SwiftPM 嵌入） |
| ⚠️ 无 JIT 的代价（**有实测数据**） | 第三方 App 无法获得 JIT，JSC 退化为**仅 LLInt 解释器**（无 Baseline/DFG/FTL）。公开测量（以 iOS 锁定模式为"仅解释器"的代理）：Speedometer 3.0 **−32%/−33%**、**JetStream 2 −88%**（156→19）、MotionMark −16%；V8 的 `--jitless` 在 Speedometer 2.0 上约 **−40%**。⇒ **可写"解释器模式相对 JIT 慢约 2-8×，基准越偏脚本/正则开销越大"**。另：⚠️ **WKWebView 有 JIT，但拿不到它的 `JSContext`** → 只能通过 `evaluateJavaScript` / `postMessage` 通信。**因此不要把热路径放在 JS 里** |
| 用途 | Workflow 脚本、轻量数据处理、TS/JSON 变换 |
| 注入的 API | Workflow：`phase/log/args/agent/pipeline/parallel`；通用：`console`、`JSON`、`Math`、`crypto.subtle`、受限 `vfs.*` |
| 禁止 | 无 `fetch`、无 `XMLHttpRequest`、无 `setTimeout`（防逃逸与死循环） |
| 上限 | 墙钟 30s（`agent()` 调用期间不计时）、内存 256MB、栈深限制 |
| 中断 | JSC 通过 `TerminateExecution` 强杀 |

**关于 Node**：`nodejs-mobile` 在 iOS 上**使用 V8**（官方 CHANGELOG："Uses V8 on iOS instead of ChakraCore"），而上游依赖 **Node 18 已于 2025-04-30 EOL**（当前 Node 24.x），上游最后发布 v18.20.4（2024-10），社区 fork 亦停在同一版本 → **需自研兜底、长期不可依赖，不随包**。需要"类 Node 环境"时，用 JSC 沙箱 + 自研的 fs/path/buffer/zlib 垫片（覆盖构建脚本的常见需求），并在文档里明确"这不是 Node"。

### 3.4 环境 ④：原生能力桥

不是"执行代码"，而是"以最小权限调用系统能力"。每个能力调用：
1. 检查 `Capability.nativeAPIs` 是否包含该项
2. 检查系统权限当前状态（未授予 → 触发系统授权或拒绝并说明）
3. 记录审计事件（谁调的、参数摘要、返回了什么类别）
4. **最小化返回**：相册只返回用户选中的资产引用，不返回整个库；定位只返回精度降级后的坐标

## 4. 虚拟文件系统（VFS）

### 4.1 路径空间

```
/                      虚拟根（不可枚举，只提供挂载点）
├─ workspace           主工作区（用户用文件选择器授权的目录，通常是一个 Git 仓库）
│  └─ …                真实路径通过 security-scoped bookmark 持久化访问
├─ user-docs           用户授权的其他目录（可多挂载：iCloud Drive / 本地 / 第三方 App 目录）
├─ inbox               分享收件箱（其他 App 分享进来的文件落这里）
├─ artifacts           大产物与大输出（不参与 Git，不受 .gitignore 影响）
├─ tmp                 临时目录（可被系统随时清理，重启不保证保留）
├─ runes               技能与 Workflow 定义
├─ memory              记忆库（数据库 + 嵌入向量，二进制不可直读）
└─ sys                 只读：运行时版本、设备能力、限额、已授予能力清单
```

**Why 虚拟根**：模型看到的是一个稳定的 Unix 风格世界，但底层映射可随时变化（用户换工作区、iCloud 未下载、文件被移到"最近删除"）。VFS 层负责把这些现实差异藏起来，并在无法满足时给出**结构化错误**（"iCloud 文件尚未下载，已触发下载，请 3 秒后重试"）而不是"no such file"。

### 4.2 关键语义

| 语义 | 规定 |
|---|---|
| 路径规范化 | 拒绝 `..` 逃逸、符号链接穿越到挂载点外、`~` 扩展（无 home 概念） |
| 大小写 | 遵循底层卷（APFS 默认不敏感）；VFS 内部统一做大小写不敏感匹配以避免"在 Mac 上能跑在 iOS 上不能" |
| 写入 | **默认原子**：写临时文件 + `replaceItem`；大文件走分块追加 |
| 编码 | 默认 UTF-8，检测到其他编码（GBK 等）自动转换并告知模型 |
| 二进制 | `read_file` 拒绝返回二进制内容，改为"这是 PNG，1280×720，可用 image_* 工具处理" |
| 大文件 | > 8MB 不走 `read_file`，强制 `read_artifact` 分片 + `grep_search` 定位 |
| 不可见文件 | `.git/`、`node_modules/`、`DerivedData/` 等通过"忽略清单"默认排除在 glob/grep 之外（可显式包含） |
| 外部变更 | ⚠️ **iOS 没有 FSEvents，也没有通用的递归目录监听 API**。因此采用三层组合：① `NSMetadataQuery`（iCloud/文件提供者场景）；② `NSFilePresenter`（**只对"经文件协调器"的改动通知，原始写入不通知**）；③ `DispatchSource` 文件系统源（只对已合法打开的描述符有效）。**兜底：前台恢复时做 mtime + size 全量比对**，检测"用户/其他 App 改了文件"并在时间轴上标记。 |
| 环境变量重映射（照抄 a-Shell 的经验） | iOS 上**只能写 `~/Documents/`、`~/Library/`、`~/tmp`**，但大量 Unix 程序假设配置在 `$HOME`。做法：把 `$HOME` 及一系列相关变量**重定向到容器的 `Documents`**，配置与包数据放 `Library`，`cd` 永远能回到 `Documents`。这是在 iOS 上跑用户脚本的必要垫片。 |
| ⚠️ 绝不把工作区放在 iCloud Drive | **git worktree + `.git` 放在 FileProvider 同步目录会被损坏**（有实证事故）。工作区默认在本地容器，靠 git remote 同步；若用户坚持选 iCloud 目录，**在挂载时明确警告**，并提供"仅代码在 iCloud、`.git` 留在本地"的选项。 |
| 授权目录的生命周期 | 目录授权必须用 `bookmarkData(options: .withSecurityScope)` 持久化，**绝不持久化原始 URL**；每次访问成对调用 `startAccessingSecurityScopedResource()` / `stopAccessingSecurityScopedResource()`。⚠️ **未配对的 stop 会泄漏内核资源，最终导致所有沙箱扩展失效直到 App 重启** —— 这是 iOS 上最容易踩且最难查的坑之一，必须用 RAII 包装（`withSecurityScope { }`）强制配对。 |
| 用户撤销授权 / 目录被移走 | 每次使用前校验 bookmark 是否 stale；失效则**不静默失败**，而是提示"工作区授权已失效，请重新选择目录"，并保留会话状态以便恢复。 |

### 4.3 快照与回滚（写时复制）

```
snapshot():
  对每个挂载点：
    若同一 APFS 卷且支持 clonefile → 为本次要修改的路径建立 clone 副本（O(1) 元数据操作）
    否则 → 记录"写前日志"：修改前把原字节追加到 /artifacts/.wal/<snapshotID>/

restore(snapshotID):
  按逆序回放写前日志，或从 clone 副本替换回原路径
  冲突处理：若文件在快照后被外部修改 → 提示用户选择"覆盖 / 保留外部版本 / 另存为"
```

**代价实测目标**：单文件快照 < 5ms，一次 Turn 内 50 个文件的快照开销 < 200ms，磁盘增量按实际改动量计（不是整目录复制）。

## 5. 每个环境里能跑什么（随包清单）

### 5.1 随包分发的能力清单（App Store 构建）

| 环境 | 内容 | 覆盖场景 | 成熟度 |
|---|---|---|---|
| **原生 CPython 3.13/3.14** | 标准库（完整）+ 纯 Python 生态 + 随包精选包 | 数据清洗、脚本、正则、JSON/CSV、文本处理、算法 | ✅ 生产可用（Pyto/a-Shell/Pythonista 先例） |
| **原生工具集（Swift）** | 文件、glob、grep、Git(libgit2)、diff/patch、图像(Core Image)、表格、HTTP、哈希、压缩 | **约 90% 的真实任务** | ✅ 生产可用 |
| **自研 shell 解释器** | `ls cat head tail wc sort uniq cut sed(子集) grep find xargs tr diff patch tar gzip base64` → 全部映射到原生实现 | 模型习惯的管道表达 | ✅ 生产可用（a-Shell 的 `ios_system` 模式） |
| **WASM 模块** | 用户/模型产出的 `.wasm` + 少量 WASI CLI（`zip`/`unzip`/`xz`） | 强隔离下的任意计算 | ✅ 可行（a-Shell 已上架验证）；⚠️ 性能约为 JIT 的 1/5-1/6 |
| **JS（JSC / quickjs-ng）** | Workflow 运行时 + 自研 fs/path/zlib 垫片 | 编排、纯 JS 工具、轻量变换 | ✅ 可行；⚠️ 无 JIT，热路径不要放这里 |
| **Git** | **原生 libgit2**（自建 XCFramework） | 全部本地与远端 Git 操作 | ✅ 生产可用（Working Copy 同款路线） |

**明确不随包的**：`bash`/`zsh`/`coreutils` 真二进制（无 fork/exec）、Node 运行时（依赖已 EOL 的 Node 18 且 iOS 上仍是解释器级）、CPython-wasm（150MB + 无线程/子进程/socket，实验状态）、任何需要 `dlopen` 的组件。

### 5.2 依赖管理（最棘手的问题，必须正面回答）

手机上"能不能 pip install"是决定用户是否失望的第一个问题。Rune 的答案分三层，且**如实告知边界**：

| 层级 | 机制 | 覆盖 | App Store 轨 |
|---|---|---|---|
| **L1 内置** | 随包分发精选的**纯 Python** 包（以及为 iOS 预编译的少数科学计算包） | 首批目标 ~35 个：`numpy`(预编译)、`pandas`(视体积决定是否内置)、`python-dateutil`、`pytz`、`regex`、`pyyaml`、`jinja2`、`tabulate`、`sqlalchemy`(sqlite)、`pydantic`、`httpx`、`beautifulsoup4`、`openpyxl`、`matplotlib`(Agg，可选) … | ✅ |
| **L2 用户自带** | 用户通过"文件"App 把 `.whl`／纯 Python 源码目录放进 `workspace/.rune/libs/`，运行时优先加载 | **纯 Python 包 100% 可用** | ✅（用户自有内容） |
| **L3 从索引获取** | 用户显式开启后，可从用户配置的索引获取**纯 Python** 包；**拒绝任何含二进制扩展的包**；全程展示将要下载什么 | 覆盖长尾的纯 Python 包 | ❌ **App Store 轨关闭**（零网络代码路径，见 [11 §3.3](11-AppStore合规与分发.md)）；仅 Full 轨可选 |

**诚实的产品文案**（这是很多手机 Agent 失信的地方）：
> 内置约 35 个常用库；需要其他库时，把**纯 Python 包**放进 `.rune/libs` 就会自动生效。**带 C 扩展的包（如需要编译的库）在手机上无法安装** —— 这是 iOS 的限制，不是 Rune 的限制。

**并且**：凡是高频需求（CSV/Excel、图像处理、HTTP、JSON 变换、正则），我们都提供**原生工具**绕开 pip ——**让用户不需要 pip 就能完成任务，比让用户能 pip 更重要。**

### 5.3 明确做不到的（设计上不假装能）

| 做不到 | 原因 | 替代方案 |
|---|---|---|
| `fork` / `exec` / 启动任意二进制 | iOS 无 `posix_spawn`，`Process` 是 macOS 专属 | 自研 shell 解释器 + 原生命令表 |
| JIT / `PROT_EXEC` / 运行时生成可执行页 | 无 iOS JIT entitlement（详见 [附录 B §4](附录B-技术选型核实表.md)） | 解释器；WASM AOT 预编译；Core AI 的 `.aimodel` AOT |
| `dlopen` 下载的 `.dylib` | 代码签名与库校验拦截 | 全部随包 |
| 编译 C/Rust/Go 扩展给 Python 用 | 无可用链接器与动态库加载路径（a-Shell 官方也明确说"编译器还无法产出 Python 可用的动态库"） | 用内置库或原生工具替代 |
| 跑 Docker / 起监听端口 | 无 fork、无原始 socket | 内存内服务桩（SQLite、进程内 HTTP 处理） |
| 装 gcc/make 类系统工具链 | — | 原生工具替代；构建类任务交给用户自己的 CI |
| 后台长时间跑测试 | 后台时间受限 | Job + 检查点续跑 + `BGContinuedProcessingTask`（[10](10-后台执行与可靠性.md)） |
| 依赖 GPU/CUDA 的框架（torch 等） | 体积与运行时都不成立 | 端侧推理走 [13](13-端侧模型与性能预算.md) 的 Apple 栈 |
| 把 git worktree 放在 iCloud Drive 同步目录 | **FileProvider 会损坏 `.git`**（有实证事故） | 工作区默认放本地容器；靠 git remote 同步；UI 上明确警告 |

## 6. 网络出口策略（Egress）

**模型可以读一个网页，但网页的内容不能变成"让 Agent 往外发数据"的指令。** 出口策略是这条防线的执行点。

```toml
# 出口策略（默认保守）
[egress]
default = "deny"                 # 默认拒绝一切出站

[[egress.allow]]
host   = "api.openai.com"        # 模型渠道自动加入白名单
reason = "模型推理"

[[egress.allow]]
host   = "github.com"
methods = ["GET", "POST", "PATCH"]
reason  = "Git 与 PR"

[[egress.allow]]
host_suffix = ".githubusercontent.com"
methods = ["GET"]
max_bytes = 200_000_000

[[egress.deny]]
host_suffix = "*"                # 未列出的全部拒绝
```

**规则：**
1. 域名必须显式允许；`host_suffix` 通配必须写明用途。
2. 请求体超过阈值（默认 64KB）时，UI 展示 **payload 摘要 + 目标域名 + 触发原因**，需确认（可在策略里对特定域名豁免）。
3. **从不可信内容里"学到"的 URL 一律标记为 `tainted`**：第一次访问需确认，之后 24 小时内对该域名的访问需再次确认（防注入外发）。
4. 所有出站请求（含模型调用）写入出口审计表：时间、域名、方法、字节数、触发工具、会话与 Turn。
5. 出口审计页一键导出（用户可以把"这台手机上的 Agent 都往外发了什么"发给别人看）。

## 7. 大文件与大输出：手机上最重要的一条工程纪律

| 场景 | 错误做法 | Rune 做法 |
|---|---|---|
| 读 200MB 日志找报错 | 读进内存，塞进上下文 | `grep_search` 定位命中行 → `read_artifact(range)` 只取上下文各 20 行 |
| 生成 5MB 报告 | 全文回灌 | 写入 `artifacts/`，上下文里放"已生成报告（5.2MB，327 行），摘要：…" + 句柄 |
| 处理 1GB CSV | 整表加载 | 分块流式处理（内置换行/分块迭代器）+ 只保留聚合结果 |
| 看一张 12MP 照片 | base64 塞进请求 | 端侧缩放到模型输入尺寸（长边 ≤1568px）+ JPEG q=0.8 → 约 200KB |
| 展示 500 行 diff | 全文回灌 | 结构化 diff（文件级 + 块级）+ 模型只看"变更意图"，全文由 UI 渲染 |

**上下文预算分配（默认，单次模型调用）：**

| 区块 | 预算 |
|---|---|
| 系统提示（层 1+2） | 25% |
| 会话历史（含压缩摘要） | 30% |
| 本轮工具结果 | 25% |
| 记忆检索命中 | 10% |
| 留给输出 | 10% |

超预算时按 `记忆 → 历史 → 工具结果` 的顺序压缩（先摘要、再丢弃最低相关性片段）。

## 8. 工具开发规范（写给实现者）

新增一个工具必须满足的检查清单：

- [ ] `ToolSpec` 完整：名称、描述（含"何时不要用"）、严格 inputSchema、并发属性、幂等性、风险等级、审批策略、输出形态
- [ ] 声明 `requirements: Set<CapabilityKind>`（策略引擎据此判定，不允许"运行时偷偷访问"）
- [ ] 所有文件访问走 `VFS`，所有网络走 `EgressProxy`，禁止直接 `FileManager`/`URLSession`
- [ ] 输出走 `ToolResult`：`summary`（给模型，≤ 预算）+ `artifacts`（全文）+ `metrics`
- [ ] 失败返回结构化错误（分类 + 可读原因 + 建议的下一步），不抛裸 error
- [ ] 支持协作式取消（循环内检查 `Task.isCancelled`）
- [ ] 单测：正常路径 + 边界（空文件/超大/权限拒绝/网络超时/编码异常）
- [ ] 有一个"黄金用例"加入回放夹具（真实模型调用 → 工具调用 → 断言结果）

## 9. 工具失败的兜底策略（长任务不死的秘密）

| 失败 | 兜底 |
|---|---|
| `read_file` 路径不存在 | 自动尝试：相似路径（编辑距离）→ 大小写变体 → 在 workspace 内 `glob` 同名文件，并把候选返回给模型 |
| `grep_search` 无命中 | 返回"无命中"，并附"是否要扩大范围？当前排除了 `.git`、`node_modules`，共有 N 个文件被排除" |
| `edit_file` 匹配不唯一 | 返回所有匹配位置 + 行号 + 上下文，建议改用 `apply_patch` 带更多上下文 |
| `run_python` 缺库 | 返回结构化错误 `ModuleNotFoundError: pandas` + "内置库清单可用；纯 Python 包可放入 .rune/libs" |
| `run_*` 超时 | 返回已完成部分（stdout/stderr 已有内容）+ "建议改用 Job 模式或缩小输入范围" |
| 沙箱内存超限 | 返回峰值用量 + 建议（分块处理 / 用原生工具 / 提高限额） |
| 出口被拒 | 返回被拒域名 + 策略来源 + "可在设置中加入白名单（需你确认）" |
| Git 认证失败 | 返回"凭据过期/缺失" + 一键跳到凭据设置 |
| 工作区被系统卸载（iCloud 未下载） | 触发下载 + 告知等待，可继续做不依赖该文件的部分 |
